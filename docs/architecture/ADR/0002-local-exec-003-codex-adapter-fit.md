# 0002 — LOCAL-EXEC-003: Codex Local Adapter dependency-fit against current official Codex CLI/app-server behavior

Status: Accepted — 2026-09-11

## Context

Rev98/Rev101 Family "LOCAL-EXEC-003" (Phase L2 of the Local Execution / Device Worker capability) requires "a fresh dependency-fit ADR against current official OpenAI Codex CLI/SDK/app-server behavior, local ChatGPT-authenticated readiness without uploading subscription credentials, start/resume/working-directory/sandbox/approval/network policy, structured events, cancellation, usage-limit mapping, checkpoint/evidence return." This is explicitly genuine, time-sensitive external research, not something this session may fabricate from memory or invent from first principles — this ADR is that research, dated to today.

`LOCAL-EXEC-001` already defines the generic `LocalWorkerAdapter` port (`execute(request: LocalWorkerAdapterRequest): LocalWorkerAdapterResult`) and `LOCAL-EXEC-002` already defines the generic, provider-neutral bridge control-channel protocol (`BridgeProtocolMessageKind`, envelope validation, replay protection). Rev99/100's own instruction is explicit: "no second worker router/IAM/workflow engine." This ADR's job is to determine what a Codex-specific implementation actually needs to satisfy, so LOCAL-EXEC-003 can compose those two existing ports/protocols rather than invent a third system.

## Research findings (sourced, dated 2026-09-11)

- **App Server / structured events**: Codex's "App Server" is the single JSON-RPC-based interface that powers the CLI, VS Code extension, web app, macOS app, and third-party IDE integrations. The protocol is fully bidirectional — a client request can produce many server notifications, and the server can itself initiate a request (e.g. an approval prompt) that pauses the turn until the client responds. Structured log events carry service name, CLI version, env tag, conversation id, model, and sandbox/approval settings as metadata. ([Codex App Server](https://developers.openai.com/codex/app-server), [Unlocking the Codex harness](https://openai.com/index/unlocking-the-codex-harness/))
- **Sandbox modes**: exactly three — `read-only`, `workspace-write`, `danger-full-access`. Codex CLI enforces these via OS-level mechanisms; by default, write access is limited to the active workspace and network access is off. ([Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security))
- **Approval policy**: exactly three — `untrusted`, `on-request`, `never`. Sandbox mode governs what Codex may technically touch; approval policy governs when it must pause and ask first — the two are independent dimensions. ([Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security))
- **Network policy**: off by default; explicitly configurable independent of sandbox/approval choice. ([Codex CLI Guide](https://blakecrosley.com/guides/codex))
- **Resume**: `codex exec resume <id>` resumes a specific prior session; `--last` resumes the most recent session scoped to the current working directory; `--all` widens scope to any directory. Sessions persist as rollout files under `~/.codex/sessions`. A resume is therefore always bound to an opaque prior-session reference, never a raw transcript this module would need to parse. ([Developer commands](https://developers.openai.com/codex/cli/reference))
- **Authentication / local readiness without credential upload**: a user authenticates via `codex login` (ChatGPT sign-in, subscription-based) or `codex login --with-api-key` (usage-based); `codex login status` reports the current authenticated state locally. The resulting session material is written to `~/.codex/auth.json` on the device and is never something this repository's cloud side should ingest — this ADR's design constraint is that only a locally-derived *readiness status* (not a token, not the file, not its contents) ever crosses the bridge. ([Using Codex with your ChatGPT plan](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan))
- **Usage-limit mapping**: usage is tracked in two real windows — a rolling 5-hour window and a weekly quota — shared across CLI, web, and IDE surfaces for a ChatGPT-authenticated session; the CLI's own `/status` command surfaces remaining allowance. ([Codex Usage Limits discussion](https://github.com/openai/codex/discussions/2251), [Using Codex with your ChatGPT plan](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan))

## Decision

`src/domain/codex-local-adapter.ts` models exactly the dimensions above as closed, validated types and pure mapping/validation functions, and composes — never redefines — `LOCAL-EXEC-001`'s `DevicePolicy`/`isWorkspaceRootAllowed`/`LocalTaskLease`/`LocalTaskCheckpoint`/`createLocalTaskCheckpoint`/`LocalWorkerAdapterResult`/`LocalWorkerAdapterOutcome` and `LOCAL-EXEC-002`'s `BridgeProtocolMessageKind`/`isRecognizedBridgeMessageKind`:

- `CodexSandboxMode = "READ_ONLY" | "WORKSPACE_WRITE" | "DANGER_FULL_ACCESS"` — a direct 1:1 projection of Codex's own three real sandbox modes (renamed to this repo's `UPPER_SNAKE` convention; no fourth mode invented).
- `CodexApprovalPolicy = "UNTRUSTED" | "ON_REQUEST" | "NEVER"` — same direct projection.
- `CodexNetworkPolicy = "DISABLED" | "ENABLED"` — fails closed to `DISABLED` wherever a caller does not explicitly request `ENABLED`, matching the real CLI's own default-off posture.
- `CodexAuthReadinessStatus = "READY_CHATGPT_SESSION" | "READY_API_KEY" | "NOT_AUTHENTICATED"` — a locally-reported status only; no field anywhere in this module can carry a token, cookie, or `auth.json` contents, structurally enforced by this type never having such a field.
- `CodexRunMode = "START" | "RESUME"`, with `CodexRunRequest`/`createCodexRunRequest` requiring a `priorSessionRef` if and only if `mode === "RESUME"` (a `START` request carrying a stale session ref, or a `RESUME` request missing one, both fail closed) and validating `workingDirectoryRef` via the existing, unmodified `isWorkspaceRootAllowed`.
- `CodexUsageLimitWindowKind = "FIVE_HOUR" | "WEEKLY"` + `resolveCodexUsageLimitDisposition`, mapping a caller-reported remaining-fraction onto `"AVAILABLE" | "EXHAUSTED"`, fail-closed on a malformed fraction.
- `CodexRunEventKind` — a closed, honestly-scoped **repository-native projection** (`TASK_STARTED`/`AGENT_MESSAGE`/`APPROVAL_REQUESTED`/`APPROVAL_DECIDED`/`USAGE_REPORTED`/`TASK_COMPLETED`/`TASK_FAILED`/`TASK_CANCELLED`) — this ADR does not claim these are the literal, undisclosed internal JSON-RPC method names of the real App Server protocol, only that they are the structural event categories the sourced documentation confirms exist (task lifecycle, agent output, approval request/response, usage reporting). `mapCodexRunEventKindToBridgeMessageKind` deterministically projects each onto an existing `BridgeProtocolMessageKind` (never a new one), asserted via the existing `isRecognizedBridgeMessageKind`.
- `resolveCodexRunOutcome` binds a terminal `CodexRunEventKind` to the existing `LocalWorkerAdapterOutcome`/`LocalWorkerAdapterResult` shape (never a new result shape), requiring non-empty evidence.
- Checkpoint/evidence return delegates entirely to the existing `createLocalTaskCheckpoint` and adds only the one Codex-specific field a checkpoint needs to be resumable (`codexSessionRef`) as a separate wrapper, never by redefining `LocalTaskCheckpoint` itself.

## Consequences

- No real Codex CLI process, JSON-RPC client, or `~/.codex` filesystem access exists anywhere in this module or its tests — every test uses caller-supplied mock inputs, requiring no Founder machine, no Codex installation, and no credentials.
- If the real App Server's actual event-method names or sandbox/approval enum spellings are later confirmed to differ from this ADR's sourced understanding (e.g. via direct SDK inspection once this repository actually integrates one), only the mapping table and the two enum value sets need correction — the port shape and generic bridge composition are unaffected.
- This ADR does not authorize installing the Codex CLI, invoking it, or storing any real credential anywhere in this repository or its CI — that remains a separate, later, explicitly-gated activation step per Rev99/100's own "physical-PC installation/native provider login/OS permission prompts become just-in-time user actions only when live activation actually reaches them."

## Alternatives considered

- **Model the literal App Server JSON-RPC method/notification names directly.** Rejected: this repository has no access to the actual, possibly-versioned protocol schema (only public documentation/blog prose), and claiming an exact undisclosed wire format would be fabrication, not research. The chosen closed, honestly-labeled projection is corrected later without redesigning the port.
- **A single flat `CodexRunConfig` blob instead of separate sandbox/approval/network enums.** Rejected: the sourced documentation is explicit that sandbox mode and approval policy are independent dimensions (what Codex may touch vs. when it must ask) — collapsing them would lose that distinction and make an over-permissive combination easier to construct by accident.
