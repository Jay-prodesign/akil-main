# 0003 — LOCAL-EXEC-006: Claude Local Adapter dependency-fit and current provider-policy check

Status: Accepted — 2026-09-12

## Context

The architecture packet's §21 names `LOCAL-EXEC-006 / Phase L5` explicitly as "policy-aware": *"current-provider-policy recheck at implementation time; select official Claude Agent SDK or `claude -p` transport; session resume/stream-json/tool permission mapping; same TaskPacket/Event/Checkpoint contract; per-user account isolation; provider usage-limit handling; no credential sharing/pooling. If current Anthropic rules/support change materially, mark the adapter POLICY_BLOCKED and leave the rest of Local Execution functional."* Canonical Handoff Rev103's own "NEXT GRAPH" text is explicit that this recheck must happen "only after fresh official Anthropic support/terms verification, with provider-specific policy blockage isolated to that adapter" — unlike Codex (LOCAL-EXEC-003), this ADR cannot proceed from the packet's own §9 text alone; it requires genuinely current research, dated to today, not fabricated from training-time assumptions about Anthropic's terms.

`LOCAL-EXEC-001` already defines the generic `LocalWorkerAdapter` port and `DeviceCapabilityReadiness` (which already includes a `"POLICY_BLOCKED"` value — this floor's own contract anticipated exactly this case). `LOCAL-EXEC-002` already defines the generic bridge protocol. `LOCAL-EXEC-003`'s `codex-local-adapter.ts` already establishes the exact shape a provider-specific local adapter should take. This ADR's job is the same as ADR-0002's: determine what a Claude-specific implementation actually needs, sourced from current documentation, so LOCAL-EXEC-006 composes the existing ports rather than inventing a fourth system — plus the policy-currency check §21 explicitly requires before implementation.

## Research findings (sourced, dated 2026-09-12)

- **Programmatic invocation is officially supported**: Claude Code's own documentation dedicates a page to running it non-interactively (`-p`/`--print` mode), explicitly recommending it for scripted/SDK-driven automation. This is Anthropic's own product surface for exactly this use case, not a workaround. ([Claude Code headless mode](https://code.claude.com/docs/en/headless.md))
- **Subscription authentication for local automation is supported and billed as before**: Pro/Max/Team/Enterprise subscription logins work with the CLI (`claude login`), and — after a proposed May 2026 change to split programmatic usage into a separate credit pool starting June 15 2026 was announced and then cancelled before taking effect — `claude -p`/Agent SDK usage still draws from the same regular subscription usage limits as interactive use, with no separate billing structure as of today. ([Claude Code authentication](https://code.claude.com/docs/en/authentication.md))
- **Consumer Terms scope (Rev109-corrected sourcing)**: Anthropic's compliance page, clarified 2026-02-20 and covered contemporaneously by [The Register](https://www.theregister.com/software/2026/02/20/anthropic-clarifies-ban-on-third-party-tool-access-to-claude/5014546), states that OAuth tokens obtained through Claude Free/Pro/Max accounts are "only intended for Claude Code and Claude.ai" and that using them "in any other product, tool, or service — including the Agent SDK — is not permitted." Anthropic describes this as clarifying existing policy language present in the Consumer Terms since at least February 2024, not a new restriction, and the restriction is scoped to *reusing subscription OAuth credentials in a different, unauthorized tool* — it does not restrict running the official Claude Code CLI itself, under a real logged-in account, on the user's own machine. This ADR draws only that narrow, sourced conclusion: this repository must invoke the real, official `claude` binary as a subprocess, never re-implement or proxy its authentication, and never extract or persist its session material. No broader legal/terms safe-harbor beyond this specific, cited clarification is inferred here.
- **Session resume / structured output / tool permissions are current and stable**: `--resume <session-id>` (and `--continue` for the most recent session) resume a specific prior thread; `--output-format stream-json` produces streamed structured events suitable for programmatic consumption; tool access is governed by an explicit permission-mode dimension. ([Claude Code headless mode](https://code.claude.com/docs/en/headless.md))
- **Permission modes are a closed, small set, directly confirmed against the official documentation (Rev109-corrected sourcing)**: the prior version of this ADR sourced the six-value set from this environment's own session-creation tool schema rather than the actual official Claude Code CLI documentation — Rev109 correctly found that insufficiently authoritative to model as a "provider-officially documented" contract. Independently re-fetched [Choose a permission mode](https://code.claude.com/docs/en/permission-modes) directly (2026-09-12): the official modes table names exactly six config values — `default` (labeled "Manual" in the CLI/UI, with `manual` accepted as an input alias), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` — matching this module's `ClaudePermissionMode` 1:1. This satisfies Rev109's own stated fallback ("fail closed unless fresh official Claude Code documentation proves them for the invoked client version"): fresh official documentation does prove all six, so none are modeled as experimental/non-portable. One honest caveat carried into the module's own doc comment: `auto` and `dontAsk` availability is plan/version-gated per that same page (e.g. the built-in `auto` default requires Claude Code v2.1.228+, and `auto`/`bypassPermissions` may be unavailable or fall back to `default` depending on plan, settings, and session surface) — this checkpoint does not itself perform any runtime version/plan negotiation, since no real CLI invocation happens here; that remains the caller's responsibility at actual activation time.
- **Usage-limit windows**: Claude Pro/Max plans are documented as resetting on a rolling multi-hour session window, with an additional weekly cap on Max plans — the same dual-window shape Codex uses (a 5-hour rolling window plus a weekly quota), tracked independently per authenticated account.
- **No material policy change since the last check**: the only notable 2026 event (the proposed then-cancelled June 15 billing split) was a billing-structure change, not a new permission or prohibition; there is no current statement newly blocking local, single-machine, officially-authenticated CLI automation.

## Decision

**Provider-policy disposition (Rev110-corrected): `POLICY_REVIEW_REQUIRED`, not an unconditional `POLICY_SAFE`.** The prior version of this ADR concluded `POLICY_SAFE` for local, single-machine, officially-authenticated `claude -p` orchestration. Independently re-verified directly against the official Claude Code Legal and Compliance documentation (`code.claude.com/docs/en/legal-and-compliance`, fetched 2026-09-12): "unless we've mutually agreed otherwise, preinstalling or running Claude Code in your products or services (e.g. in hosted sandboxes or other agent infrastructure) requires agreeing to our Commercial Terms of Service" and complying with conditions (the Claude Code binary must not be modified; customers may not pay for, resell, or intermediate Claude usage on end users' behalf — each end user authenticates with their own credential, billed to them directly). The same page separately states this "does not prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription... including where a platform hosts Claude Code as described under *Can customers offer Claude Code in their products?*."
Whether AKILTA's own Local Execution feature (each staff member's device running the official, unmodified CLI under their own account, orchestrated by internal engineering tooling) falls inside that end-user carve-out, or counts as AKILTA "running Claude Code in your product/service" requiring Anthropic's Commercial Terms, is a business/use-case classification question this ADR cannot resolve from documentation alone — it is not a technical fact and not this checkpoint's call to make. `POLICY_REVIEW_REQUIRED` represents exactly that unresolved state honestly, and is treated identically to `POLICY_BLOCKED` by every fail-closed check in `claude-local-adapter.ts`: an unresolved commercial-terms/use-case question is never silently treated as safe. Resolving it (confirming AKILTA's specific intended use against Anthropic's Commercial/Consumer Terms, or obtaining an explicit mutual agreement) is a separate, later, real Founder/protected-gate decision at actual activation time — not authorized or assumed by this checkpoint, and not evaluated at all for any future distributed/shared-backend use of a subscription session, which remains further out of scope.

`src/domain/claude-local-adapter.ts` models the dimensions above as closed, validated types and pure mapping/validation functions, composing — never redefining — `LOCAL-EXEC-001`'s `DevicePolicy`/`isWorkspaceRootAllowed`/`LocalTaskLease`/`LocalTaskCheckpoint`/`createLocalTaskCheckpoint`/`LocalWorkerAdapterResult`/`LocalWorkerAdapterOutcome`/`DeviceCapabilityReadiness` and `LOCAL-EXEC-002`'s `BridgeProtocolMessageKind`/`isRecognizedBridgeMessageKind`:

- `ClaudeAdapterPolicyDisposition = "POLICY_SAFE" | "POLICY_REVIEW_REQUIRED" | "POLICY_BLOCKED"` + `ClaudeAdapterPolicyCheck` (disposition, timestamp, reason) — the packet's own explicit "represent [policy compatibility] as a capability admission gate" requirement, structurally required by every readiness resolution below rather than left as a comment. `POLICY_REVIEW_REQUIRED` (Rev110) represents the unresolved commercial-terms/use-case classification above and is treated identically to `POLICY_BLOCKED` everywhere.
- `ClaudePermissionMode = "DEFAULT" | "PLAN" | "ACCEPT_EDITS" | "DONT_ASK" | "BYPASS_PERMISSIONS" | "AUTO"` — a direct 1:1 projection of the CLI's own six real permission-mode values, confirmed directly against the official documentation (see Research findings above); `auto`/`dontAsk`/`bypassPermissions` availability is plan/version-gated at actual runtime, which this checkpoint does not itself negotiate since no real CLI invocation happens here.
- `ClaudeAuthReadinessStatus = "READY_SUBSCRIPTION_SESSION" | "READY_API_KEY" | "NOT_AUTHENTICATED"` — a locally-reported status only; no field anywhere in this module can carry a token, cookie, or session-file contents, mirroring `CodexAuthReadinessStatus`'s own structural guarantee.
- `resolveClaudeRunReadiness` fails closed to `NOT_READY` whenever the policy check is not `POLICY_SAFE`, checked strictly before auth readiness — neither a `POLICY_BLOCKED` nor a `POLICY_REVIEW_REQUIRED` disposition can ever be bypassed by an otherwise-valid authenticated session.
- `ClaudeRunMode = "START" | "RESUME"`, with `ClaudeRunRequest`/`createClaudeRunRequest` requiring a `priorSessionRef` if and only if `mode === "RESUME"`, validating `workingDirectoryRef` via the existing, unmodified `isWorkspaceRootAllowed`, and carrying `permissionMode` plus an explicit `allowedToolRefs` list (never an implicit "all tools" default).
- `ClaudeUsageLimitWindowKind = "FIVE_HOUR" | "WEEKLY"` + `resolveClaudeUsageLimitDisposition`, identical fail-closed-on-malformed-fraction shape to Codex's own.
- `ClaudeRunEventKind` — a closed, honestly-scoped repository-native projection (`TASK_STARTED`/`AGENT_MESSAGE`/`TOOL_PERMISSION_REQUESTED`/`TOOL_PERMISSION_DECIDED`/`USAGE_REPORTED`/`TASK_COMPLETED`/`TASK_FAILED`/`TASK_CANCELLED`) of the structural event categories the sourced documentation confirms exist (session lifecycle, assistant output, tool-permission request/decision, usage, terminal states) — not a claim of literal internal stream-json field names. `mapClaudeRunEventKindToBridgeMessageKind` deterministically projects each onto an existing `BridgeProtocolMessageKind`, asserted via the existing `isRecognizedBridgeMessageKind`.
- `resolveClaudeRunOutcome` binds a terminal `ClaudeRunEventKind` to the existing `LocalWorkerAdapterOutcome`/`LocalWorkerAdapterResult` shape.
- Checkpoint/evidence return delegates entirely to the existing `createLocalTaskCheckpoint`, adding only the one Claude-specific field a checkpoint needs to be resumable (`claudeSessionRef`).
- `resolveClaudeAdapterCapabilityReadiness` composes the policy check, auth readiness, and usage-limit disposition into the existing, unmodified `DeviceCapabilityReadiness` value set (`POLICY_BLOCKED`/`AUTH_REQUIRED`/`USAGE_LIMITED`/`AVAILABLE`) — this floor's own L0 contract already reserved exactly this value for exactly this situation.

## Consequences

- No real `claude` CLI process, Agent SDK client, or local session-file access exists anywhere in this module or its tests — every test uses caller-supplied mock inputs, requiring no Founder machine, no Claude Code installation, and no credentials.
- If Anthropic's terms materially change before or at activation time, only `resolveClaudeAdapterPolicyCheck`'s caller-supplied disposition needs to flip to `POLICY_BLOCKED` — every other function already fails closed on that value without code changes, satisfying the packet's own "mark the adapter POLICY_BLOCKED and leave the rest of Local Execution functional."
- This ADR does not authorize installing the Claude Code CLI, invoking it, or storing any real credential anywhere in this repository or its CI — that remains a separate, later, explicitly-gated activation step, exactly as LOCAL-EXEC-003's own ADR established for Codex.
- This ADR's finding (Rev110-corrected to `POLICY_REVIEW_REQUIRED`, not `POLICY_SAFE`) is scoped narrowly to local, single-machine, officially-authenticated CLI automation, and does not resolve — let alone authorize — any future distributed or shared-backend use of a subscription session, which remains further out of scope and would require its own fresh check in addition to the commercial-terms/use-case classification above.

## Alternatives considered

- **Reuse `CodexRunEventKind`/`CodexSandboxMode`-shaped types directly instead of defining Claude-specific ones.** Rejected: those types are explicitly named and documented as Codex-specific projections in a sibling module this checkpoint must not modify; Claude's own real dimensions (permission modes vs. Codex's sandbox+approval split) are not identical, so a shared type would either misrepresent Claude's actual controls or force an inaccurate re-labeling of Codex's.
- **Skip the explicit policy-check gate and just document current safety in this ADR's prose.** Rejected: the packet explicitly requires policy compatibility be "represented as a capability admission gate," not merely documented — a structural, fail-closed gate survives a later policy change without requiring every caller to remember to re-check prose.
