## Goal

Represent organization membership, role, and a generic ownership-assignment *reference* — the V3 Workstream A "foundation" only — without collapsing identity, tenant, customer, or action authority into one concept, and without granting any of those roles actual permission/protected-action authority.

## Scope (this checkpoint — foundation only)

- `OrganizationRole` (`STAFF | JUNIOR | STUDENT | CLIENT_ASSOCIATE`) + `OrganizationMembership` + `createOrganizationMembership` (`src/domain/organization-membership.ts`).
- `AssignmentReference` + `createAssignmentReference` — a generic member → customer/project assignment reference (not yet LeadOwner/DealOwner/AccountOwner/DeliveryOwner distinction; that is Workstream B, explicitly out of scope here).
- `AssignmentStatus` (`ASSIGNED | UNASSIGNED | NOT_APPLICABLE | UNAVAILABLE | UNKNOWN`) + `resolveAssignmentStatus` — fail-closed resolution, including a cross-tenant membership-id-collision adversarial case.

## Architecture / semantic invariants

- Identity/Principal, organization membership, role, ownership assignment, and action authority remain distinct types with no field crossover: `OrganizationMembership` has no `permissions`/`canPerformProtectedActions` field, and `organization-membership.ts` imports nothing from `authority.ts` — a role can never itself grant `READ`/`WRITE`/`EXECUTE` or protected-action authority (verified by boundary-scan import check and a functional test asserting no `AuthorityContext`-shaped export/field exists).
- `principalRef` reuses the string identity of the existing V2-APP-001 `AuthenticatedPrincipal.principalId` **by shape, not by import** — `src/domain/` depends on nothing else in `src/` (see `docs/architecture/DEPENDENCY_MAP.md`), so a web-layer type cannot be imported into a domain module. A caller in `src/web/`/`src/application/` passes `session.principal.principalId` directly at the call site; no adapter is needed since a branded string is a structural subtype of `string`. This dependency choice is disclosed here per the blueprint's own "dependency delta and exact reused V2 types are disclosed" acceptance direction.
- An `AssignmentReference`'s `tenantId` is always derived from its own `membership` argument, never a separately supplied value — an assignment cannot be constructed against a tenant its own membership does not belong to.
- `resolveAssignmentStatus` is pure and fail-closed: a same-`membershipId`-different-tenant collision (adversarial membership-id reuse across tenants) resolves `UNAVAILABLE`, never `ASSIGNED` — this is the concrete "no cross-tenant membership leakage" proof.
- `NOT_APPLICABLE`/`UNKNOWN` are declared on `AssignmentStatus` but not produced by this bounded foundation slice (reserved for a future caller context that genuinely cannot resolve an answer) — same "declared, not yet producible" discipline already established by `NextActionOwner.EXTERNAL_WAIT` in `client-project-snapshot.ts`; not an oversight.
- No `LeadOwner`/`DealOwner`/`AccountOwner`/`DeliveryOwner`, SLA/escalation, commission/pricing, or frontend concept is introduced — those are Workstreams B through G, explicitly out of scope here.
