## Scope (this checkpoint)

`src/domain/local-execution-hardening.ts` implements the three L6-named dimensions that are honestly buildable as domain contracts today, composing L0's (`local-execution.ts`) unmodified `ExecutionMode`/`ExecutionPolicy`/`DeviceRegistration`/`DeviceCapabilitySnapshot`/`DeviceCapabilityReadiness`/`LocalWorkerRegistration`/`resolveEligibleLocalWorkers` and mirroring `local-execution-collaboration.ts`'s own `planCollaborationModeTransition` preflight shape:

- **Kill switch** (§19: "Settings -> Devices & Local Workers ... revoke/quarantine/kill switch"): `LocalExecutionKillSwitch`/`createLocalExecutionKillSwitch`/`engageLocalExecutionKillSwitch`/`disengageLocalExecutionKillSwitch` — a tenant/project-level circuit breaker, distinct from L0's own per-device `DevicePolicy.killSwitchEngaged` (which only ever gates one device's own `isWorkspaceRootAllowed` check). `resolveEligibleLocalWorkersUnderKillSwitch` is the one required composition point: it checks `engaged` first and short-circuits to `[]`, otherwise delegates entirely to the existing, unmodified `resolveEligibleLocalWorkers` — no second routing engine.
- **Safe switch/migration preflight**: `planExecutionModeTransition` mirrors `planCollaborationModeTransition`'s exact shape for the `ExecutionMode` dimension. Rank reflects local-worker routing-eligibility breadth exactly as `resolveEligibleLocalWorkers` itself implements it (`CLOUD_NORMAL` < `PERSONAL_LOCAL` < `{TEAM_LOCAL, HYBRID}`, the latter two sharing a rank since `resolveEligibleLocalWorkers`'s own filter treats them identically). `TEAM_LOCAL <-> HYBRID` is its own `"LATERAL"` direction (same local-worker eligibility, but not `"UNCHANGED"` since they are genuinely different mode values) — honestly disclosing that whether normal remote/API workers also coexist in the candidate pool (`HYBRID`'s own distinguishing behavior) is a caller-side decision this module does not observe or govern, matching `resolveEligibleLocalWorkers`'s own documented honest limit. §3's "Local Mode must never automatically enable Team Pool or Shared Repo" is enforced structurally: `ExecutionModeTransitionPlan` carries no `collaborationMode` field at all, so it cannot alter that dimension even by construction.
- **Capability/health telemetry** (§18's own named fields): `resolveLocalDeviceHeartbeatFreshness` (computed, never stored, relative to a caller-supplied `asOf`, mirroring `observability-telemetry.ts`'s own `resolveMetricFreshness` discipline exactly — L0 has no `lastSeenAt`/heartbeat field on `DeviceRegistration`, so a heartbeat timestamp is always caller-supplied here, never read off the device) and `projectLocalWorkerHealth`, which surfaces `deviceStatus`/`workerAvailability`/`capabilityReadiness`/heartbeat freshness as their own real, honestly-optional fields rather than collapsing them into one fabricated composite status — an absent snapshot or heartbeat is never silently rendered as a positive `AVAILABLE`/`FRESH` result. Fails closed on any structural cross-reference mismatch (worker/snapshot must actually belong to the given device/tenant).

- ExecutionMode preflight: every widening/narrowing/lateral/unchanged direction is correctly classified across all four `ExecutionMode` values (M1-M7); an unrecognized mode value fails closed (M8); every disclosure states CollaborationMode is never altered, and the return type itself carries no such field (M9).
- Health read-model: full caller-supplied data (device, snapshot, fresh heartbeat) surfaces every dimension honestly (H1); absent snapshot/heartbeat yields only the always-present base fields, nothing fabricated (H2); a stale heartbeat is reported as `STALE`, never silently treated as fresh (H3); a worker/device deviceId mismatch (H4), a worker/device tenantId mismatch (H5), and a snapshot/device deviceId mismatch (H6) all fail closed before any projection is built; `resolveLocalDeviceHeartbeatFreshness` rejects an `asOf` before `lastHeartbeatAt` (H7, time-travel guard) and a non-positive `maxAgeMs` (H8).

## Independent-review correction (post-checkpoint, same PR)

- **Trigger**: per Handoff Rev105's own endorsed principle ("LOW/MEDIUM-risk exact heads may reach VERIFIED through independent exact-head review by a verifier distinct from the implementing execution context"), the `code-review` skill was run against this checkpoint's own just-shipped diff as a genuinely independent check, rather than relying on self-review alone.
- **Finding (confirmed, live-reproduced)**: `planExecutionModeTransition`'s fail-closed validation was bypassable. The original code indexed the plain object literal `EXECUTION_MODE_RANK` directly with the caller-supplied `unknown` value (`EXECUTION_MODE_RANK[input.from as ExecutionMode]`) and treated `=== undefined` as the sole recognized/unrecognized signal. Because plain-object bracket indexing in JavaScript walks the prototype chain, an unrecognized-but-`Object.prototype`-shaped key (e.g. `"constructor"`, `"toString"`, `"hasOwnProperty"`, `"valueOf"`, `"isPrototypeOf"`) resolves to an inherited function value instead of `undefined`, defeating the fail-closed check entirely. Live-reproduced: `planExecutionModeTransition({ from: "constructor", to: "toString" })` returned a fabricated `WIDENING` plan instead of throwing `InvalidExecutionModeTransitionError`.
- **Precedent**: this is the identical bug class this same codebase already found and fixed once before, in `worker-routing-policy.ts`'s `AUTHORITY_RANK` lookup (documented there as "Rev60 F1", fixed via `isRecognizedAuthorityLevel`) — that fix was never generalized or re-scanned for elsewhere, so this checkpoint's brand-new code reintroduced the same shape.
- **Fix**: added `RECOGNIZED_EXECUTION_MODES` (a `ReadonlySet<string>`) and `isRecognizedExecutionMode(value): value is ExecutionMode`, which performs an explicit `Set.has()` equality-based membership check — a check that can never resolve through the prototype chain, unlike object-key indexing. `planExecutionModeTransition` now calls this guard on both `from` and `to` and throws before the `EXECUTION_MODE_RANK` table is ever indexed, rather than indexing first and checking the result for `undefined` after.
- **New coverage**: `tests/local-exec-007-hybrid-hardening.test.ts` gained adversarial test `M8b`, explicitly probing `"constructor"`, `"toString"`, `"hasOwnProperty"`, `"valueOf"`, `"isPrototypeOf"`, `"__proto__"` as both `from` and `to`. `tests/local-exec-007-boundary-scan.test.ts` gained a structural test asserting `isRecognizedExecutionMode` runs (and uses `RECOGNIZED_EXECUTION_MODES.has(`, not raw object-key existence) strictly before `EXECUTION_MODE_RANK` is indexed.
- **Sanity-check**: reverted the fix back to the vulnerable direct-indexing form, rebuilt, and reran full regression — result was exactly **1517 pass / 2 fail**, with the 2 failures being precisely the new boundary-scan structural test and the new `M8b` adversarial test, no others. Restored the fix and reconfirmed **1519/1519 pass** (1517 + 2 new tests as part of the fix itself).
- **Evidence (updated)**: `npm run test`: **1519/1519 pass** (1517 from the original checkpoint + this correction's own 2 new tests: `M8b` and the boundary-scan structural check).
