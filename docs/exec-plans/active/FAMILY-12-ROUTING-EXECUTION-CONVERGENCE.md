## Part 2 — admitted-routing ↔ authorized-execution glue

- **The gap, precisely**: `worker-routing-policy.ts`'s `resolveWorkerRoute` produces a `WorkerRoutingDecision` naming an `executorWorkerId` for an abstract `requiredCapabilityRef` — it carries no `OutcomeJob` identity at all. `outcome-job.ts`'s own `MAIN_PATH_TRANSITIONS` lets any caller move a `READY` job straight to `EXECUTING` via the generic `transitionOutcomeJob`/`authorizedTransitionOutcomeJob`, with no routing decision required or even representable at that call site. A job can begin executing without ever having gone through admitted routing, and a routing decision has nothing binding it to the specific job it was meant to authorize.
- **New module**: `src/domain/outcome-job-routing-execution.ts` — `RoutedExecutionAssignment` (mirrors `outcome-job-closure-approval.ts`'s own `ClosureApprovalReference` tenant/scope-binding discipline, Rev62 AUD-V2-01, but binds a `ROUTED` `WorkerRoutingDecision` to job identity instead of an approval); `createRoutedExecutionAssignment` (fails closed on any `decision.status !== "ROUTED"` — a `REJECTED` route can never authorize execution); `isRoutedExecutionAssignmentValidForJob` (fail-closed scope check, identical shape to `isClosureApprovalValidForJob`); `authorizeOutcomeJobExecutionFromRouting` (throws `OutcomeJobExecutionNotRoutedError` unless a valid, matching assignment is supplied, then delegates the actual transition entirely to the existing, unmodified `transitionOutcomeJob`).
- **Application-boundary wrapper**: `src/application/authorized-outcome-job-operations.ts` gains `authorizedTransitionOutcomeJobToExecutingViaRouting(authority, job, assignment)` — same tenant match and WRITE permission as the existing `authorizedTransitionOutcomeJob`, plus the routing-assignment gate.
- **Deliberately not done — and why**: unlike the Family-12 closure-approval-gate correction (which narrowed `authorizedTransitionOutcomeJob` to reject `"CLOSED"` outright), this checkpoint does **not** narrow `authorizedTransitionOutcomeJob` to reject `"EXECUTING"`. That closure-gate narrowing was justified by a real, empirically-demonstrated bypass with zero legitimate existing callers of the ordinary path for that exact transition. No equivalent finding exists for `EXECUTING` — `authorizedTransitionOutcomeJob(..., "EXECUTING")` is exercised throughout this repository's own existing, already Brain-reviewed test suites (every `jobAtVerifying`-style helper) as ordinary, non-routed staff-initiated work. Retroactively closing that path here would be an unreviewed, overreaching behavior change to already-verified callers, not a bounded addition. This checkpoint instead adds the missing glue as a real, usable, purely-additive composition — exactly matching Rev98 Family 12's own text, "reusing existing segments and adding only missing glue/tests," not a rewrite.
- **Explicitly deferred, not fabricated**: `PartnerRoutingDecision` (`partner-routing-decision.ts`) is a distinct, separately-scoped routing concept (external partner-organization assignment via `targetOwnership`/`decidedByOwnerId`, not `AdmittedWorker` selection) with no job-execution semantics to bind — inventing a shared binding would conflate two real, distinct domain concepts rather than closing a genuine gap, so it is out of scope here.
- `tests/outcome-job-routing-execution.test.ts` (11 tests: R1–R11), `tests/outcome-job-routing-execution-boundary-scan.test.ts` (6 tests), and 5 new tests in `tests/authorized-outcome-job-operations.test.ts` covering the application-boundary wrapper (WRITE+valid-assignment succeeds; READ-only fails closed; no-assignment fails closed; wrong-job assignment fails closed; cross-tenant fails closed).

## Architecture / semantic invariants (verified by test)

- `createRoutedExecutionAssignment` binds every scoping field from the supplied job and decision, never caller-typed input (R1); fails closed on a `REJECTED` decision (R2); fails closed on empty/whitespace `boundAt` (R3); correctly carries or omits `reviewerWorkerId` matching the underlying decision (R4).
- `isRoutedExecutionAssignmentValidForJob` is true only for the exact job an assignment was created for (R5); false for a different `jobId` even in the same tenant/customer/project (R6); false across a cross-tenant substitution even when the `jobId` string happens to collide (R7).
- `authorizeOutcomeJobExecutionFromRouting` transitions `READY` → `EXECUTING` given a valid, matching assignment (R8); throws `OutcomeJobExecutionNotRoutedError` when no assignment is supplied — a `READY` job is never moved to `EXECUTING` "by default" through this function (R9); throws when the assignment belongs to a different job (R10); throws when the job is not yet `READY` even with a well-formed matching assignment, since it still delegates to `transitionOutcomeJob`'s own unmodified state-machine check (R11).
- Boundary-scan confirms structurally: never redefines `OutcomeJob`/`OutcomeJobState`/`WorkerRoutingDecision`; imports `transitionOutcomeJob` from the unmodified module; the assignment check runs strictly before the transition call; `outcome-job.ts`'s own `MAIN_PATH_TRANSITIONS` still contains the untouched `READY -> EXECUTING` edge; `createRoutedExecutionAssignment` rejects any non-`ROUTED` status before binding any field; module exports exactly the expected surface.
- Application-boundary tests confirm: WRITE authority with a valid assignment succeeds; READ-only authority is rejected (`InsufficientAuthorityError`); WRITE authority with no assignment or a wrong-job assignment is rejected (`OutcomeJobExecutionNotRoutedError`); cross-tenant authority is rejected (`CrossTenantAuthorityError`) even with an otherwise-valid assignment.
