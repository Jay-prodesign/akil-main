## Resource binding rule (packet's own text)

A binding points to an authoritative resource owner; it never duplicates credentials, raw secrets, provider session/cookies, repository contents, provider-thread memory, or customer data. Every bound resource is an opaque, already-validated id (`OrganizationMembership["membershipId"]`, `OrganizationServicePrincipal["servicePrincipalId"]`, `Project["projectId"]`, `ProjectOwnershipRef`, `ConnectionBinding["connectionBindingId"]`, opaque config/policy/route/knowledge-evidence ref strings) — never the resource's own mutable state copied into the binding. `ConnectionBinding["secretRef"]` (already itself only an opaque `SecretRefId`, never raw credential material) is never read or stored by this module at all — the binding stores only the `connectionBindingId`, and a caller who needs the connection's own current `secretRef`/state re-resolves it from `connection-authority.ts` directly.

## Design: deterministic bootstrap + pure current-status resolution (not a frozen cached verdict)

Mirroring `ProjectActivationProfile`'s own "pure, always re-resolved from current inputs, never cached" discipline and `resolveEffectiveOrganizationAccess`'s "re-invoking is the only way to get a current answer" discipline: the DURABLE record is only the immutable set of resource refs a caller bound at bootstrap time (`OrganizationResourceBinding`, put-once via `putIfAbsent`). The READY/ACTION_REQUIRED/BLOCKED verdict is NEVER itself durably frozen — `resolveOrganizationResourceBindingStatus` is a pure function taking the durable binding plus freshly-supplied CURRENT evidence (the current `Organization`, current memberships, current service principals, current connections) and computing the current truth. This is what makes "stale/revoked membership/policy/connection/worker blocks downstream use WITHOUT deleting historical binding evidence" possible: the historical ref list never changes, but re-resolving it against now-revoked evidence correctly reports `BLOCKED`/`ACTION_REQUIRED` — exactly the same mechanism `resolveEffectiveOrganizationAccess` already uses to observe a membership revocation without deleting the `OrganizationMembership` record itself.
