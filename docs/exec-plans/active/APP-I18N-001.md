## Scope

Base: PR #90 exact head `f74e2890283d7db49cd80023e35fd795b642ff14`. Branch `claude/app-i18n-001-tr-en-portal-localization`, draft-targeting `claude/rev53-implementation-completion-closure-audit`. Risk: MEDIUM, confined to presentation/locale resolution. Founder gate: NONE.

Supported operator locales are `tr` (Türkiye-launch primary/default) and `en` (independently adapted secondary). Three new modules:

- `src/web/locale.ts` — the closed `Locale = "tr" | "en"` type, `DEFAULT_LOCALE = "tr"`, `isRecognizedLocale` (a `Set.has()`-based guard, never a bracket-indexed lookup — mirrors this codebase's own established `isRecognizedAuthorityLevel`/`isRecognizedExecutionMode` discipline against the prototype-pollution bug class this session already found and fixed three times elsewhere), and `resolveRequestLocale` (deterministic `Accept-Language` parsing with an explicit Turkish-primary fallback on a missing/empty/malformed/wholly-unsupported header value — never an ambient system locale, never an exception).
- `src/web/shell-copy.ts` — the one centralized, typed fixed-copy catalog (`ShellCopy`) the entire shell renders through, with a complete `en` and `tr` translation. Dynamic/customer-supplied domain data (a snapshot's raw status enum, an `UNAVAILABLE`/`ERROR` free-text `reason`, customer/project identifiers, timestamps) is deliberately out of scope — it is domain data, not fixed shell copy.
- `src/web/shell-render.ts` (modified) — `renderShellPage(content, locale: Locale = "en")` threads `locale`/its resolved `ShellCopy` through every render function; `<html lang="${locale}">` now reflects the effective locale exactly. The `locale` parameter defaults to `"en"` — the exact pre-localization behavior — solely so every pre-existing caller/test that does not pass a locale is entirely unaffected; the live system's actual default is Turkish, established explicitly in `request-handler.ts`, not by this default.
- `src/web/request-handler.ts` (modified) — resolves `locale` once per request via `resolveRequestLocale(request.headers)` and passes it explicitly to every `renderShellPage` call site, so a real request with no `Accept-Language` header renders the Turkish shell by default.

No existing tenant/customer/project/resource identity, authorization, route, or state semantics were touched — `route-guard.ts`, `session-context.ts`, `snapshot-view-state.ts`, and `team-attention-view-state.ts` are untouched; the locale resolution happens entirely independently of, and before, any authorization check runs, and never influences its outcome (proven by I22/I23 below).
