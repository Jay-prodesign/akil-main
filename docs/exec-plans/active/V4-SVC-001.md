## Goal

Resolve a customer/service need to a currently admitted capability's execution maturity without ever making provider/connection presence equal permission, and without inventing an adapter capability this repository does not yet have.

## Scope (this checkpoint — routing floor only)

- `ExecutionMaturity` (ten literals declared; only `UNAVAILABLE`/`READ_ONLY` producible) + `ServiceCapabilityRoute` + `resolveServiceCapabilityRoute` (`src/domain/service-capability-routing.ts`) — pure function composing an existing `ProjectOwnershipRef` and `CapabilityAdmission` (V2-CDO-004) into a deterministic route.
- One canonical `WEBSITE_BUILD_v1` fixture (`src/fixtures/website-build-v1-service-route.ts`) reusing the existing ownership and capability-admission fixtures verbatim.

## Explicitly deferred (not invented)

Of §5's seven distinct dimensions ("service/customer outcome, required capability, admitted capability, provider support, entitlement, delegated authority and execution maturity"), this checkpoint represents only **required capability** (reused from `CapabilityAdmission`) and **execution maturity** (capped at the honest floor). **Provider support**, **entitlement**, and **delegated authority** are not modeled — no canonical source in this repository specifies how they compose with capability admission, and inventing that composition would be fabricating policy. `MANUAL`/`PROVIDER_NATIVE`/`ENGINEER_ASSISTED`/`DIAGNOSE`/`RECOMMEND`/`DRAFT_PREVIEW`/`APPROVAL_REQUIRED`/`CONTROLLED_APPLY` are declared on `ExecutionMaturity` but not producible until real adapters (V4 §7 Workstream C) exist. Staleness detection ("stale admission state cannot appear as current executable support") is not implemented — `CapabilityAdmission` carries no timestamp field in this repository, so there is no data to detect staleness from; this is a disclosed gap for a future slice, not a silent omission.

## Architecture / semantic invariants

- `resolveServiceCapabilityRoute` imports only **types** from `capability-admission.ts` — no create/promote function — so this module structurally cannot mutate or promote a `CapabilityAdmission`.
- The given `admission`'s ownership tuple must exactly match the given `ownership` scope, or construction throws `InvalidServiceCapabilityRouteError` — fail-closed cross-tenant/cross-project substitution, same pattern as every other slice this checkpoint train.
- `UNVERIFIED`/`UNSUPPORTED`/`INELIGIBLE` all resolve `UNAVAILABLE` — never executable, regardless of any other input.
- `VERIFIED_AVAILABLE` resolves exactly `READ_ONLY`, never a higher rung — verified statically by a boundary-scan test that greps every `executionMaturity: "..."` assignment in source and asserts each is `UNAVAILABLE` or `READ_ONLY`.
- `reason` always cites the exact admission status the decision was made from (provenance, §5).
- No import of `authority.ts`, `outcome-job.ts`, or any `connection-authority.ts` mutation function, and nothing from `src/web/`/`src/application/`.

## Hard Non-Scope

No real provider/connection adapter (read, diagnose, recommend, draft-preview, apply); no provider SDK/OAuth/credential; no entitlement or delegated-authority model; no `DIAGNOSE`/`RECOMMEND`/`DRAFT_PREVIEW`/`APPROVAL_REQUIRED`/`CONTROLLED_APPLY` production; no persistence/database; no HTTP/UI surface; no AI Commerce mutation; no merge/deploy/release/production/publication/customer-binding/legal/financial action anywhere in this checkpoint's source.
