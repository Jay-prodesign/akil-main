## Real gap (what this task actually builds)

Three small, additive modules — no fork of any existing owner:

1. **`src/domain/outcome-job-golden-path-composition.ts`** (pure, closes Live Gap A1/A2): `composeTaskPacketForOutcomeJob` deterministically derives a real `TaskPacket` from an exact `OutcomeJob` + its `OutcomeJobSpec` + current `ProjectActivationProfile` + (if routing-required) its `RoutedExecutionAssignment`/`ExecutionRoutingRequirement` + current `OutcomeJobExecutionRunState` (if any) + evidence/blocker refs — closing Gap A1 ("no load-bearing OutcomeJob→TaskPacket composer"). `resolveNextRunnableGoldenPathAction` is a pure, always-re-resolved function examining current `ProjectActivationProfile` blockers, `OutcomeJob` state, `OutcomeJobExecutionRunState` attempt status, and an optional `VerificationResult`, returning one exact next actor/action — closing Gap A2 ("no one-lineage execution→verification→continuation proof") by giving Golden A's integration test one real, restart-safe function to assert against at every stage of the lineage rather than ad hoc per-caller logic.
2. **`src/domain/protected-decision-wait-gate.ts`** + **`src/domain/durable-protected-decision-wait-store.ts`** (the benchmark-audit amendment): a `ProtectedDecisionWaitRequest` durably binds one specific protected decision to an exact tenant/job/run/attempt + effect ref (mirroring `ApprovalReference`'s own exact-identity-binding discipline). `resolveProtectedDecisionWaitRequest` requires a granted, protected-action-authorized `AuthorityContext` plus a currentness recheck (the caller's freshly-resolved current activation fingerprint must match the one recorded at WAIT time) before producing a single-use `ProtectedDecisionResumeAuthorization` — the durable store's `putIfAbsent`-only resume-claim (a direct structural clone of `FileDurableExternalSaleBootstrapStore`'s atomic-`linkSync` pattern, same as OS-V0-09's own resource-binding store) makes a second resume attempt for the same wait request a safe, authority-free no-op rather than a double-effect.
3. **`src/domain/connector-capability-verified-effect.ts`** (closes Live Gap C1): `executeConnectorCapabilityAsVerifiedEffect` composes `createExternalEffectIntent` + `startExternalEffectAttempt` + the existing, unmodified `executeConnectorCapability` + `reportExternalEffectOutcome` + a caller-injected readback callback + `verifyExternalEffectReadback`. Transport `SUCCESS` from `executeConnectorCapability` is reported as `APPLIED`, never directly as verified effect; only the caller's own independent readback can move the attempt to `VERIFIED` (readback disagreement corrects it to `FAILED`). An exception thrown by `executeConnectorCapability` that is not a recognized authorization/transport-error class (an ambiguous transport failure) is reported as `UNKNOWN`, never silently retried.

Deliberately NOT built: a new TaskPacket/handoff type (reuses `local-execution-collaboration.ts` verbatim), a second workflow/state engine for "next action" (the resolver is a pure projection over existing blocker/attempt/verification vocabulary, exactly like `ProjectActivationProfile` itself), a generic approvals product or sandbox platform (the WAIT gate binds one exact effect/decision, nothing generic), and any real HTTP/OAuth/provider transport (Golden C's `executeConnectorCapability` call remains injected/mock exactly as OS-V0-06 established — real credential activation remains a separately-gated protected effect).
