## Goal

A thin, deterministic, event-sourced orchestration layer that gives `organization.ts` the durable, replay-safe provisioning/reinitialize/suspend/reactivate owner it explicitly left to V1 — without inventing a second IAM/workflow/provisioning framework. "Switching" between two controlled Organizations is not a new runtime concept: it falls out of per-(tenantId, organizationId) ledger scoping, mirrored directly from `durable-quota-reservation-store.ts`'s own per-scope file pattern.

## Design decisions and why

- **Provisioning identity**: `organizationId` (scoped per tenant) is the canonical dedup key — mirrors `deriveCanonicalSaleId`'s role in the sale-bootstrap precedent. `provisionControlledOrganization` only succeeds for an organizationId with NO prior ledger history; re-provisioning an existing organizationId under a different idempotencyKey is rejected with an explicit instruction to use `reinitializeControlledOrganization` instead, keeping "first provision" and "re-provision" unambiguous.
- **All rejections throw, none are durable "REJECTED" events**: mirrors `FileDurableExternalSaleBootstrapStore.putIfAbsent`'s own convention (conflicting replay throws, nothing is persisted) rather than `execution-quota-admission.ts`'s REJECTED-event convention (reserved there for legitimate business-level inadmissibility like quota exhaustion, not caller usage errors). A conflicting idempotencyKey replay or an invalid-state transition attempt is a usage error, not a business fact worth permanent evidence.
- **Reactivation touches ONLY the `Organization` value** — `reactivateControlledOrganization` never reads or re-issues `founderMembership`/`founderAccessRoleContext` at all. This is the direct mechanism behind "reactivation without stale membership/connection/config/session resurrection": there is structurally nothing here that COULD resurrect a membership, because membership currentness remains entirely `organization-membership.ts`'s own separate, always-fresh-re-derived concern.
- **Reinitialize requires the current organization to be `ACTIVE`**, and explicitly `revokeOrganizationMembership`'s the prior founder (carried as `supersededFounderMembership` evidence, never silently dropped) before minting a genuinely new membership + access-role context. Requiring `ACTIVE` is this task's own direct "suspend blocking new effects" witness: suspension blocks this provisioning-layer effect exactly as `resolveOrganizationResourceBindingStatus` already blocks resource-binding readiness while suspended.
- **A↔B switch isolation is structural, not a new abstraction**: the durable store scopes one physical ledger file per (tenantId, organizationId) pair. Two different Organizations under the same tenant are two different files — there is no shared mutable cache or "current context" singleton anywhere for one Organization's state to leak into another's, even under deliberately adversarial idempotencyKey reuse across the two (proven in W6).
