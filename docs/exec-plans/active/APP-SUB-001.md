## Same-PR extension: `changeSubscriptionPlan` (upgrade/downgrade floor)

- The OS blueprint's own V2 bullet text names "upgrade/downgrade/suspend/cancel flows." `suspend`/`cancel` already existed in the ported module (`PAUSED`/`CANCELED`). A plan change (switching a `Subscription`'s bound `SubscriptionPlan`) did not — `subscriptionPlanId` is fixed at construction and never mutated by the fact-fold reducer.
- Added `changeSubscriptionPlan`, consistent with this repository's established "new record, provenance-preserving, never silent mutation" discipline (`ownership-assignment.ts`'s `reassignOwnership`, `partner-capability-admission.ts`'s revoke-is-terminal): it supersedes the current subscription (new terminal `SubscriptionStatus: "SUPERSEDED"`, reached via a new `"PLAN_CHANGE_SUPERSEDED"` lifecycle fact type, only from `ACTIVE`/`PAST_DUE`/`PAUSED`) and constructs a brand-new `Subscription` bound to the target plan, linked back via a new `supersedesSubscriptionId` field (forward provenance only, `undefined` on every ordinarily-created subscription).
- Deliberately **not** labeled "upgrade" or "downgrade": `SubscriptionPlan` carries no price/tier/rank field anywhere in this repository, so classifying a change's direction would require fabricating a pricing hierarchy that does not exist — exactly the invented business scope REV215 forbids. The function only proves the change is scope-safe (same tenant/customer/storefront, genuinely different plan, current subscription in a changeable state, new id distinct from the old) and replay-safe; a caller with its own external pricing source may label the change itself.
- Explicitly deferred: no numeric usage/credit/allowance ledger. The OS blueprint's "usage/quota/credit" wording was considered and rejected as a reuse target for `execution-quota-admission.ts` (that module governs internal execution/worker cost, a different domain — conflating it with customer-facing commercial usage would repeat the exact mistake `SubscriptionPlan`/`ProjectPlanVersion` already deliberately avoid). No real metering/usage-event source exists anywhere in this repository yet, so no credit-balance type is introduced — mirroring `V3-COM-001`'s own `CommissionLedgerStatus: "UNKNOWN"` restraint rather than fabricating one.
- 7 new adversarial tests (S30–S36): successful change (provenance + entitlement correctness on both sides), wrong-customer-linkage rejection, cross-storefront target-mapping rejection, same-plan rejection, `PENDING_ACTIVATION`-cannot-change rejection, terminal-`CANCELED`-cannot-change rejection (no resurrection via plan change), and new-id-collision rejection. `tests/app-sub-001-boundary-scan.test.ts` B6's expected export list updated (`SubscriptionPlanChangeError`, `changeSubscriptionPlan`); B1–B5/B7/B8 unaffected and re-confirmed passing.

## Architecture / semantic invariants (verified by test)

- An external platform's own roles/permissions cannot reach, create, widen, or mutate AKILTA `OrganizationRole`/membership/READ/WRITE/EXECUTE/protected-action authority through this module — structurally (zero import of `authority.ts`/`organization-membership.ts`), not by convention (B1–B4).
- A `SubscriptionPlan`-mapping admission requires a real `AdmittedWorker` that is both `trustStatus: "ADMITTED"` and `authorityLevel: "ELEVATED"` — a merely-available or merely-admitted-but-`STANDARD`-authority worker cannot admit a mapping (S7b/S7c).
- A `SubscriptionLifecycleFact` is rejected unless its full five-field lineage (`subscriptionId`/`tenantId`/`customerId`/`storefrontRef`/`externalSubscriptionContractRef`) exactly matches the target subscription — a fact genuinely constructed for one subscription can never be misapplied to a different one, even when only one of the five fields is tampered (S23–S25, S28–S29).
- Out-of-order fact delivery can never produce an incorrect terminal state: replaying facts in a different arrival order than their true `occurredAt` always re-folds to the same result as the correct order (S26–S27).
- `deriveEntitlement` throws rather than silently deriving when `plan` does not exactly match the subscription's own bound `tenantId`/`subscriptionPlanId` (S21–S22).
- Historical sanity-check disclosure (from the original Rev60/Rev61 corrected commits, re-confirmed applicable to this unmodified port): each of the guards above was independently verified load-bearing by temporary removal, confirming only its own named test(s) failed, then restored with the full suite reconfirmed green. This is disclosed as a limitation of this specific session's re-verification, not evidence the guards are untested; the original historical disclosure (quoted in PR #93's own commit messages) remains the record of record.
