## Design decisions and why

- **The snapshot carries ONLY the `Organization` value's own public lifecycle fields** (`state`/`createdAt`/`activatedAt`/`suspendedAt`/`offboardedAt`/`displayName`) plus export provenance — never a membership, connection, config, or resource-binding object. This mirrors `controlled-organization-provisioning.ts`'s own Rev203 F3 discipline exactly ("the snapshot now stores ONLY the opaque refs... there is structurally nothing left to expose as stale"). "Export is scope-limited" is therefore true by construction, not by a separate filtering step that could be forgotten.
- **Export requires the caller's own current access to be GRANTED** — an export is itself a read of organization state, gated the same way every other internal OS view already is (`requireInternalOsAccess`'s own precedent).
- **Restore/migration is deterministic reconstruction, not blind deserialization**: it REPLAYS the same already-accepted `createOrganization`→`activateOrganization`→`suspendOrganization` transition functions with the snapshot's own historical timestamps, verbatim. This closes "restart/replay is idempotent" for free (pure function, identical inputs → deep-equal output) and "partial restore" correctly (a snapshot with no `activatedAt` restores to `BOOTSTRAPPING` only — nothing is fabricated beyond what the snapshot actually recorded).
- **The load-bearing fix for "restore cannot resurrect revoked access"**: `restoreOrganizationLifecycleFromSnapshot` does not and cannot re-derive the caller's own current standing itself (it has no membership/store dependency) — the CALLER must supply a freshly re-resolved `currentAccess` (`EffectiveAccessResolution`), exactly like every other "re-resolve fresh immediately before granting" primitive in this repository (`requireInternalOsAccess`, `authorizeProtectedDecisionResume`, `resolveControlledOrganizationSwitch`, OS-V1-02's own `resolveEffectiveDelegatedAccess`). A caller whose own membership was revoked since they last had access is denied regardless of what the snapshot itself says (R4). `canPerformProtectedActions` is independently required too (R5) — restore/migration is a protected action, not an ordinary read.
- **"Foreign export/restore" fails closed via a strict tenant equality, not a richer cross-tenant transplant**: `currentAccess.tenantId`, `targetTenantScope.tenantId`, and `snapshot.tenantId` must all exactly match. Restore/migration never crosses a tenant boundary in this bounded slice — a deliberately simpler, safer invariant than inventing cross-tenant membership/resource transplantation semantics, which REV209's own text does not ask for.
- **"Deleted-data reappearance" is structurally impossible, not merely checked**: `restoreOrganizationLifecycleFromSnapshot` throws immediately on `snapshot.state === "OFFBOARDED"`, before any reconstruction branch runs — there is no code path in this function that can ever produce an `OFFBOARDED`-state result (R7).
- **"Migration preserves provenance"**: when `targetOrganizationId` differs from `snapshot.organizationId`, the result's `migratedFrom` field names the snapshot's own original tenant/organizationId exactly — never silently discarded (R3). This is the entire "migration/rekey" capability this task provides: a same-tenant identifier change with provenance, not a cross-tenant move.
