## Semantics

- `validatePersistedPlanAdmissionEvent(raw, expected)` is invoked for every line `getEvents` reads, before any event reaches the reducer. `expected` is the exact `{tenantId, customerId, projectId, planId}` tuple the caller passed to `getEvents`/`getState` — never a value read from the persisted data itself.
- Every persisted event must be a recognized `EVALUATION_RECORDED` or `ANSWER_RECORDED` object shape; `eventId`/`recordedAt` must be non-empty, non-whitespace-padded strings; `planVersion` must be a positive integer. Any violation throws `CorruptedPlanAdmissionEventError` (fail-closed) — nothing is silently dropped, coerced, or partially accepted.
- The event's own `tenantId`/`customerId`/`projectId`/`planId` must exactly equal the requested tuple ("envelope scope" gate) — this is what stops a foreign-scoped FIRST event from ever reaching the reducer and constructing foreign state.
- For `EVALUATION_RECORDED`, the nested `result`'s `tenantId`/`customerId`/`projectId`/`planId`/`planVersion` must exactly equal the event envelope's own identity/version ("nested-result correlation" gate) — an independent, overlapping check from the envelope-scope gate (guard-disable sanity proved both are independently load-bearing: disabling either one still leaves the other catching most cross-scope forgeries; only the envelope gate catches an `ANSWER_RECORDED`-type forgery, since that event type has no nested result to cross-check). `result.status` must be a recognized `AdmissionStatus` (`ADMITTED`/`BLOCKED`/`WAITING`).
- For `ANSWER_RECORDED`, `answeredEntity` must be a non-empty, non-whitespace-padded string. No business-level admission authorization is performed here (that remains `recordAnswer`'s job, unchanged) — this task hardens persistence integrity/isolation only, per Rev137's explicit instruction not to alter `applyPlanAdmissionEvent` business semantics.
- Phase A explicitly deferred `FileDurableOutcomeJobStore`'s equivalent blind-cast gap and `FileDurableEngineeringStore`'s equivalent blind-cast gap (see Inventory table below). Phase B (below) closes the former; the latter remains DEFERRED-BY-ACTIVATION per Rev138's activation-aware truth-sync.

### Semantics (Phase B)

- `validatePersistedOutcomeJobLine(raw, expectedTenantId, filePath)` is invoked for every line `FileDurableOutcomeJobStore.readAll` reads, before dedup/`get`/`list` logic ever sees it. Invalid JSON fails closed with the new `CorruptedOutcomeJobLineError` rather than escaping as an unclassified `SyntaxError`.
- A persisted record must be a JSON object with structurally valid (non-empty, correctly-typed) `tenantId`/`customerId`/`projectId`/`jobId`/`jobFamily`/`businessObjective` and a `state` drawn from the same recognized `OutcomeJobState` closure already used elsewhere in this repository (`postgres-outcome-job-store.ts`'s `RECOGNIZED_OUTCOME_JOB_STATES`).
- The record's own embedded `tenantId` must exactly equal the `tenantId` whose file is actually being read — this is the exact gap Rev138 named: previously a forged/corrupted record with a foreign `tenantId` could be returned by `get()`/`list()` from the requested tenant's own file, since nothing checked the record's own identity against the tenant whose file was read. Guard-disable sanity confirms this is independently load-bearing (witnesses: B4, B5).
- `putIfAbsent` and `list` both call through `get`/`readAll`, so a corrupted line fails closed on every path — `putIfAbsent` can never append/rewrite through a corruption it cannot safely interpret (witness: B8), and `list` never returns a partial/empty result over a corrupted file (witness: B5).
- No public interface changed: `get(tenantId, jobId)` and `list(tenantId, customerId, projectId)` keep their exact pre-existing signatures and same-tenant/customer/project conflict semantics (`InvalidDurableOutcomeJobStoreError`, unchanged). First-record-wins dedup for legitimate replay is preserved unmodified.
