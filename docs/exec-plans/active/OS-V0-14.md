## Implementation record

`tests/os-v0-14-second-organization-smoke.test.ts` (7 tests), introducing one distinct, real Organization B (`organizationId: "org-b-smoke"`, tenant `t-b-smoke`) alongside Organization Zero's own real identity (`org_akilta`, tenant `t-akilta`, mirroring OS-V0-13's own constants exactly), through the identical constructors/resolvers both organizations already used:

- **org/membership/access** (3 tests): Organization A's and Organization B's own authenticated staff ingress each succeed independently; Organization A's own staff session/grant, substituted into a `requireInternalOsAccess` call for Organization B's organization, fails closed with `NoStaffMembershipError`/`InternalOsAccessDeniedError` (the "stale A deep link after switching to B" case, modeled directly).
- **resource binding** (1 test): both organizations' resource bindings bootstrapped into the SAME shared `FileDurableOrganizationResourceBindingStore` instance each resolve READY independently; a cross-tenant `.get()` lookup (Organization B's tenantId against Organization A's organizationId, and vice versa) returns `undefined`.
- **connection/SecretRef** (1 test): the exact SAME bare `connectionBindingId` string, used by both organizations in the SAME shared `FileDurableConnectorConnectionStore` instance, independently reaches VERIFIED for each (proving the store key is tenant-scoped, not id-only — each tenant's first save independently starts at version 1). Revoking Organization A's connection (via the real OWNER-authenticated admin boundary) does not affect Organization B's identically-named connection, which remains VERIFIED. Restart: fresh store instances at the shared directory reconstruct each organization's own isolated truth (A REVOKED, B VERIFIED).
- **plan/job/run/task identity** (1 test): one bounded CONCURRENT dispatch (`Promise.all`) of Organization A's and Organization B's own `OutcomeJobExecutionRun`, using the exact SAME bare `jobId`/`runId` string, against the SAME shared `FileDurableOutcomeJobExecutionStore`/`FileDurableQuotaReservationStore` instances. Each organization's own run state is independently invoked and independently retrievable (`assert.notDeepEqual`), never the same shared record. Restart reconstructs both organizations' own run states identically.
- **evidence/audit/observability** (1 test): a real `/os/admin` HTTP route configured for Organization B, with `OperationalObservabilitySource` wired to the SAME shared connection store (keyed by the request's own current `organization.tenantId`, never a cached/stale one), renders Organization B's own `CONNECTED_UNVERIFIED` state and never Organization A's `VERIFIED` state for the identically-named connection.

**Golden C**: not re-proven for Organization B — OS-V0-13's own repo-wide finding (no concrete `ConnectorTransport` implementation exists anywhere in `src/`) is a global repository property, not an org-specific one; manufacturing a second live provider action "for symmetry" is explicitly forbidden by Rev196's own text. Config/policy and quota/economics planes are exercised live by the concurrent dispatch test's own `createQuotaAdmissionScope`/tenant-bound quota reservation, consistent with this packet's own bounded "focused validation, not broad chaos" scope (Non-scope above).

**Sanity check (test-validity, not a new production guard — none was introduced):** the Admin-scoping test's own `OperationalObservabilitySource.resolveView` was temporarily hardcoded to always read Organization A's tenant regardless of which organization the live route actually serves, simulating exactly the cross-org leak Rev196 is concerned about. This reproduced exactly the predicted single failure (the "must never leak" assertion), with the other 6 tests unaffected, then was restored.
