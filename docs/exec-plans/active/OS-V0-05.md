## Why this package is source-ready (Rev144's own gap analysis)

Live exact-head inspection at the start of this task confirmed the specific gap Rev142 anticipated: `OutcomeJob` business lifecycle/verification semantics (`outcome-job.ts`) are already strongly guarded, but `FileDurableOutcomeJobStore`/`PostgresOutcomeJobStore` expose only `putIfAbsent`/`get`/`list` — later execution transitions (progress, checkpoint, result, retry) are not durable runtime truth. `WorkerInvoker.invokeSafely` explicitly records no retry/dedupe persistence. `local-execution-hardening.ts` explicitly discloses no authoritative durable `LocalTaskLease`/effect-state store exists. `ExternalEffectAttempt` already has fail-closed UNKNOWN/retry/readback semantics and is reused, not replaced. The smallest honest package is therefore a durable OutcomeJob execution-run/event runtime composing existing primitives — no generic queue, second workflow engine, second IAM, Agent Supervisor, or Reliability Engine.

## Semantics

### Event/run identity (`outcome-job-execution-event.ts`)

`OutcomeJobExecutionEvent` binds exact `tenantId+customerId+projectId+jobId+runId+correlationId+attempt+sequence+type`. `eventId` is never caller-supplied: it is derived via `deriveOutcomeJobExecutionEventId` as `JSON.stringify([tenantId, customerId, projectId, jobId, runId, attempt, sequence, type])` — the same collision-safe injective-tuple-encoding discipline as `durable-plan-admission-store.ts`'s `planKey` (Rev44 F2) and `effective-configuration-policy.ts`'s `effectiveRef` (Rev143 F1). **`type` is included in the tuple** because the run-level `ACCEPTED` event and its first attempt's `ATTEMPT_STARTED` event deliberately share the same `(attempt: 1, sequence: 1)` coordinate by convention; without `type` in the id, those two structurally distinct events would collide onto one `eventId` and the second would be silently deduped away as a false "duplicate" of the first (this exact defect was caught live during this task's own guard-disable-equivalent development cycle — see Validation below — before ever reaching Brain review).

Twelve event types: `ACCEPTED` (run-level, once), `ATTEMPT_STARTED` (begins an attempt), `PROGRESS`/`CHECKPOINT` (ongoing truth), and nine attempt-closing types: `SUCCEEDED`, `FAILED`, `CANCELLED`, `TIMED_OUT`, `STALLED`, `DEGRADED`, `BLOCKED`, `UNKNOWN`, `UNSUPPORTED`. `reason` is mandatory on every closing type except `SUCCEEDED`, and forbidden elsewhere; `progressRef`/`checkpointRef` are type-scoped the same way.

### Deterministic reducer (`outcome-job-execution-run-state.ts`)

`applyOutcomeJobExecutionEvent(state, event)` is a pure fold, mirroring `plan-admission-run-state.ts`'s own reducer discipline:

- The first event for a run must be `ACCEPTED` at attempt 1, sequence 1 (Package Contract B) — anything else throws.
- Every subsequent event's `tenantId/customerId/projectId/jobId/runId/correlationId` must exactly match the run's own identity — any mismatch throws (cross-scope substitution fails closed).
- Exact duplicate `eventId` redelivery is a no-op returning the identical `state` reference.
- `ATTEMPT_STARTED` may only start `currentAttempt + 1`, only once the current attempt (if any) is terminal; a stale/superseded attempt number is a silent no-op.
- A result/progress event targeting an attempt that has not started fails closed; targeting an older, superseded attempt, or an already-terminal current attempt, or carrying a sequence ≤ the attempt's last-applied sequence, is a silent no-op (never regresses durable truth).
- Once an attempt reaches any of the nine closing statuses, it is terminal: no further progress/result applies to it short of a new `ATTEMPT_STARTED`.

`reconstructOutcomeJobExecutionRunState` folds a full event log from scratch — restart-safety is structural, not a separate cache that could diverge.

### Durable stores (`durable-outcome-job-execution-store.ts`, `postgres-outcome-job-execution-store.ts`)

Both mirror this repository's established durable-store convention (`FileDurablePlanAdmissionStore`, `PostgresOutcomeJobStore`): persisted replay is untrusted input, fully revalidated on read (`validatePersistedOutcomeJobExecutionEvent` / `validatePersistedOutcomeJobExecutionRow`) against the exact requested scope before ever reaching the reducer, and `getState` always replays the reducer itself — so a shape-valid but logically corrupted persisted log (e.g. a `SUCCEEDED` with no prior `ATTEMPT_STARTED`) fails exactly the same way a corrupted live event stream would.

The Postgres store's `ON CONFLICT (tenant_id, event_id) DO NOTHING` is the actual duplicate-protection primitive (database constraint, not a read-then-write race). It is keyed on `(tenant_id, event_id)` rather than the bare `(tenant_id, job_id, run_id, attempt, sequence)` tuple precisely because `ACCEPTED`/`ATTEMPT_STARTED` share a coordinate by convention (see above) — `event_id` (which already encodes `type`) is what actually distinguishes them at the database layer too.

### Runtime composition (`outcome-job-execution-runtime.ts`)

- `dispatchOutcomeJobExecutionRun`: durably accepts a run, starts attempt 1, invokes the worker via the existing, unmodified `invokeSafely`. Idempotent by construction — dispatching an already-existing `runId` is a no-op that never re-invokes the worker.
- `retryOutcomeJobExecutionAttempt`: advances to the next attempt only from a retryable terminal status (`FAILED`/`TIMED_OUT`/`STALLED`/`DEGRADED`/`BLOCKED`/`UNKNOWN`); `UNKNOWN` additionally requires an explicit `AuthorityContext` with `canPerformProtectedActions: true` (never blindly retried).
- Both dispatch and retry re-check a caller-supplied `expectedFingerprint` vs. `currentFingerprint` (the caller's own freshly-resolved `ProjectActivationProfile.sourceFingerprint`) **before** appending any event or invoking the worker — a stale fingerprint blocks with zero durable side effect (`StaleActivationFingerprintError`).
- `recordExecutionResult`/`SUCCEEDED` never itself calls `verifyOutcomeJob` or produces `VERIFIED`. `advanceOutcomeJobAfterExecutionSuccess` is the one narrow, separate bridge, and it only ever reaches the existing, unmodified `EXECUTING -> VERIFYING` edge via `transitionOutcomeJob` — reaching `VERIFIED` still requires the existing, separate verification gate.
- `applyWorkerHeartbeat` is the identity function: heartbeat/connectivity telemetry has no code path capable of mutating execution-run truth.
- `requestExecutionCancellation`/`requestExecutionCheckpoint` return `UNSUPPORTED` (never a fabricated `CANCELLED`/`CHECKPOINT`) unless the caller-supplied executor capability descriptor actually declares support.
- Only `executorKind: "INJECTED"` is activated; any other value throws, disclosing NOT_ACTIVATED/UNSUPPORTED rather than simulating a local/provider lane this package does not durably support (Activation Boundary).

### `worker-invoker.ts` extension (Package Contract G)

`OutcomeJobExecutionInvocationContext` is a new, optional field (`outcomeJobExecution?`) on `WorkerInvoker.invoke`'s input and `invokeSafely`'s input. `taskId`/`branch`/`checkpointSha` are completely untouched — no existing ENG-ORCH caller supplies the new field, so none is affected. Proven by two new additive tests in `worker-invoker.test.ts` plus the pre-existing 8 ENG-ORCH-focused tests remaining green unmodified.

## Rev145 correction (independent exact-head review of `80b24fa`)

Brain Rev145 found four real gaps, all corrected on the same PR #109 / branch, within the same bounded 15-file surface (no new file added):

- **F1 — concurrent dispatch/retry double-invoke**: durable event-row dedupe alone did not make "invoke the worker" a single-authority action — two concurrent callers could both observe no prior state, both durably append the same (deduped) `ACCEPTED`/`ATTEMPT_STARTED` truth, and both invoke. **Fix**: `DurableOutcomeJobExecutionStore.appendEvent` / `AsyncOutcomeJobExecutionStore.appendEvent` / `ExecutionEventStore.appendEvent` now return `created: boolean` — an atomic single-authority claim (a synchronous check-then-write for the file store, since JS's run-to-completion semantics make this genuinely atomic within one process; the database's own `ON CONFLICT (tenant_id, event_id) DO NOTHING ... RETURNING event_id` for Postgres, correct even under real concurrent writers). `dispatchOutcomeJobExecutionRun`/`retryOutcomeJobExecutionAttempt` now invoke the worker **only** when their own `ATTEMPT_STARTED` append reports `created: true`. Evidence: `D14`, `D15` (concurrent `Promise.all` dispatch/retry witnesses, `invokeCount === 1`); `S2`/`P2` re-asserted for the new single-authority append semantics.
- **F2 — persisted replay boundary not fully fail-closed**: the file store trusted a persisted `eventId` verbatim (a forged `ATTEMPT_STARTED` line carrying the preceding `ACCEPTED` event's `eventId` would be silently swallowed by reducer dedupe); neither store fully re-enforced type-scoped field rules (required/forbidden `reason`, `progressRef`, `checkpointRef`, valid `occurredAt`) on replay; the Postgres store silently recomputed `eventId` instead of rejecting a raw column mismatch, and checked only `tenant_id` rather than the full five-field requested scope. **Fix**: a single shared function, `validatePersistedOutcomeJobExecutionEventRecord` (`outcome-job-execution-event.ts`), is now the sole persisted-replay boundary for **both** stores — it fully re-enforces every construction-time field rule (via the same `parseOutcomeJobExecutionEventCoreFields` `createOutcomeJobExecutionEvent` itself calls), requires exact five-field (tenant+customer+project+job+run) scope correlation, and recomputes the canonical `eventId` from the record's own tuple, throwing on any mismatch. Evidence: `S8` (forged-eventId swallow witness), `S9` (missing-required-`reason` witness), `S10` (eventId-forgery witness), `P6` (Postgres eventId-forgery witness), `P7` (Postgres full-scope, not tenant-only, witness).
- **F3 — execution authority incomplete**: dispatch/retry required same-tenant but never checked `EXECUTE` permission, so a same-tenant READ-only or empty-permission `AuthorityContext` could reach worker invocation. **Fix**: both `dispatchOutcomeJobExecutionRun` and `retryOutcomeJobExecutionAttempt` now call `requirePermission(authority, "EXECUTE")` immediately after `requireSameTenant`. Evidence: `D16`.
- **F4 — caller-supplied current state not scope-correlated**: `retryOutcomeJobExecutionAttempt`/`recordExecutionProgress`/`recordExecutionResult`/`requestExecutionCancellation`/`requestExecutionCheckpoint` consumed a caller-constructible `currentState`'s `runId`/`correlationId`/`attempt`/`sequence` without first proving it belonged to the exact target tenant/customer/project/job, and without re-fetching actual current durable truth. **Fix**: a new shared helper, `verifyAndRefreshExecutionState`, is now called first by all five functions — it fails closed on any identity mismatch between `currentState` and the given `tenantScope`/`customer`/`project`/`job`, then re-fetches the real current state from the store by `runId` and uses that (not the caller's copy) for every subsequent derivation. Evidence: `D17` (forged cross-job `currentState` witness across all five functions), `D18` (stale-caller-copy freshness witness).

Guard-disable sanity performed on all four new/strengthened guards: disabling the F1 atomic-claim check failed exactly `D14`/`D15`; disabling the F2 eventId-forgery check failed exactly `S8`/`S10`/`P6`; disabling the F3 `EXECUTE`-permission check failed exactly `D16`; disabling the F4 identity-correlation check failed exactly `D17`. Each restored and reconfirmed against a full green regression before proceeding to the next.

Full regression after all four corrections: **1963/1963 passing** (1953 prior + 10 new: `D14`–`D18` [5], `S8`–`S10` [3], `P6`–`P7` [2]).
