## Goal

Make "a post-review push invalidates old merge approval" an enforced, tested domain invariant rather than only conversational/process discipline — by extending (not duplicating) `src/domain/engineering-run-state.ts`'s existing pure reducer.

## Scope (this checkpoint — the narrow, additive extension only)

- `EngineeringRunState.supersededResolutions: ReadonlyArray<BrainResolution>` (new field) — durable history of every `BrainResolution` a later `CHECKPOINT` on the same run has superseded. A resolution is explicitly retained as superseded history, never silently dropped, so a caller can always distinguish "no resolution ever existed" from "an approval existed but is now stale for the current `checkpointSha`."
- `CHECKPOINT_ACCEPTING_STATUSES` now includes `"PASS"`, so a fresh `CHECKPOINT` event is an authorized transition out of `PASS`, not a status-guard no-op.
- New guard inside the `CHECKPOINT` case: if the run is `PASS` and the incoming event's `checkpointSha` equals the run's current `checkpointSha` (a duplicate delivery of the exact same reviewed commit, not a genuine new push), it remains a safe no-op — the still-current approval is not invalidated by replay traffic.
- Otherwise, when the run has a live `resolution` at the moment a `CHECKPOINT` is accepted (whether the prior status was `PASS` or `CHANGES_REQUIRED`), that resolution is appended to `supersededResolutions` and the new state's `resolution` is cleared — the run explicitly reopens into `CHECKPOINT_RECEIVED` for the new `checkpointSha`.

## Explicitly deferred (not invented)

No new event type was added — the existing `CHECKPOINT` event already carries everything needed (`branch`, `baseSha`, `checkpointSha`, `fencingToken`) to represent "a fresh push." No second orchestration engine, no second canonical-state system, no PR/merge-execution side effect (this module remains a pure reducer with no I/O) — a caller (e.g. a future merge-gating integration) is responsible for actually checking `resolution` before allowing a merge; this slice only makes the invalidation itself an enforced state transition instead of a caller-side convention. `COMPLETED` remains untouched and terminal — this task's acceptance criterion is about pre-merge review approval, not about reopening an already-completed/merged run, and `TERMINAL_STATUSES` is checked before the `CHECKPOINT`-accepting-status guard is even consulted, so this is enforced by the existing generic invariant, not a new one.

## Architecture / semantic invariants (preserved, verified by test)

- Global fencing floor is checked before the `CHECKPOINT`-accepting-status guard (unchanged code path): a stale-fenced `CHECKPOINT` still cannot invalidate a `PASS` approval, regardless of this change.
- `COMPLETED` remains terminal: a post-completion `CHECKPOINT` still cannot reopen a completed run (E3 invariant, now re-verified against the new `PASS`-accepting behavior specifically, not just against non-`PASS` statuses).
- Wrong branch/baseSha for an existing run still fails closed before the new duplicate/supersession logic is reached (unchanged `E1`/`E8` check, now proven to run ahead of the new guard).
- A duplicate `CHECKPOINT` delivering the exact same reviewed `checkpointSha` on a `PASS` run is a safe no-op — replay traffic cannot accidentally invalidate a still-current approval.
- Superseded resolutions accumulate correctly across multiple push→review→push cycles (verified with a two-cycle chain: the second supersession appends to, rather than overwrites, the first).
- `reconstructState`/`projectLifecyclePhases` require no change — both already operate generically over `applyEvent`'s output and correctly observe the new `CHECKPOINT_RECEIVED` phase transition out of `PASS`.
