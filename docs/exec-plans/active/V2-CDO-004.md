## Invariants

- Requirement, binding and secret-reference IDs are explicit, non-empty stable refs.
- `ConnectionRequirement`/`ConnectionBinding` remain bound to the exact ownership tuple; a binding cannot rebind a requirement to a different customer/organization/project/service (checked before any other validation).
- `accountOwner` is always explicit; no default is inferred.
- `delegatedScope` cannot silently widen beyond `ConnectionRequirement.minimumProviderScope` (subset semantics); an empty `minimumProviderScope` requires no delegated scope, a non-empty one requires a non-empty, bounded `delegatedScope`.
- Construction never proves requested/connected/verified state. `createConnectionBinding` always starts `REQUESTED`; `transitionConnectionBinding`'s table has no `-> VERIFIED` edge from any state — `verifyConnectionBinding` is the sole path to `VERIFIED`, requiring an explicit non-empty `evidenceRef`, mirroring `outcome-job.ts`'s `verifyOutcomeJob` split.
- `SecretRef` is a one-field opaque reference boundary; `ConnectionBinding.secretRef`, when present, is only that opaque id — never raw credential material.
- `VERIFIED_AVAILABLE` capability admission requires a compatible `VERIFIED` binding (matching ownership tuple) plus explicit evidence; `UNVERIFIED`/`UNSUPPORTED`/`INELIGIBLE` are never silently promoted — there is no separate promotion function, only the one construction function.
- `CapabilityAdmission` has no field or function capable of executing a provider action, approving work, or transitioning/verifying an `OutcomeJob`/`ProjectPlanVersion` (verified functionally and by import-boundary scan).
- `REVOKED`/`HANDOVER_COMPLETE` are terminal state/reference semantics only — plain map lookups with no external effect.
- No provider SDK, OAuth runtime, or commerce-connector-specific semantics anywhere in this contract (DEC-084 boundary).
- Pure creation/validation has no external effect.

## Round 1 Correction (CR-1) — 25 August 2026

Brain independent disposition on checkpoint `7b48fdcea11fe024cc753649e99a69cd76f91876`: **CHANGES_REQUIRED — CR-1 CAPABILITY/BINDING COMPATIBILITY**, same task/branch, no Founder relay required.

- **CR-1 (capability/binding compatibility defect)**: closed. `createCapabilityAdmission()` checked ownership equality, `VERIFIED` `connectionState`, and a non-empty `evidenceRef`, but never proved that the supplied `binding` actually corresponded to the `requiredCapabilityRef` being admitted. `ConnectionBinding` carries only an opaque `connectionRequirementId`, not the capability it satisfies, so `binding` alone can never prove capability identity — a VERIFIED binding for capability A could be reused to construct `VERIFIED_AVAILABLE` for capability B under the same ownership tuple. Corrected by requiring `VERIFIED_AVAILABLE` construction to also receive the exact `ConnectionRequirement` the binding was issued against, and validating two facts transitively: (a) `requirement.requiredCapabilityRef === input.requiredCapabilityRef`, and (b) `binding.connectionRequirementId === requirement.connectionRequirementId`. Both must hold — matching capability text alone is not sufficient if the binding was not actually issued against that specific requirement (a distinct requirement object that happens to declare the same capability string does not count). The `WEBSITE_BUILD_v1` fixture's `createCapabilityAdmission` call was updated to pass `requirement: WEBSITE_BUILD_V1_CONNECTION_REQUIREMENT`.
- New focused regressions in `tests/capability-admission.test.ts`: "CR-1: VERIFIED_AVAILABLE without the ConnectionRequirement rejects...", "CR-1 (a): a VERIFIED binding whose requirement's capability matches the admitted capability succeeds", "CR-1 (b): a same-ownership VERIFIED binding issued for a DIFFERENT capability cannot produce VERIFIED_AVAILABLE for this capability" (the core mismatch regression Brain's disposition asked for), and "CR-1: a requirement whose requiredCapabilityRef matches, but whose connectionRequirementId does not match the given binding's, rejects" (the linkage check independently, using two distinct requirements that coincidentally share the same capability text). Four existing C8 tests ("with a binding that is not itself VERIFIED rejects", "without an explicit evidenceRef rejects", "with a VERIFIED binding + evidenceRef succeeds", the cross-tenant test) were updated to also pass the matching `requirement`, so each continues to test the specific failure mode its title claims rather than being short-circuited by the new missing-requirement check.
