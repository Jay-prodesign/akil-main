## Invariants

- Requirement, binding and secret-reference IDs are explicit, non-empty stable refs.
- `ConnectionRequirement`/`ConnectionBinding` remain bound to the exact ownership tuple; a binding cannot rebind a requirement to a different customer/organization/project/service (checked before any other validation).
- `accountOwner` is always explicit; no default is inferred.
- `delegatedScope` cannot silently widen beyond `ConnectionRequirement.minimumProviderScope` (subset semantics); an empty `minimumProviderScope` requires no delegated scope, a non-empty one requires a non-empty, bounded `delegatedScope`.
- Construction never proves requested/connected/verified state. `createConnectionBinding` always starts `REQUESTED`; `transitionConnectionBinding`'s table has no `-> VERIFIED` edge from any state — `verifyConnectionBinding` is the sole path to `VERIFIED`, requiring an explicit non-empty `evidenceRef`, mirroring `outcome-job.ts`'s `verifyOutcomeJob` split.
- `SecretRef` is a one-field opaque reference boundary; `ConnectionBinding.secretRef`, when present, is only that opaque id — never raw credential material.
- `VERIFIED_AVAILABLE` capability admission requires a compatible `VERIFIED` binding (matching ownership tuple) plus explicit evidence; `UNVERIFIED`/`UNSUPPORTED`/`INELIGIBLE` are never silently promoted — there is no separate promotion function, only the one construction function.
- `CapabilityAdmission` has no field or function capable of executing a provider action, approving work, or transitioning/verifying an `OutcomeJob`/`ProjectPlanVersion` (verified functionally and by import-boundary scan).
- `REVOKED`/`HANDOVER_COMPLETE` are terminal state/reference semantics only — plain map lookups with no external effect.
- No provider SDK, OAuth runtime, or commerce-connector-specific semantics anywhere in this contract (DEC-084 boundary).
- Pure creation/validation has no external effect.
