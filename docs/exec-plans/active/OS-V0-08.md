## Why this package is source-ready (Rev168's own gap analysis)

Rev168 itself states the repo-native constraint directly: this repository is TypeScript/Node with no React/Vite/Next stack and no runtime UI dependency. `src/web/shell-render.ts` is the existing Client Portal (V2-APP-001) - deliberately separate and untouched. This package is exactly that missing composition, reusing every existing primitive by import (never by re-implementation), adding no new identity/authority concept.

No `ProjectStore`/`ProjectPort` exists anywhere in this repository (confirmed by repo-wide inspection) - Work's project listing is therefore built on a caller-injected `WorkProjectSource` read source (mirroring `request-handler.ts`'s own optional `teamAttentionSource?` pattern exactly), honestly `NOT_ACTIVE` in production until a real source is separately authorized, never fabricated.

## Goal

A distinct, staff-only, read-only internal web application surface (`/os/...`) presenting the 9 primary destinations Rev168 names (Home/Command, Work, Attention/Approvals, AI & Capabilities, Connections, Knowledge/Evidence, People, Products, Admin/Settings), gated by real staff-session + organization-membership + effective-access truth, rendering deterministic truthful-incomplete states (`NOT_ACTIVE`/`FORBIDDEN`/`EMPTY`/`READY`) wherever a real backing data source does not yet exist, with zero mutating affordances anywhere. ## Semantics

### Identity and access (`internal-os-access.ts`)

`requireInternalOsAccess` composes three already-existing, unmodified primitives in sequence: `requireStaffSession` (proves a genuine staff session), `requireMatchingStaffMembership` (proves exactly one ACTIVE `OrganizationMembership` in the target organization's tenant), and `resolveEffectiveOrganizationAccess` (proves tenant correlation, principal binding, and - when a project is later named - assignment evidence, then reads `permissions`/`canPerformProtectedActions` verbatim from the caller-supplied `AuthorityContext`). This repository has no existing "staff membership -> AuthorityContext" derivation, and inventing one would be new IAM policy (explicitly forbidden) - so, matching the repository's universal discipline that `AuthorityContext` is always caller-supplied, a `StaffAccessGrant` bundles `{membership, authority, assignments, roleContext?}` per staff member, supplied by the caller exactly like `requireMatchingStaffMembership`'s own `memberships` parameter. Phase A additionally requires `READ` permission on every grant (the read-only floor) via the existing `requirePermission`.

`requireInternalOsProjectAccess` re-runs the identical `resolveEffectiveOrganizationAccess` decision with a `project` supplied, so a `MEMBER` with `READ` but no `AssignmentReference` for that exact project is denied even after organization-level access was already granted - this is what makes Work project-detail deep-linking fail server-side (`D`-style test: `FORBIDDEN`, never widened).

### View state (`internal-os-view-state.ts`)

Nine destinations, one stable IA (`NAV_DESTINATIONS`), visibility computed from real `EffectiveAccessResolution` permissions/`canPerformProtectedActions` plus actual assignment evidence (`isDestinationVisible`/`resolveNavVisibility`) - never from `OrganizationAccessRole` alone, and (Rev170 F1) never uniform across every GRANTED resolution either: `home`/`people`/`products` are the READ-only floor every GRANTED staff member sees; `work` requires at least one real project `AssignmentReference`; `admin`/`ai-capabilities`/`connections`/`knowledge` require `WRITE`; `attention` requires `EXECUTE` or `canPerformProtectedActions`. The request handler calls the SAME `isDestinationVisible` function to fail closed (403) on a direct deep-link to a destination hidden from that caller's own nav - a destination invisible in the sidebar is equally unreachable by URL. Home and Work are genuinely real (organization/access summary; project + job listings scoped to the CURRENT membership's own `AssignmentReference` evidence, hydrated through caller-injected `WorkProjectSource`/`WorkJobSource` read sources that degrade to `NOT_ACTIVE` when absent - matching `request-handler.ts`'s own optional-source pattern). Attention/Approvals, AI & Capabilities, Connections, and Knowledge/Evidence render a shared, honest `NOT_ACTIVE` state (no OS-V0-06/07/13 backend exists yet). People shows only the current viewer's own membership (no directory-listing source exists anywhere in this repository, so a broader directory would be fabricated). Products declares only this shell `ACTIVE`; every other line is `NOT_ACTIVE` (no purchase/commercial implication). Admin/Settings echoes the SAME organization/access truth already resolved, plus an explicit list of the concepts (`Workers`/`Connections`/`Policies`/`Defaults`/`Approvals`/`Usage`/`Audit`/`Kill-switch`) that have no backing source yet - there is no separate, richer "admin-only" data source anywhere in this package.

### Rendering (`internal-os-render.ts`)

A single reusable application-chrome wrapper (branded header, current-Organization line, responsive sidebar-collapsing-to-top-nav at one `@media` breakpoint, skip link, semantic header/nav/main landmarks, `:focus-visible` outlines, status text always visible - never color alone) plus reusable primitives (nav item, status chip, card, table). Zero `<button>`/`<form>` elements exist anywhere in this module's own template-literal text (verified directly by `os-v0-08-boundary-scan.test.ts`) - Phase A exposes no mutating affordance of any kind, so "ADMIN label + READ-only authority exposes no active write/execute CTA" holds by construction, not merely by runtime check.

### Routing and transport (`internal-os-request-handler.ts` / `internal-os-http-server.ts`)

Manual path parsing (`/os`, `/os/home`, `/os/work`, `/os/work/:customerId/:projectId`, `/os/attention`, `/os/ai-capabilities`, `/os/connections`, `/os/knowledge`, `/os/people`, `/os/products`, `/os/admin`) - no router library, matching `request-handler.ts`'s own `parsePortalPath` discipline exactly. A distinct session-token header (`x-akilta-staff-session-token`, vs. the Client Portal's `x-akilta-session-token`) keeps the two identity families unambiguous even before either provider is consulted. `internal-os-http-server.ts` is the only file in this package's own surface that imports `node:http`, mirroring `http-server.ts`'s own ADR 0001 exactly for this package.
