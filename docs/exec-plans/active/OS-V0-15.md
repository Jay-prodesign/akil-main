## New witnesses (`tests/os-v0-15-v0-adversarial-chaos-gate.test.ts`, 3 tests)

- **#11 retry-storm**: an envelope exhausted by one occupant reservation; a second identity's admission request is REJECTED, then retried 25 further times with the IDENTICAL idempotencyKey (simulating cost fan-out/retry-storm pressure). Every retry stays REJECTED with the IDENTICAL cached `eventId`, and the durable ledger file's line count never grows beyond the original 2 lines (1 RESERVED occupant + 1 REJECTED storm) across the entire storm AND across a restart (fresh store instance, same directory) - proving the exact next allowed action (wait for allowance to free up, never "keep retrying harder") survives both the storm and a crash/restart mid-storm.
- **#13 secret-exfiltration**: a real VERIFIED `org_akilta`-style connection with a bound `secretRef`. (a) A resolver that throws, with its own exception text deliberately engineered to contain a real secret value, proves `executeConnectorCapability`'s own thrown `UnresolvedConnectorSecretError` never echoes that value - only the opaque `secretRef` id. (b) A resolver returning an empty value hits the same opaque-id-only contract. (c) A resolver that genuinely succeeds and returns the real secret proves the function's own successful `ConnectorExecutionResult` return value never itself carries the resolved secret as a field or in its serialized form, even though the injected transport boundary (the one intentional handover point) does receive it.
- **#17 crash-loop**: one genuine dispatch (worker invoked, quota RESERVED+COMMITTED - 2 durable lines). Then three separate, consecutive simulated crash+restart cycles, each constructing FRESH durable store instances at the SAME directories and naively re-issuing the IDENTICAL dispatch call. Every cycle proves: the worker is never re-invoked (`invoked: false`, `callLog.length` stays at 1); the reconstructed durable state is byte-identical (`assert.deepEqual`) to the genuine first dispatch; and the quota ledger's line count never grows beyond the original 2 lines - proving idempotent recovery holds across a repeated crash LOOP, not merely a single restart.

## Load-bearing defects found and fixed

Chaos testing against item #11 and item #13 exposed two real, narrow, pre-existing defects. Per the Chaos Execution Rules' own instruction ("fix the smallest coherent root cause on the same OS0-15 branch, add the direct regression/failure witness, and continue the matrix"), both were fixed on this branch rather than deferred:

1. **`src/domain/execution-quota-admission.ts` — REJECTED-event `amount` field asymmetry.** The RESERVED event branch of `admitQuotaReservation` always set `amount: requestedAmount`; the REJECTED branch only set it when `requestedAmount.presence === "REPORTED"`, omitting it entirely for an UNKNOWN-presence request. Since `assertReplayMatchesOriginalRequest` compares `existing.amount` against a freshly-derived, always-defined `createCostAmount(...)` result on every replay (RESERVED or REJECTED alike), a REJECTED decision for an UNKNOWN-presence request could never be safely replayed - the very next identical retry (exactly the retry-storm scenario item #11 chaos-tests) threw `QuotaReservationConflictError` instead of correctly replaying the cached REJECTED outcome. **Fix**: the REJECTED branch now unconditionally sets `amount: requestedAmount`, mirroring RESERVED exactly. `amount` was already an optional field (`readonly amount?: CostAmount`) and is read elsewhere only on `RESERVED`/`COMMITTED`/`RECONCILIATION_REQUIRED` events (never on REJECTED), so this is a safe, purely additive change with no other call site affected. Confirmed load-bearing: the pre-fix code reproduced the exact predicted single failure in witness #11 (`QuotaReservationConflictError` on the very first retry); after the fix, all 3 new witnesses and the full existing 2507-test regression pass unchanged. Scoped to the `FileDurableQuotaReservationStore`/pure-ledger-fold path only, which is the only path OS-V0-13/14 activated; the Postgres adapter's own independent row-reconstruction has a related but distinct symptom (an `amountMinorUnits: 0` default is always included rather than omitted) and is left as a separately-trackable, non-blocking finding since the Postgres plane is not activated by any accepted V0 candidate to date.
2. **`src/domain/connector-execution.ts` — resolver-exception-message forwarding.** `executeConnectorCapability`'s secret-resolution catch block forwarded an arbitrary caught exception's own `.message` verbatim into its own thrown `UnresolvedConnectorSecretError`. A `SecretResolver` is caller-injected and not guaranteed to sanitize its own exception text; if a real resolver implementation's underlying client library ever embeds the actual secret value (or other sensitive request content) in its own thrown message, this forwarding would leak it through this layer's own error. **Fix**: the catch block no longer interpolates the caught exception's message at all - the thrown message cites only the opaque `secretRef` id, exactly matching the sibling "no secretRef bound"/"empty value" branches' own style. Confirmed load-bearing: the pre-fix code reproduced the exact predicted single failure in witness #13 (the "must never echo the real secret value" assertion) when the test's resolver stub was engineered to embed a real secret in its own thrown message; after the fix, all 3 new witnesses and the full existing regression pass unchanged.

Neither fix introduces a NEW load-bearing guard (both correct an existing guard's completeness/boundary rather than adding a new one), so per the Chaos Execution Rules' own "Guard-disable sanity is required only for NEW or materially changed load-bearing guards" instruction, no separate guard-disable pass is required beyond the TDD-style fail-before/pass-after cycle already performed and recorded above (which is this project's own established sanity-check methodology).
