## Goal

Support partner-agency organizations and agency employees while preventing membership from becoming unrelated-client access or commercial rights: a distinct partner/agency organization identity, explicit employee→client assignment as the minimum access relationship, deterministic revocation, and fail-closed cross-client access resolution.

## Architecture / semantic invariants

- **Why `PartnerEmployeeMembership` is a distinct type from `OrganizationMembership` (V3-ORG-001), not a reuse**: `OrganizationMembership.tenantId` represents AKILTA-internal staff membership in the AKILTA tenant's own org chart. Reusing it for an agency employee would imply the employee is a member of that same org chart — exactly what §6 requires to remain distinct ("partner/agency organization identity is distinct from AKILTA/customer organizations"). `PartnerEmployeeMembership` is scoped to a `PartnerOrganization` instead, itself tenant-scoped via `TenantScope` reuse (not a second tenant concept). This dependency choice is disclosed here per the blueprint's own "reuse where natural, disclose the choice" discipline already applied in `V3-ORG-001`/`V3-OWN-001`.
- `PartnerEmployeeMembership.tenantId` is always derived from its own `partnerOrganization` argument, never separately supplied — a membership can never claim a tenant its own partner organization does not belong to.
- `createPartnerClientAssignment` rejects when the given membership's tenant does not match the given `ownership` scope's tenant (fail-closed foreign-tenant grant).
- `resolvePartnerClientAccess` never consults a `PartnerEmployeeMembership`'s mere existence — only an `ACTIVE` `PartnerClientAssignment` matching the exact membership id AND the full `ownership` tuple resolves `AUTHORIZED`. A matching `REVOKED` assignment resolves `REVOKED` (distinct from `UNAUTHORIZED` — "never granted at all"), so no revoked or never-granted access is ever mistaken for `AUTHORIZED`.
- `revokePartnerClientAssignment` returns a new value; the original grant is never mutated in place (functional test asserts this), and rejects revoking an already-revoked assignment.
- `PartnerRelationshipType` is representable on `PartnerOrganization` but is never read by `resolvePartnerClientAccess` or any other function in this module — no relationship type can imply access, sell-rights, or customer-binding authority by presence (structural, verified by a functional test constructing a `WHOLESALE` partner with zero assignments and confirming `UNAUTHORIZED`).
- `PartnerClientAssignment` carries only identifier/status/timestamp fields — no field exists that could hold projected customer content (margins/notes/prompts/secrets), verified by a boundary-scan field-name check.
