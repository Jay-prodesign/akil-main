## Goal

Implement the smallest honest, repo-native floor for §11's own candidate lifecycle:

> OBSERVED_PATTERN → CANDIDATE → EVALUATED → APPROVED_REUSABLE → PRODUCT/CAPABILITY_CANDIDATE → separately governed release/commercial state.

This floor implements exactly the first four states. `PRODUCT/CAPABILITY_CANDIDATE` and beyond are explicitly "separately governed release/commercial state" per §11's own text and are not fabricated here — the same declared-but-not-producible discipline already used by `commercial-authority.ts`'s `DiscountAuthorityLevel` and `service-capability-routing.ts`'s `ExecutionMaturity`.

## Scope

New pure domain module: `src/domain/reusable-capability-learning.ts`.

- `ReusableCapabilityCandidateStatus`: `"OBSERVED_PATTERN" | "CANDIDATE" | "EVALUATED" | "APPROVED_REUSABLE"`.
- `CapabilityEvaluationOutcome`: `"REUSABLE" | "NOT_REUSABLE"`.
- `CapabilityObservationRef`: one tenant/project's contribution toward proving a pattern is genuinely reusable (`tenantScope`, `projectRef`, `observedAt`).
- `ReusableCapabilityCandidate`: the lifecycle record. `observationRefs` is present only pre-promotion; an `APPROVED_REUSABLE` candidate never carries it.
- `observeCapabilityPattern(input)` — the only construction function; always produces `OBSERVED_PATTERN` with exactly one observation; accepts no status/evidence/promotion field from the caller.
- `recordAdditionalObservation(input)` — appends a further independent occurrence; only valid on `OBSERVED_PATTERN`; rejects a duplicate `tenantScope`/`projectRef` pair already recorded.
- `promoteToCandidate(candidate)` — `OBSERVED_PATTERN` → `CANDIDATE`; requires at least two observations spanning at least two distinct tenants.
- `evaluateCandidate(input)` — `CANDIDATE` → `EVALUATED`; requires a non-empty `evalEvidenceRef`; records `REUSABLE` or `NOT_REUSABLE`.
- `promoteToReusable(input)` — the only function that can produce `APPROVED_REUSABLE`; requires the candidate be `EVALUATED` with `evaluationOutcome === "REUSABLE"`; requires non-empty `licenseOrIpNote` and `reusableAssetVersion`; strips `observationRefs` from the returned object.

## §11 acceptance directions and how each is satisfied

| §11 text | This module's enforcement |
|---|---|
| "one customer artifact or one successful agent run never becomes a product by assertion" | `promoteToCandidate` structurally rejects fewer than two observations, or observations confined to a single tenant (tests G4, G6) |
| "reusable learning must strip customer secrets/confidential context and retain provenance/licensing/IP boundaries" | `promoteToReusable` always omits `observationRefs` from its return value (test G16); requires non-empty `licenseOrIpNote` (test G15) |
| "no hidden cross-client training/data blending" | Observations are never merged/interpreted — only counted and compared by `tenantScope.tenantId`/`projectRef` identity; `patternRef` is an opaque, uninterpreted pointer |
| "customer-specific prompt/data cannot be promoted raw; eval evidence required" | `evaluateCandidate` requires a non-empty `evalEvidenceRef` (test G10); `promoteToReusable` rejects any candidate that was never evaluated (test G13) or evaluated `NOT_REUSABLE` (test G14) |
| "reusable asset versioned and independently testable" | `promoteToReusable` requires a non-empty `reusableAssetVersion` (test G15) |
| "product-specific demand/economics/governance remain separate from Customer Execution" | No commercial/demand/governance field exists anywhere on this type — out of scope by construction |
| "BUILD/BUY/INTEGRATE/ORCHESTRATE/DOWNGRADE/REMOVE review applies to reusable technology choices" | Explicitly deferred — this floor governs *pattern* promotion (something observed across customer delivery work), not infrastructure/technology-choice review, which has no real process anywhere in this repository yet; not fabricated |

## Explicitly deferred

- `PRODUCT/CAPABILITY_CANDIDATE` and the "separately governed release/commercial state" beyond it — no commercial/release governance system exists in this repository; fabricating one would misrepresent capability.
- BUILD/BUY/INTEGRATE/ORCHESTRATE/DOWNGRADE/REMOVE technology-choice review (§11) — a genuinely separate process from pattern-candidate promotion; not invented here.
- Any wiring into an actual observation source (e.g. deriving `CapabilityObservationRef`s automatically from delivery/outcome-job data) — this floor accepts caller-supplied observations only, matching the "declared, not yet producible" discipline used throughout this repository's V3–V5 slices.
