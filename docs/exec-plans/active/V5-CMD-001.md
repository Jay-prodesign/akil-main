## Scope

New pure domain module: `src/domain/internal-command-projection.ts`.

- **"Company / Portfolio Attention"** surface ← `OperationsAttentionItem` (V4 Workstream B, already merged). Unlike the existing customer-facing `resolveActiveOperationsAttention` (which correctly filters to one tenant/customer/project), this aggregation is deliberately **cross-tenant** — the intended, authorized behavior for an internal company-wide view, never for a customer session.
- **"Partners"** surface ← `PartnerCapabilityClaim` (V5 Workstream H, `V5-PTN-001`, already merged).
- `buildInternalCommandCenterProjection(input)`: pure function taking `attentionItems`, `partnerClaims`, `generatedAt`, `asOf`; returns:
  - `companyPortfolioAttention.items` (verbatim), `.activeCount`, `.levelTally` (`NORMAL`/`EXCEPTION`/`ESCALATED` counts).
  - `partners.items` (Rev90-corrected — see below): each entry pairs the raw `claim` (verbatim) with its computed `effectiveStatus`, via the existing `resolvePartnerCapabilityClaimStatus` (not the claim's raw stored `status`), so the never-stored `EXPIRED` disposition is correctly reflected as of the caller-supplied `asOf`. `.statusTally` (`UNVERIFIED`/`ADMITTED`/`EXPIRED`/`REVOKED` counts) is computed from the same `effectiveStatus` values, so it can never disagree with `partners.items`.

## Rev90 correction (Brain CHANGES_REQUIRED — BOUNDED, exact head `0d3380786d033371b0e41b79022d0c33034ffe35`)

Brain's exact-head review found (F1): exposing the raw `PartnerCapabilityClaim[]` (`partners.claims`) alongside a separately-computed `statusTally` let the two silently disagree — a claim stored `ADMITTED` but past its `reviewByAt` counts as `EXPIRED` in the tally while the claim object's own `status` field still reads `ADMITTED`. A downstream reader consulting the raw claim's `status` directly (instead of the tally) could present stale authorization as current.

Fix: `partners.claims: ReadonlyArray<PartnerCapabilityClaim>` is replaced with `partners.items: ReadonlyArray<PartnerCapabilityClaimWithEffectiveStatus>`, a new exported wrapper type pairing each raw `claim` (unchanged, still available for audit/provenance) with its `effectiveStatus` — computed the same way and at the same `asOf` as the tally, via the existing `resolvePartnerCapabilityClaimStatus`. `statusTally` is now derived from exactly the same `effectiveStatus` values written into `items`, so the two can never contradict each other by construction. This module remains unwired (the internal/staff auth boundary above is unaffected — this fix is purely to the projection's own internal consistency). Two new adversarial tests: J7 (a stored-`ADMITTED`-but-expired claim exposes `item.claim.status === "ADMITTED"` and a distinct `item.effectiveStatus === "EXPIRED"`, proving neither is hidden nor silently overwritten) and J8 (recomputing the tally from `items` byte-for-byte matches `statusTally` for a mixed set of claims). J6 updated for the new shape (reference-identity now checked per-item's `claim`, not the whole array, since `items` is a freshly derived array of wrapper objects).
