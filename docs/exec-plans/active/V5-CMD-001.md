## Goal and genuine boundary (disclosed, not fabricated)

§14's outcome: "internal company/project command center plus customer-facing progress/approval surfaces that reflect governed state rather than agent narration," naming eight internal conceptual surfaces (Company/Portfolio Attention, Projects/Repositories/Engineering, Operations/Capabilities/Providers, Approvals/Protected Gates, Evidence/Audit/Incidents, Workers/Routing/Evaluations, Partners, Product Lab/Reusable Capabilities) plus customer-facing progress surfaces, with "live route names resolved later."

**This repository has no internal/staff authentication concept anywhere.** `AuthenticatedPrincipal` / `SessionContext` / `TenantContext` (`src/web/session-context.ts`) are exclusively customer/tenant-scoped, built for the customer-facing Client Portal (`V2-APP-001`/`V2-CDO-006`). §14's own required UX truths demand internal and customer projections stay separate ("customer projection excludes internal prompts/secrets/private reasoning/irrelevant repo detail") — reusing the customer `AuthenticatedPrincipal` for an internal command surface would blur exactly that boundary, and inventing a new internal-principal/session concept is a genuine new architectural decision, not something a bounded floor slice should decide unilaterally.

This checkpoint therefore implements only the **read-model aggregation** piece — a pure function with no HTTP/session/route wiring — covering two of the eight named internal surfaces that already have real, merged-`main` backing data. Live routing and internal authentication are the genuine dependency boundary this checkpoint stops at, matching Rev89's own closing instruction ("continue... until a genuine protected/dependency/capability boundary").

## Scope

New pure domain module: `src/domain/internal-command-projection.ts`.

- **"Company / Portfolio Attention"** surface ← `OperationsAttentionItem` (V4 Workstream B, already merged). Unlike the existing customer-facing `resolveActiveOperationsAttention` (which correctly filters to one tenant/customer/project), this aggregation is deliberately **cross-tenant** — the intended, authorized behavior for an internal company-wide view, never for a customer session.
- **"Partners"** surface ← `PartnerCapabilityClaim` (V5 Workstream H, `V5-PTN-001`, already merged).
- `buildInternalCommandCenterProjection(input)`: pure function taking `attentionItems`, `partnerClaims`, `generatedAt`, `asOf`; returns:
  - `companyPortfolioAttention.items` (verbatim), `.activeCount`, `.levelTally` (`NORMAL`/`EXCEPTION`/`ESCALATED` counts).
  - `partners.claims` (verbatim), `.statusTally` (`UNVERIFIED`/`ADMITTED`/`EXPIRED`/`REVOKED` counts) — computed via the existing `resolvePartnerCapabilityClaimStatus` (not the claim's raw stored `status`), so the never-stored `EXPIRED` disposition is correctly reflected as of the caller-supplied `asOf`.

| §14 text | Enforcement |
