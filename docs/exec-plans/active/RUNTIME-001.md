## Scope (this checkpoint)

- **Application runtime boundary**: `src/runtime/app-config.ts` (`resolveAppConfig`) resolves a validated, provider-neutral `AppConfig` (port, deployment environment, persistence driver, optional database URL) from a plain string-keyed env record — fails closed on every malformed input, never silently defaults. `src/runtime/node-server-entrypoint.ts` (`createNodeRuntime`) is the one Node-hosting-target adapter that turns a resolved `AppConfig` into an actually-listening `node:http` server, reusing the existing, unmodified `createHttpServer` (`src/web/http-server.ts`) wired to the existing `src/fixtures/web-shell.ts` fixture sources — a deliberate bootstrap default, not a persistence-wiring decision (see "Explicitly deferred" below). Only listens when run as the actual entry point (`isMainModule()` guard), so it stays safely importable by tests.
- **Health contracts**: `src/runtime/health-check.ts` (`evaluateHealth`) is a pure aggregation over caller-supplied `HealthProbeResult`s — `HEALTHY` only if every probe passed (including the zero-probe case), `DEGRADED` if only non-critical probes failed, `UNHEALTHY` if any critical probe failed.
- **Provider-neutral PostgreSQL persistence interface + migrations**: `src/ports/sql-client.ts` (`SqlClient`) is the injected, driver-neutral SQL execution boundary (parameterized queries only — no caller may interpolate a value into a query string). `src/ports/async-outcome-job-store.ts` (`AsyncOutcomeJobStore`) is a deliberately distinct, async-native sibling port to the existing, unmodified, synchronous `DurableOutcomeJobStore` (see "Explicitly deferred" below for why these are not unified). `src/domain/postgres-outcome-job-store.ts` (`PostgresOutcomeJobStore`) implements it against an injected `SqlClient`, with `validatePersistedOutcomeJobRow` fail-closed replay validation (matching this codebase's own established convention from `validatePersistedConnectorConnection`/`validatePersistedSaleBootstrapRecord`) — never trusts a driver-returned row as `OutcomeJob` via a blind cast. `putIfAbsent`'s actual idempotency primitive is the database's own `UNIQUE (tenant_id, job_id)` constraint via `ON CONFLICT ... DO NOTHING` (`migrations/0001_outcome_jobs.sql`), correct even under genuinely concurrent writers — not a read-then-write race in application code.
- **Cloudflare-runtime candidate scaffolding**: `src/runtime/cloudflare-worker-fetch-adapter.ts` (`createCloudflareWorkerFetchHandler`) is the Fetch-API counterpart to `http-server.ts`'s `node:http` adapter, translating a Worker isolate's Web-standard `Request`/`Response` to/from the exact same transport-agnostic `IncomingRequestLike`/`OutgoingResponseLike` shape `request-handler.ts` already defined (ADR 0001) — proving the existing read-only shell logic can serve Worker traffic, with zero change to `request-handler.ts` itself. `deploy/cloudflare/wrangler.toml.example` documents the target shape without being a live binding (no `account_id`, no credential, `.example` suffix so it is never picked up as a real config by accident).
- **Deployment automation artifacts**: `deploy/docker/Dockerfile` (+ `.dockerignore`) is a Node-runtime container candidate (multi-stage build → run `dist/`), config supplied entirely through the same env vars `app-config.ts` consumes. `.github/workflows/ci.yml` runs `npm install && npm run build && npm run test && npx tsc --noEmit` on every PR and push to `main` — build/test verification only, no deploy step, no secret, no live account touched.
- **Build hygiene fix carried onto this branch**: `package.json` gained a `clean` script (`rm -rf dist`) wired into `build` (`npm run clean && tsc -p tsconfig.json`), matching the same fix already applied on the `claude/conn-001-integration-control-plane` and `claude/sale-to-close-e2e-floor` branches earlier in this session — without it, switching branches without a manual `rm -rf dist` can leave a stale compiled test file (from a branch with different `tests/*.ts` sources) picked up by `node --test dist/tests/*.test.js`, exactly as was independently observed and fixed while validating this branch's own build.

## Explicitly deferred (not invented)

- **No wiring of `AsyncOutcomeJobStore`/`PostgresOutcomeJobStore` into any existing synchronous domain call site.** `DurableOutcomeJobStore` (`src/domain/durable-outcome-job-store.ts`) is synchronous by design (in-process `node:fs` calls); a network-backed store cannot honestly implement that same interface without either lying about synchronicity or blocking the event loop. Rather than force a false unification, `AsyncOutcomeJobStore` is its own port with the same idempotency contract expressed as `Promise`s. Deciding how (or whether) an async, network-backed store gets threaded through the domain's existing synchronous call sites is an explicit, disclosed, later architectural decision — not made here.
- **No live database connection, account, or credential anywhere in this checkpoint.** `migrations/0001_outcome_jobs.sql` is never applied against any database by this checkpoint; `PostgresOutcomeJobStore` is only ever exercised in tests against an injected in-memory `FakeSqlClient`, never a real `pg` client. No `pg` (or any SQL driver) package was added to `package.json` — the `SqlClient` port is deliberately driver-agnostic, and choosing/wiring a concrete driver is left to whoever makes the actual "connect to a real Postgres instance" decision.
- **No Cloudflare account, zone, or deploy.** `wrangler.toml.example` is exactly that — an example, not a live binding — and no `wrangler` dependency was added. No Worker entry point that a real deploy would target was written; `cloudflare-worker-fetch-adapter.ts` is the reusable translation layer such an entry point would call into, once a real deploy decision is made.
- **No production data-wiring decision for the Node runtime.** `createNodeRuntime` serves the existing fixture-backed `ClientProjectSnapshotSource`/`TeamAttentionSource` (`src/fixtures/web-shell.ts`) — proving the runtime boundary (config resolution, health reporting, actually listening and serving real HTTP traffic) works end-to-end, not that real customer data is wired through it. That remains its own later decision.
- **No CI deploy step.** `.github/workflows/ci.yml` only builds and tests; it deploys nothing, touches no secret, and mutates no live account or infrastructure — consistent with the corridor's "no live account mutation" hard stop.

## Architecture / semantic invariants (verified by test)

- `resolveAppConfig` fails closed on a non-numeric or out-of-range `PORT`, an unrecognized `DEPLOYMENT_ENV`, an unrecognized `PERSISTENCE_DRIVER`, or a `PERSISTENCE_DRIVER=POSTGRES` with a missing/whitespace-only `DATABASE_URL` — never silently defaults to a guessed configuration.
- `evaluateHealth` is a pure function: `HEALTHY` for zero probes or all-passing probes, `DEGRADED` for only non-critical failures, `UNHEALTHY` if any critical probe failed (a failed critical probe always outranks a simultaneously failed non-critical one).
- `PostgresOutcomeJobStore.putIfAbsent` replay of the same job is idempotent (`created: false`, returns the first-persisted job unchanged); the same `jobId` under two different tenants persists as two fully independent rows; reusing the same `jobId` for a different project under the same tenant fails closed (sanity-checked: the guard was temporarily removed, the corresponding test confirmed it then fails, and the fix was restored and reconfirmed passing).
- `PostgresOutcomeJobStore.get`/`list` never trust a driver-returned row as valid: an unrecognized `state`, an empty required field, or a row returned under the wrong tenant (a defense-in-depth check against a mis-scoped driver) all throw `CorruptedOutcomeJobRowError` rather than silently reconstructing a plausible-looking `OutcomeJob`.
- `createCloudflareWorkerFetchHandler` round-trips method/path/headers/status/body through `request-handler.ts`'s existing `RequestHandler` type completely unmodified — the same handler function passed to `createHttpServer`'s underlying `createRequestHandler` output would work identically here.
- `createNodeRuntime`'s server, bound to a real ephemeral local port, serves an authenticated portal request with `200` and rejects an unauthenticated one with a non-`200` status — a genuine local HTTP round-trip, not a mocked transport.

## Hard Non-Scope
