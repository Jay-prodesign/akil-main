## Goal

Provide a pure, side-effect-free capability-claim lifecycle for partner organizations in which a claim can never be self-certified into an admitted state, admission always requires evidence, and admission is always subject to a caller-supplied review date rather than standing indefinitely.

## Scope (this checkpoint)

- `src/domain/partner-capability-admission.ts`:
  - `PartnerCapabilityClaim` — scoped to an existing `PartnerOrganization` (imported type-only from `partner-organization.ts`, not duplicated), carrying an opaque `capabilityRef`, a `PartnerCapabilityClaimStatus` (`UNVERIFIED` | `ADMITTED` | `EXPIRED` | `REVOKED`), and admission provenance (`evidenceRef`/`admittedAt`/`reviewByAt`) present only once admitted.
  - `createPartnerCapabilityClaim(input)` — the only construction function; accepts no status or evidence field, so every claim is born `UNVERIFIED`.
  - `admitPartnerCapabilityClaim(input)` — the only function that can produce `ADMITTED`; requires a non-empty `evidenceRef` and a `reviewByAt` strictly after `admittedAt`; rejects any claim not currently `UNVERIFIED`.
  - `revokePartnerCapabilityClaim(input)` — transitions `ADMITTED` → `REVOKED`; rejects a claim that was never admitted or is already revoked.
  - `resolvePartnerCapabilityClaimStatus(input)` — resolves the claim's effective status as of a caller-supplied `asOf`; an `ADMITTED` claim whose `reviewByAt` has passed resolves `EXPIRED` (computed, never stored); `UNVERIFIED`/`REVOKED` pass through unchanged.

## Explicitly deferred (not invented)

No filesystem/network/child_process coupling, no persistence layer, no system-clock read anywhere (the module has exactly one type-only import, `PartnerOrganization`, and every status resolution is bound to a caller-supplied `asOf`, never `Date.now()`). No capability catalog or capability-taxonomy validation (`capabilityRef` is an opaque pointer, exactly like `sourceRef`/`capabilityRef` conventions elsewhere in `src/domain/`). No wiring of claim status into `resolvePartnerClientAccess` or any client-assignment gate — §12 does not require capability claims to gate client access, only to exist as a governed, non-self-certifiable lifecycle; conflating the two would be inventing scope. No commercial/legal relationship modeling (§12: "commercial/legal relationship state is separate from technical eligibility" — untouched, consistent with `PartnerRelationshipType`'s existing representable-only discipline). No partner routing/reason/fallback recording (§12's last acceptance bullet) — that is a distinct, larger routing-decision concern (structurally similar to `V5-WRK-001`'s worker routing, but for partners) intentionally left for a separate future checkpoint rather than bundled in here.

## Architecture / semantic invariants (verified by test)

- A freshly created claim is always `UNVERIFIED` — there is no construction path, and no way to pass extra fields through `createPartnerCapabilityClaim`, that can produce any other status.
- Only `admitPartnerCapabilityClaim` can produce `ADMITTED`, and only when given a non-empty `evidenceRef` and a `reviewByAt` strictly after `admittedAt`; it rejects a claim that is not currently `UNVERIFIED`.
- Only `revokePartnerCapabilityClaim` can produce `REVOKED`, and only from `ADMITTED`; a never-admitted or already-revoked claim rejects.
- `EXPIRED` is never a stored value — it is a `resolvePartnerCapabilityClaimStatus` computation relative to the caller-supplied `asOf`, so the same stored claim can honestly resolve `ADMITTED` at one `asOf` and `EXPIRED` at a later one with no mutation.
- `REVOKED` and `UNVERIFIED` pass through `resolvePartnerCapabilityClaimStatus` unchanged regardless of `asOf` — expiry only ever applies to an `ADMITTED` claim.

## Hard Non-Scope

No filesystem/network/child_process import (verified by boundary scan — exactly one type-only import, `PartnerOrganization`); no provider/model hard-coding; no secret/credential material; no system-clock read (verified by boundary scan); no capability-catalog validation or taxonomy; no wiring into client-access resolution; no commercial/legal/payment modeling; no merge/deploy/release/production/publication/customer-binding action anywhere in this checkpoint's source.
