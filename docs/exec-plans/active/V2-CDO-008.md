## Goal

Implement the smallest truthful, provider-neutral, read-only Delivery Project Advisor domain contract: L0 Observe (truthful restatement of existing `ClientProjectSnapshot` state) and L1 Recommend (recommend only among currently policy-eligible, `VERIFIED_AVAILABLE` capabilities). The advisor is an explanation/recommendation surface only — not a state authority, evidence source, approval mechanism or executor.

## Scope (this checkpoint — domain contract only)

- `AdvisorObservation` / `AdvisorRecommendationOption` / `AdvisorResult` types + `buildAdvisorResult` (`src/domain/delivery-advisor.ts`) — pure function composing an existing `ClientProjectSnapshot` (V2-CDO-005) and an optional `DeliveryRecipe` (V2-CDO-002) into a deterministic L0/L1 result.
- One canonical `WEBSITE_BUILD_v1` fixture (`src/fixtures/website-build-v1-advisor.ts`) reusing the existing V2-CDO-005 snapshot fixture and V2-CDO-002 recipe fixture verbatim.

## Explicitly deferred (not invented as done)

Per the corridor's own "no invented scope" discipline, this checkpoint does **not** build the presentation/UI layer (acceptance items A12's visual distinction and the rendered half of A13's loading/empty/error states) — it only builds the domain contract those UI states would consume. This mirrors how V2-CDO-002 (recipe contract) itself preceded any execution/UI layer. `AdvisorResult.status` (`"RECOMMENDATIONS_AVAILABLE" | "UNAVAILABLE"`) is a deterministic discriminated result already available for a future UI slice to render truthfully; no advisor UI currently exists in `src/web/`.

## Architecture / semantic invariants

- `buildAdvisorResult` imports only **types** from `client-project-snapshot.ts` and `delivery-recipe.ts` — no create/transition/verify function from `outcome-job.ts`, `project-plan.ts`, `approval-reference.ts`, `capability-admission.ts` or `connection-authority.ts` is imported, so this module structurally cannot mutate any of those (A7).
- A recommendation can only be constructed from a capability summary whose `status` is exactly `VERIFIED_AVAILABLE` (A5) — `UNVERIFIED`/`UNSUPPORTED`/`INELIGIBLE` are classified into observation-only lists (`unsupportedCapabilityRefs`/`ineligibleCapabilityRefs`), never recommended.
- `ownership` must exactly match `snapshot.ownership` (tenant/customer/project/service tuple) or construction throws `InvalidAdvisorContextError` (A3), same fail-closed pattern as `buildClientProjectSnapshot` / `createCapabilityAdmission`.
- A recipe is only cited as `applicableRecipeRef` provenance when its own `jobFamily` actually appears among the project's real `OutcomeJob` records in the snapshot's `deliveryStatus.jobs` — never merely because a caller passed one in (A1/A11).
- Zero eligible capabilities yields a deterministic `UNAVAILABLE` result with an explicit `unavailableReason`, never an empty/ambiguous state (A6, A13 domain half).
- No provider/model SDK, prompt, persistent memory, RAG/vector store, or new dependency is referenced anywhere in this module (A8, A10, A15).
