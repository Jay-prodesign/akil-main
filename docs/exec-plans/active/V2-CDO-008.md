## Architecture / semantic invariants

- `buildAdvisorResult` imports only **types** from `client-project-snapshot.ts` and `delivery-recipe.ts` — no create/transition/verify function from `outcome-job.ts`, `project-plan.ts`, `approval-reference.ts`, `capability-admission.ts` or `connection-authority.ts` is imported, so this module structurally cannot mutate any of those (A7).
- A recommendation can only be constructed from a capability summary whose `status` is exactly `VERIFIED_AVAILABLE` (A5) — `UNVERIFIED`/`UNSUPPORTED`/`INELIGIBLE` are classified into observation-only lists (`unsupportedCapabilityRefs`/`ineligibleCapabilityRefs`), never recommended.
- `ownership` must exactly match `snapshot.ownership` (tenant/customer/project/service tuple) or construction throws `InvalidAdvisorContextError` (A3), same fail-closed pattern as `buildClientProjectSnapshot` / `createCapabilityAdmission`.
- A recipe is only cited as `applicableRecipeRef` provenance when its own `jobFamily` actually appears among the project's real `OutcomeJob` records in the snapshot's `deliveryStatus.jobs` — never merely because a caller passed one in (A1/A11).
- Zero eligible capabilities yields a deterministic `UNAVAILABLE` result with an explicit `unavailableReason`, never an empty/ambiguous state (A6, A13 domain half).
- No provider/model SDK, prompt, persistent memory, RAG/vector store, or new dependency is referenced anywhere in this module (A8, A10, A15).
