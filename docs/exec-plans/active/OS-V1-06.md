## New production surface

1. **`src/domain/local-execution-bridge.ts` (EXTENDED)** — `BridgeReplayOutcome`'s `ACCEPTED` variant gains `gapDetected: boolean` (`true` iff `envelope.eventSeq > priorState.lastAcceptedEventSeq + 1`; always `false` on a device's bootstrapping first message). Purely additive — no existing call site destructures the full shape, confirmed by a targeted boundary-scan read before editing.
2. **`src/domain/local-execution-adapter-certification.ts` (NEW)** — `admitLocalWorkerAdapterResult` (stale-authority re-admission gate) and `resolveAmbiguousLocalRunDisposition` (partial-effect/timeout → `UNKNOWN`, lease target `BLOCKED` only, never overriding a real terminal event or an already-terminal lease).

Zero changes to `LocalWorkerAdapterOutcome`/`LocalTaskLeaseStatus`/`LocalWorkerAdapter` — the two new seams are closed as additive compositions over the existing, unmodified types, not a new FSM value. `BLOCKED` (already reachable from `RUNNING`/`CHECKPOINTED`) is the existing "ambiguous, needs resolution" bucket this task's `UNKNOWN` disposition routes into — inventing a parallel lease status here would duplicate it.

## Design decisions and why

- **No new lease status for "unknown."** `local-execution.ts`'s own `LocalTaskLeaseStatus` FSM is reused by every other LOCAL-EXEC module; widening it would be exactly the kind of cross-cutting change this corridor's "reuse, don't invent" discipline forbids when an existing value already serves the purpose. `BLOCKED` already means "cannot currently proceed/resolve" (it is also where `TASK_CANCELLED` lands) — `resolveAmbiguousLocalRunDisposition`'s `allowedLeaseTarget: "BLOCKED"` is a disclosure of which transition is safe, not a second status.
- **`resolveAmbiguousLocalRunDisposition` never overrides a real terminal event or an already-terminal lease.** This is the direct fix for the risk that a late-arriving disconnect/timeout signal could discard a genuine `SUCCEEDED`/`FAILED`/`CANCELLED` disposition — closing "cancel race" and the adjacent "false success via override" risk in the same function, by construction (both are `NOT_APPLICABLE` branches checked before the ambiguity branch is ever reached).
- **`admitLocalWorkerAdapterResult` requires the CALLER to supply freshly-read current device/worker state**, exactly like every other "re-resolve fresh immediately before granting" primitive in this repository (`requireInternalOsAccess`, `resolveEffectiveDelegatedAccess`, `restoreOrganizationLifecycleFromSnapshot`). It has no store dependency of its own (mirroring every other pure domain module in this family) — it cannot itself detect staleness, only refuse to honor it once detected.
- **`gapDetected` discloses, never fabricates recovery.** No retransmission/replay-request transport exists anywhere in this repository (confirmed by inspection) — adding one now would be exactly the kind of fabricated infrastructure `local-execution-hardening.ts`'s own Rev129 correction already refused for a different gap. The honest, bounded fix is making the gap an observable fact on the return value.
