## Goal

Add a pure, deterministic, explainable effective-access resolver composing `Organization` + `OrganizationMembership` + a caller-supplied `AuthorityContext`, optionally scoped to a `Project`. Identity, membership, role, ownership, assignment, permission, approval, and execution remain distinct concepts — membership role or ownership must never manufacture permissions.

## Semantics

- Exact tenant correlation is required across `Organization`/`OrganizationMembership`/`AuthorityContext`/optional `Project`; any foreign substitution fails closed.
- Permission comes only from the supplied `AuthorityContext`, read verbatim (never widened, never narrowed) — after scope/membership correlation passes.
- Protected-action eligibility additionally requires `AuthorityContext.canPerformProtectedActions` explicitly; `EXECUTE` permission alone never implies it.
- Legacy `OrganizationMembership.role` (`STAFF`/`JUNIOR`/`STUDENT`/`CLIENT_ASSOCIATE`) projects uniformly to a single effective role literal, `"MEMBER"` — no richer `OWNER`/`ADMIN` classification is fabricated from any legacy role or from `Project.ownerRef`/`OwnershipAssignment`. This module does not import `ownership-assignment.ts` at all, and never reads `Project.ownerRef` — ownership cannot grant permission or approval by construction, not merely by convention.
- Missing membership fails closed (denied, not defaulted to some implicit access level).
- The resolution carries explicit provenance (`tenantId`/`organizationId`/`membershipId`/`projectId`) and a machine-readable `reasons` list explaining the decision.
- No wall-clock read, no randomness, no hidden default. The resolver is a pure function of its inputs — re-running it with current inputs is the only way to get a current answer, so a caller cannot cache a stale decision through this module itself.

**Explicitly deferred (not fabricated):** `Organization.state` (e.g. `SUSPENDED`) is not read or checked by this resolver — the Rev127 acceptance list does not require lifecycle-state-based access revocation, and inventing it here would be scope creep beyond the specified A1-A17 matrix. This is left for later policy work, exactly as `OWNER`/`ADMIN` role richness is.

## Reuse / dependency contract

Reuses `TenantScope` (type only), `Organization`, `OrganizationMembership` (including its `OrganizationRole` type only for reference, never re-exported), `AuthorityContext` (including its `Permission` type), and `Project`/`ProjectOwnershipRef` (type only, `Project` for the optional scope check) exactly as they exist.
