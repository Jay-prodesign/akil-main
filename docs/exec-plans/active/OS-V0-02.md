## Semantics

- Exact tenant correlation is required across `Organization`/`OrganizationMembership`/`AuthorityContext`/optional `Project`; any foreign substitution fails closed.
- **(Rev129) Exact principal-identity binding is required:** the caller supplies `currentPrincipalRef`, an already-resolved application-boundary identity claim on the same trust footing as `AuthorityContext` — never inferred from `membership`, `role`, `ownerRef`, or permissions. It must be a non-empty, non-whitespace, un-padded string; missing/malformed values fail closed. Once every tenant correlation passes, the resolver additionally requires `membership.principalRef === currentPrincipalRef` before granting — this is what closes same-tenant membership substitution, which tenant correlation alone cannot detect (a different member of the same organization cannot be paired with the current caller's authority to gain that caller's access).
- Permission comes only from the supplied `AuthorityContext`, read verbatim (never widened, never narrowed) — after scope/membership/principal correlation passes.
- Protected-action eligibility additionally requires `AuthorityContext.canPerformProtectedActions` explicitly; `EXECUTE` permission alone never implies it.
- Legacy `OrganizationMembership.role` (`STAFF`/`JUNIOR`/`STUDENT`/`CLIENT_ASSOCIATE`) projects uniformly to a single effective role literal, `"MEMBER"` — no richer `OWNER`/`ADMIN` classification is fabricated from any legacy role or from `Project.ownerRef`/`OwnershipAssignment`. This module does not import `ownership-assignment.ts` at all, and never reads `Project.ownerRef` — ownership cannot grant permission or approval by construction, not merely by convention.
- Missing membership fails closed (denied, not defaulted to some implicit access level).
- The resolution carries explicit provenance (`tenantId`/`organizationId`/`membershipId`/`projectId`) and a machine-readable `reasons` list explaining the decision — including which correlation failed (tenant vs. principal) — without exposing the raw `currentPrincipalRef`/`principalRef` values being compared.
- No wall-clock read, no randomness, no hidden default. The resolver is a pure function of its inputs — re-running it with current inputs is the only way to get a current answer, so a caller cannot cache a stale decision through this module itself.
- This module does not authenticate `currentPrincipalRef` or resolve who the current caller is — that trust boundary is a future, separate application concern. This task's obligation is only to prevent membership substitution once a current identity claim is supplied by that trusted boundary.
- **(Rev130 Phase B) Exact project-scope assignment evidence is required when `Project` is supplied:** the caller optionally supplies `assignments: ReadonlyArray<AssignmentReference>` (defaulting to `[]` when omitted). Once tenant correlation and principal binding both pass, if a `Project` was supplied the resolver calls the existing `resolveAssignmentStatus({ membership, assignments, customerId: project.customerId, projectId: project.projectId })` and requires exactly `"ASSIGNED"` before granting — any other status (`UNASSIGNED`/`UNAVAILABLE`/`NOT_APPLICABLE`/`UNKNOWN`, including the empty-evidence default) fails closed. No-`Project` (organization-level) resolution is completely unaffected by this gate — Phase A's behavior is preserved exactly.
- `Project.ownerRef` and `OwnershipAssignment` still cannot substitute for `AssignmentReference` evidence or grant permission — this module still does not import `ownership-assignment.ts` and still never reads `Project.ownerRef` for any decision, in Phase A or Phase B.
- **(Rev131 Phase C) `OrganizationMembership` now carries the minimum V0 lifecycle floor:** `state: "ACTIVE" | "REVOKED"`, plus `revokedAt?`/`revokedReason?` populated only on `REVOKED`. `createOrganizationMembership` always produces a coherent `ACTIVE` record with no revocation metadata (source-compatible with every existing call site). A new one-way `revokeOrganizationMembership` transition (`ACTIVE -> REVOKED` only, no reactivation) validates the full pre-existing record via `isOrganizationMembershipActive` before consuming it (Rev126 F1 factory-bypass discipline, reused here), and validates the new `revokedAt` (valid ISO timestamp) and `revokedReason` (non-empty, non-whitespace) before transitioning. `OrganizationMembership` has no `createdAt` field, so no `createdAt`-vs-`revokedAt` ordering rule is fabricated. `resolveEffectiveOrganizationAccess` now requires `isOrganizationMembershipActive(membership)` to be `true` before granting anything — a revoked or incoherent membership denies with zero permissions regardless of how well tenant/principal/assignment/authority otherwise match. `staff-membership-guard.ts`'s `resolveMatchingStaffMembership` now additionally requires an equivalent active/coherent check before a candidate can match, so a revoked membership can never bind a staff session, and `local-execution-staff-binding.ts`'s existing `requireMatchingStaffMembership` call inherits this fail-closed behavior with zero source changes. Revocation is not permission: `AuthorityContext` remains the sole permission/protected-action source, `ACTIVE` never widens it, and assignment remains separate Project-scope evidence, all unchanged by Phase C.
- **(Rev131 Phase C, design note) `staff-membership-guard.ts` does not import `isOrganizationMembershipActive` as a value.** A pre-existing, out-of-Phase-C-surface test (`tests/family-2-boundary-scan.test.ts`) asserts this module composes `OrganizationMembership`/`TenantScope` by type only and never imports a value from `organization-membership.ts`. Rather than breaking that admitted boundary or requesting a ninth file for a one-line assertion update, the exact same three-line coherence check (`state === "ACTIVE" && revokedAt === undefined && revokedReason === undefined`) is inlined locally as `isCoherentActiveMembership`, with a doc-comment cross-referencing `organization-membership.ts`'s canonical predicate so the two stay in sync if the lifecycle shape ever changes again.

**Explicitly deferred (not fabricated):** `Organization.state` (e.g. `SUSPENDED`) is not read or checked by this resolver — neither the Rev127 nor the Rev130 acceptance list requires lifecycle-state-based access revocation, and inventing it here would be scope creep beyond the specified matrix. This is left for later policy work, exactly as `OWNER`/`ADMIN` role richness is.
