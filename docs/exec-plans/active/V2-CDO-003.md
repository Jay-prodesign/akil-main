## Goal

Implement the first pure, provider-neutral, machine-consumable domain contract for stable customer/organization/project/service ownership boundaries and customer-safe project-linked communication history/routing semantics required by the minimum `OPS-010` V2 slice. Identity, classification, routing/observation and validation semantics only — no communications runtime, CRM, or persistence layer.

## Scope (Minimum Domain Objects)

- `ProjectOwnershipRef` / `createProjectOwnershipRef` (`src/domain/project-ownership.ts`) — stable reference tuple: `tenantId` (organization mapping), `customerId`, `projectId`, optional `serviceRef`. Reference only; does not create a second customer/project lifecycle.
- `ProjectCommunicationRecord` / `createProjectCommunicationRecord` (`src/domain/project-communication.ts`) — `communicationId`, `ownership`, `direction`, `classification`, `requiredActor`, `observationState`, optional `evidenceRef`/`relatedPlanVersionId`/`relatedJobId`/`relatedArtifactRef`, `timestamp`.
- `CommunicationDirection` — `CUSTOMER_TO_AKILTA` | `AKILTA_TO_CUSTOMER`.
- `CommunicationClassification` — `INFORMATIONAL` | `ACTION_REQUIRED`.
- `RequiredActor` — `NONE` | `CUSTOMER` | `AKILTA`, with deterministic compatibility: `INFORMATIONAL` ⇒ `NONE`; `ACTION_REQUIRED` ⇒ `CUSTOMER` or `AKILTA`.
- `CommunicationObservationState` — `RECORDED_ONLY` | `DELIVERY_UNVERIFIED` | `DELIVERY_VERIFIED` | `DELIVERY_FAILED`; `DELIVERY_VERIFIED` requires a non-empty `evidenceRef`.
- `ProjectCommunicationHistory` / `buildProjectCommunicationHistory` — a validated, ownership-bound collection of records (fail-closed cross-tenant/cross-project binding + duplicate-id rejection).
- One canonical fixture (`src/fixtures/website-build-v1-communication.ts`) reusing the existing `WebsiteBuildV1Fixture`'s project identity (DEL-003) for ownership, with two example communications (one informational/verified, one action-required/unverified).

## Invariants

- Customer, organization (`tenantId`) and project references are explicit, non-empty stable refs; `serviceRef`, when present, is explicit (empty string rejected — only `undefined` omits it).
- A communication record binds to one customer/organization/project tuple; `relatedPlanVersionId`/`relatedJobId`/`relatedArtifactRef` remain contextual/reference-only and cannot rebind ownership.
- Communication IDs are unique within any validated `ProjectCommunicationHistory`.
- Direction is explicit and provider/channel-neutral — no email/SMS/Slack/vendor implementation is encoded.
- `INFORMATIONAL` requires `requiredActor` `NONE`; `ACTION_REQUIRED` requires `CUSTOMER` or `AKILTA`. No implicit actor is inferred.
- `ACTION_REQUIRED` is attention semantics only — it grants no approval/execution/resume/`OutcomeJob`-transition/customer-binding authority (no such function exists in this module; `project-plan.ts`/`outcome-job.ts` are `import type`-only dependencies, so this module has zero runtime coupling to their transition/admission functions).
- `DELIVERY_VERIFIED` requires an explicit `evidenceRef`; `RECORDED_ONLY`/`DELIVERY_UNVERIFIED` can never be silently promoted — there is no "mark delivered" mutation function; a different observation state requires constructing a new record.
- The customer-safe shape exposes no internal notes, margins/unit economics, prompts, credentials/secrets, or provider payloads.
- Existing `ProjectPlanVersion`/`OutcomeJob` verification, evidence, approval and resume semantics remain authoritative and are not duplicated or bypassed.
- Contract creation/validation has no external effect.
