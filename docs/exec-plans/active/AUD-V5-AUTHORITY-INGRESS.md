## Goal

Close the specific, real fail-open gap the finding identifies: *any* caller — with no permission, no tenant match, no protected-action authorization — could currently admit or revoke a partner capability claim. Require the caller to hold a real, tenant-matched, protected-action-authorized `AuthorityContext` before either operation can proceed, using only the existing `authority.ts` primitives.

## Scope (this checkpoint)

- `src/domain/partner-capability-admission.ts`:
  - `PartnerCapabilityClaim` gains a `tenantId` field (`PartnerOrganization["tenantId"]`), populated in `createPartnerCapabilityClaim` from the given `partnerOrganization.tenantId` — the claim now carries its own tenant identity rather than only reaching it transitively through `partnerOrganizationId`.
  - `admitPartnerCapabilityClaim` and `revokePartnerCapabilityClaim` both gain a required `authority: AuthorityContext` parameter, checked fail-closed, in this order, before any existing business check (including the claim-status check — Rev74 F2 ordering correction, so an unauthorized/cross-tenant caller cannot learn the claim's current status by observing which error is thrown): (1) `requireSameTenant(authority, claim.tenantId)`; (2) `requireProtectedActionAuthorization(authority, "<functionName>")`; (3) `requirePermission(authority, "WRITE")`.
  - Import of `requireSameTenant`, `requirePermission`, `requireProtectedActionAuthorization`, and the `AuthorityContext` type from the existing `./authority.js` sibling module — the only new import, disclosed and reflected in the updated boundary-scan test.
- `tests/internal-command-projection.test.ts` / `tests/partner-routing-decision.test.ts` (this re-derivation's own additive work, not part of original PR #33): added a shared `AuthorityContext` fixture matching each file's existing tenant scope, passed into every existing `admitPartnerCapabilityClaim`/`revokePartnerCapabilityClaim` call site. No test assertion or business logic in either file was changed.

## Explicitly NOT closed (do not disguise this as the full FINAL-V5 requirement)

This does **not** prove that `admittingAuthorityId` (the string persisted as `admittedByAuthorityId`) corresponds to any authenticated identity. `AuthorityContext` itself is explicitly documented as "a caller-supplied, application-boundary authority context - not identity/session resolution... this module does not resolve 'who is calling' from anywhere." Binding the *specific asserted string* to a *proven* authenticated principal requires real session/identity infrastructure this repository does not have anywhere (same boundary that keeps V4 Workstreams C-H blocked). What this checkpoint proves instead, honestly: the *caller invoking the admission/revocation operation itself* must hold real, tenant-scoped, protected-action-authorized permission — closing the "any anonymous caller can admit/revoke" fail-open gap, a genuine (if partial) authority-ingress improvement. No new identity/session/authentication system, no credential material, no new provider/connector.

## Architecture / semantic invariants (verified by test)

- A freshly created claim carries `tenantId` derived from its `partnerOrganization`.
- Admission/revocation both fail closed (`CrossTenantAuthorityError`/`InsufficientAuthorityError`/`ProtectedActionNotAuthorizedError`) on cross-tenant authority, missing `WRITE` permission, or missing protected-action authorization, respectively.
- The authority gate runs *before* the existing business-field checks (self-admission, claim-status, evidence, timestamps) — proven directly by H27 (authority before self-admission check) and the Rev74 F2 regressions H28/H29 (authority before claim-status check on both admit and revoke).
