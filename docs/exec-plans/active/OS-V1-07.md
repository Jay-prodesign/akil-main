## New production surface

1. **`src/domain/outcome-job-retry-containment.ts` (NEW)** — `resolveRetryContainmentDisposition`: a pure, stateless, ADDITIONAL admission gate a caller consults BEFORE constructing the next `ATTEMPT_STARTED` event. Classifies `RETRY_STORM` (absolute attempt-count cap exceeded) and `CRASH_LOOP` (next attempt too soon after the current one, or too many attempts already landed within a sliding density window). Never modifies `outcome-job-execution-run-state.ts`'s own frozen/ACCEPTED reducer (hardened through Rev145-191) — this is a separate, composable gate, exactly mirroring OS-V1-06's own `admitLocalWorkerAdapterResult` pattern (a new admission check layered on top of an already-accepted primitive, not a change to it).

## Design decisions and why

- **No change to the frozen reducer.** `applyOutcomeJobExecutionEvent` has been reviewed and hardened across Rev145 through Rev191; reopening it for a bound-retries feature would risk the exact kind of re-litigation this corridor's "reuse, cite, don't re-prove" discipline exists to avoid. The gate is a pure precondition the RUNTIME (not the reducer) is expected to consult — this task provides the real, usable primitive; live wiring into `outcome-job-execution-runtime.ts`'s own dispatch/retry call site is explicitly named as a follow-on in "Non-scope" below, not fabricated as already wired (mirroring OS-V1-02's own delegated-access-grant primitive, which was accepted standalone before any web-layer wiring existed).
- **The gate never blocks a run's first attempt.** REV209 says "bound RETRIES" — a run must always be allowed to start once; only the decision to retry again is in this gate's scope. Initial admission remains quota/authority's own separate, already-closed concern (OS-V0-07).
- **Two independent containment signals, not one.** An absolute cap (`RETRY_STORM`) catches a run that has simply retried too many times in total, regardless of pacing. A density/interval check (`CRASH_LOOP`) catches a run retrying too FAST — either back-to-back with almost no gap, or in a dense burst within a short window — even while still well under the absolute cap. REV209 names both "crash loop" and "retry storm" as separate witnesses; collapsing them into one signal would lose the distinction the contract draws.
- **"Rollback during in-flight work" is proven as independence, not special-cased handling.** `rollbackConfigurationPolicyDecision` (config/policy domain) and `OutcomeJobExecutionRunState` (task/run domain) share no store, no identity field, and no call path — RIF1 demonstrates this directly: rolling back a configuration decision while a job's run is actively `RUNNING` succeeds, and the run's own already-applied event log is byte-for-byte unchanged afterward. This is the honest shape of "rollback never corrupts in-flight work" for two domains that were already correctly kept separate — not a new synchronization primitive.

## Required witnesses → coverage

12 new tests in `tests/os-v1-07-operational-reliability-incident-controls.test.ts`:

| Witness | Covers |
|---|---|
| RC1 | `ADMIT` below both the absolute cap and the crash-loop density/interval thresholds |
| RC2 (retry storm) | `BLOCKED`/`RETRY_STORM` once the next attempt would exceed the absolute cap |
| RC3 (crash loop, density) | `BLOCKED`/`CRASH_LOOP` once enough prior attempts already landed within the sliding window |
| RC4 (crash loop, interval) | `BLOCKED`/`CRASH_LOOP` when the next attempt would start sooner than the minimum inter-attempt interval |
| RC5 | The run's first attempt (`currentAttempt === 0`) is always `ADMIT`, regardless of policy |

| KILL1 | Existing kill-switch control: engaging empties local-worker routing eligibility; disengaging requires protected-action authority |
| OUT1 | Outage: a `REVOKED` connection composes `killSwitchEngaged: true`; a `DEGRADED` one composes `degraded: true` — never silently `AVAILABLE` |
| LKG1 | Last-known-good rollback succeeds to a prior entry when no protected-floor conflict exists |
| LKG2 | Rollback is `BLOCKED_PROTECTED_FLOOR_CONFLICT` with zero mutation when the target would weaken a newer PLATFORM protected floor |
| RIF1 (rollback during in-flight work) | A config rollback succeeds while a same-scope `OutcomeJobExecutionRunState` is actively `RUNNING`, and that run's own event log/attempt state is completely unchanged afterward |
