### C6 — Wire retry containment into the live execution path
- **Gap (verified):** `resolveRetryContainmentDisposition` has no caller outside `outcome-job-retry-containment.ts`.
- **Canonical source:** OS-V1-07.md non-scope, which names this as "a separate, explicitly-named follow-on". REV209 OS-V1-07 "bound retries … crash-loop containment".
- **Size:** small to medium.
- **Resolution (2026-10-26):** `resolveRetryContainmentDisposition` is now wired into `retryOutcomeJobExecutionAttempt` (#187) through a new optional, backward-compatible `retryContainmentPolicy` input. When the policy is omitted, behavior is exactly unchanged. When it is supplied, the gate runs on the freshly re-read run state after the activation/quota-currentness/lineage checks and before `admitQuotaForAttempt`. A `BLOCKED` disposition returns `{ state, invoked: false, containment }` (a new optional `containment` field on `DispatchOutcomeJobExecutionResult`): no quota is reserved, no `ATTEMPT_STARTED` is appended, and the worker is never invoked. `dispatchOutcomeJobExecutionRun` is deliberately not touched, because it only ever starts attempt 1 of a run with `currentAttempt === 0`, which the gate's own rule always admits. `src/domain/outcome-job-retry-containment.ts` is unchanged. Still open, and out of this item's scope: there is no live caller of `retryOutcomeJobExecutionAttempt` in `src/runtime` or `src/web` yet, so no production path supplies a real policy. That wiring, and the canonical policy values, need their own task contract.

### C7 — Break-glass route wiring plus a durable grant/audit store
- **Gap:** OS-V1-09.md non-scope lists both the route wiring and "a durable break-glass grant/audit STORE" as follow-ons.
- **Canonical source:** REV209 OS-V1-09 and OS Blueprint §25.T.
- **Note:** this is security-sensitive, so it should come after C2/C4.
- **Resolution (2026-10-27):** both halves are built and wired (#191). **Stores:** `FileDurableBreakGlassAccessGrantStore` (`src/domain/durable-break-glass-access-grant-store.ts`) clones `FileDurableProtectedDecisionRecordStore`'s technique - a per-target-tenant append log, `linkSync` single-winner create and revise claims (a grant is created once and revised at most once, `ACTIVE` -> `REVOKED` with every other field unchanged), latest-wins reads - and revalidates every persisted grant by rebuilding it through the frozen domain's own `createBreakGlassAccessGrant`/`revokeBreakGlassAccessGrant`, never blind-casting it. `FileDurableBreakGlassSupportAccessAuditStore` (`src/domain/durable-break-glass-support-access-audit-store.ts`) clones `FileDurableAuditLog`'s technique (one global lock, a separate global `auditRef` index so uniqueness is global rather than per-tenant - the REV216 F1 correction applied from the start - and full revalidation on read), as its own store for `BreakGlassSupportAccessAudit`, not a reuse of the OutcomeJob-shaped `AuditEvent` log. **Authentication:** `authorizeBreakGlassSupportAccessAsAuthenticatedStaff` (`src/web/authenticated-break-glass-support-access.ts`) mirrors `authenticated-delegated-access.ts`: `requireStaffSession` (not `requireInternalOsAccess`, since a support principal has no membership here) supplies `currentPrincipalRef`, and each `GRANTED` decision's audit is durably appended before the decision is returned. **Route:** `GET /os/admin` takes a new, separate branch only when `x-akilta-break-glass-grant-id` is present (and the stores are wired); without it the ordinary path is unchanged byte-for-byte (proven over a real socket). The branch authenticates first (so 401/403 is never a grant-existence oracle), looks the grant up once under this deployment's own tenant, calls the frozen domain gate once per view kind (one audit per granted kind), and renders a new, narrower, read-only `BREAK_GLASS_OBSERVABILITY` page carrying only the granted `OperationalObservabilityView` fields - never `AdminViewState`, no nav, no form or button. All five kinds denied, or no such grant, is the existing 403. The runtime composes both stores (two new `/health` probes). **Still open, out of this item's scope:** no runtime path mints or revokes grants yet (that needs its own task contract), so in a deployment every break-glass request currently answers 403.

### C8 — Require `TrustedServiceResolution` in sold-scope intake
- **Gap:** SVC-ADM-001 names this as a follow-up composition. `intakeSoldScopeFromResolution` still accepts a raw `DeclaredServiceLookupResult`.
- **Canonical source:** AUD-V5-GAP-02 ("trusted service-resolution provenance … explicitly OPEN").
- **Size:** small.
- **Resolution (2026-10-27):** `intakeSoldScopeFromResolution` now requires the admission-catalog-checked `TrustedServiceResolution` (`service-catalog-admission.ts`) instead of the raw, caller-self-declared `DeclaredServiceLookupResult` - a `NOT_ADMITTED` or `UNRESOLVED_SERVICE` resolution fails closed, and the supplied `blueprint` is matched against the real admission's own `blueprintId`/`blueprintVersion`. **Found and fixed during independent adversarial review, before merging**: the first draft narrowed to `RESOLVED` but never re-checked that the carried `admission.status` was still `"ADMITTED"` - since `TrustedServiceResolution` is a plain structural type (not branded), a caller could hand-build a `RESOLVED` value wrapping an admission already revoked since it was first resolved, and intake would silently accept it.
