## Goal

Provide a single, deterministic aggregation envelope over the one real attention source-domain this repository has, without flattening its distinct domain truth, without granting action authority, and without inventing the nine unrepresentable attention families or a next-safe-action reference no data source supports.

## Scope (this checkpoint — single-domain aggregation floor only)

- `AttentionSourceDomain` (single literal `"DELIVERY_OUTCOME_JOB"`) + `OperationsAttentionItem` + `toOperationsAttentionItem` + `resolveActiveOperationsAttention` (`src/domain/operations-attention.ts`) — pure functions composing the existing `AttentionState` (V3-SLA-001) into a deterministic aggregation item and a tenant/project-scoped active-item filter.
- One canonical `WEBSITE_BUILD_v1` fixture pair (`src/fixtures/website-build-v1-operations-attention.ts`) — a fresh job placed into a `BLOCKED` exception state via the existing `outcome-job.ts` functions, wrapped through `buildAttentionState` (V3-SLA-001) and then `toOperationsAttentionItem`.

## Explicitly deferred (not invented)

Nine of §6's eleven candidate attention families (customer approval required, provider wait, credential/access problem, SLA/operating risk, failed external effect, telemetry anomaly, policy restriction, data-quality uncertainty, recovery required, optimization opportunity) have no real observable source anywhere in this repository and are therefore not represented on `AttentionSourceDomain` at all — adding a real second source domain later is additive, not a breaking change. Grouping/deduplication of correlated events (§6: "may be grouped") is not implemented — with only one source domain, there is nothing genuinely cross-domain to correlate yet. `nextSafeActionRef` is omitted entirely — no such source exists. Dismiss/resolve semantics are not implemented at all (no mutation capability exists in this module), so "dismiss/resolve semantics cannot rewrite source domain truth unless the source contract permits it" is satisfied by absence rather than by a permission check.

## Rev28 bounded correction (2026-09-02) — CHANGES_REQUIRED_SOURCE_SEMANTICS

Brain Handoff Rev28 finding on PR #7: "Current attention items omit customer/client isolation and material V4 Workstream B context/freshness semantics. Tenant+project filtering alone is insufficient for cross-client isolation."

Required bounded correction: "carry authoritative customer/client scope and filter tenant+customer+project; preserve known service/capability/source/evidence/next-safe-action/approval context and keep unknowns explicit without fabricated joins; represent freshness so absent/stale evidence cannot look current; add regression coverage for cross-customer isolation, stale/unknown freshness, and no-fabricated-join behavior."

Root cause: `AttentionState` (V3-SLA-001, merged) itself carries no `customerId` field, so `OperationsAttentionItem` could only ever be filtered by tenant+project — two customers sharing a tenant (and, in principle, even a projectId string) could not be distinguished. Separately, `buildAttentionState` can honestly report `isActive: true` on a job already in an exception state even when no `latestExceptionEvent` was supplied to it, leaving `reason`/`timestamp` absent — an aggregated item could look identically "active" whether or not real timestamped evidence actually backs it.

Fix (`src/domain/operations-attention.ts`): `toOperationsAttentionItem` now takes `{ state, job }` instead of a bare `state`. It verifies `job` identifies the exact same `jobId`/`tenantId`/`projectId` as `state` (throwing `InvalidOperationsAttentionItemError` on any mismatch — no fabricated join), then reuses `job.customerId` (`OutcomeJob`, AKI-BE-001) directly as the new required `customerId` field. `resolveActiveOperationsAttention` now takes and filters on `customerId` as well as `tenantId`/`projectId`. A new `evidenceFreshness: "CURRENT" | "UNKNOWN"` field is `"CURRENT"` only when both `reason` and `timestamp` are present (i.e. backed by a real `AuditEvent`), `"UNKNOWN"` otherwise — including for `NORMAL`/inactive items, which make no attention claim to be fresh about in the first place. `outcome-job.ts` is now imported, but as `import type` only (verified by boundary-scan) — no `createOutcomeJob`/`transitionOutcomeJob`/`verifyOutcomeJob`/`enterExceptionState` value import, so this module still cannot itself transition or fabricate an `OutcomeJob`.

Nothing else in this checkpoint's scope changed: no new source domain, no `nextSafeActionRef`, no dismiss/resolve/escalation capability, no persistence/HTTP/UI surface — those remain exactly as declared above, honestly absent rather than invented, per the "preserve known ... context and keep unknowns explicit without fabricated joins" clause of the required correction.

## Architecture / semantic invariants

- `toOperationsAttentionItem` reads every field directly off the given `AttentionState` — it cannot promote/demote urgency, invent an owner, or fabricate a reason/timestamp the source state does not already carry ("UI aggregation cannot manufacture status," §6). (Rev28) It additionally requires the originating `OutcomeJob` and fails closed if that job does not identify the exact same tenant/project/job as the `AttentionState` given — a mismatched job can never donate its `customerId` to a foreign state.
- `isActive` is always recomputed from the exact given `AttentionState.internalAttentionLevel` at call time — never cached or independently toggled, so a stale/resolved source cannot remain flagged active ("stale resolved source cannot remain active," §6 acceptance).
- (Rev28) `evidenceFreshness` is always recomputed from whether `reason`/`timestamp` are both present on the given `AttentionState` — never independently set, defaulted to `"CURRENT"`, or inferred from `isActive` alone.
- `contractualSlaStatus` is deliberately not carried into the aggregation — conflating it with internal attention would blur the exact internal-vs-contractual distinction V3-SLA-001 exists to preserve.
- `resolveActiveOperationsAttention` is a pure filter — it never mutates an item, and only ever narrows to the exact requested tenant/customer/project scope (Rev28: `customerId` added as an independently-checked filter key), verified by adversarial cross-project and cross-customer tests, including a scenario where two customers genuinely share both a tenant and a project-id string.
- This module exports no escalation/dismiss/resolve function — visibility never grants action authority ("escalation and next action are separately authorized," §6), verified by a boundary-scan test asserting the module's exact export set (now including `InvalidOperationsAttentionItemError`).
- No import of `authority.ts`, `capability-admission.ts`, `connection-authority.ts`, `service-capability-routing.ts`, or `partner-organization.ts`. `outcome-job.ts` (Rev28) is now imported, but strictly as `import type` — no create/transition/verify mutation function is pulled in, keeping this module structurally unable to itself transition an `OutcomeJob`.

## Hard Non-Scope

No provider-wait/credential/telemetry/policy/data-quality/recovery/optimization attention family; no cross-domain grouping/deduplication; no `nextSafeActionRef`; no dismiss/resolve/escalation mutation; no persistence/database; no HTTP/UI surface; no AI Commerce mutation; no merge/deploy/release/production/publication/customer-binding/legal/financial action anywhere in this checkpoint's source.
