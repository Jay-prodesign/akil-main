## Goal

Close the V5 §5 acceptance gap "agent cannot self-mark final VERIFIED" by making `EngineeringRunState`'s `RESOLVE` transition structurally reject any event not authored by `BRAIN` or `OWNER`, so a `WORKER`-authored self-certification attempt can never produce a `BrainResolution` or move the run to `PASS`/`CHANGES_REQUIRED`.

## Scope (this checkpoint)

- `src/domain/engineering-run-state.ts`: `applyEvent`'s `RESOLVE` case gains one guard, evaluated immediately after the existing status guard and before the existing `checkpointSha`/field validation: `if (event.fromRole !== "BRAIN" && event.fromRole !== "OWNER") { return noOp(state, nextFencingToken); }`. A rejected self-certification attempt is treated exactly like every other RESOLVE-path rejection already in this reducer (wrong status, wrong `checkpointSha`) — a safe no-op that still advances the fencing floor per the existing E7 convention, never a thrown error (a `WORKER` issuing a stray `RESOLVE` is expected protocol traffic to reject, not a caller bug).
- `tests/engineering-run-state.test.ts`: every one of the 14 pre-existing `RESOLVE`-emitting test call sites now passes `fromRole: "BRAIN"` explicitly (previously relying on the shared `makeEvent` helper's `fromRole: "WORKER"` default, which the fix now closes) — no existing test's actual assertions changed. Four new tests: a `WORKER`-authored `RESOLVE(PASS)` is rejected; a `WORKER`-authored `RESOLVE(CHANGES_REQUIRED)` is also rejected (self-marking either disposition is forbidden, not only the favorable one); an `OWNER`-authored `RESOLVE` is accepted (the guard admits independent `BRAIN` review or an explicit `OWNER` override, never `WORKER` self-certification); a rejected self-certification attempt still advances the fencing floor without any business effect.

## Explicitly deferred (not invented)

No new event type, no second orchestration engine, no change to the `EngineeringRole` enum (`WORKER`/`BRAIN`/`OWNER` already existed in `engineering-event-envelope.ts`; this checkpoint only makes `RESOLVE` consult a field that already existed on every event). No authentication/identity-proofing of `fromRole` itself — as with every other field on `EngineeringEventEnvelope`, the envelope's `fromRole` is trusted input from the durable event log; this checkpoint closes the *reducer-level* self-certification gap the blueprint names, not a cryptographic-identity concern outside this slice's scope.

## Architecture / semantic invariants (verified by test)

- A `RESOLVE` event with `fromRole: "WORKER"` never produces a `BrainResolution` and never changes `state.status` away from `VERIFYING`/`REVIEW_REQUIRED`, for either `PASS` or `CHANGES_REQUIRED`.
- A `RESOLVE` event with `fromRole: "BRAIN"` or `fromRole: "OWNER"` behaves exactly as before (all 14 pre-existing tests pass unchanged in their assertions).
- A rejected self-certification `RESOLVE` still advances `currentFencingToken` (E7 convention: an accepted-but-business-rejected event still raises the fencing floor) without any other state mutation.
