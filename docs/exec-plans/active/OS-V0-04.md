## Goal

Implement a pure, deterministic resolver that selects, for every distinct `kind` (`CONFIG`/`POLICY`) + `key`, the single highest-precedence scoped control among caller-supplied layers, along the precedence chain PLATFORM → ORGANIZATION → CUSTOMER → PROJECT → JOB → ACTION — with a `PLATFORM` control marked `protectedFloor` never overridable at any lower scope, and every scope layer's own identity fail-closed correlated against the exact requesting tenant/customer/project/job/action context. Prove, via one real integration witness, that `compileProjectActivationProfile` consumes this resolver's `effectiveConfigRefs`/`effectivePolicyRefs` output unchanged, and that a material selected ref/version change propagates to a different `ProjectActivationProfile.sourceFingerprint` — without any modification to `project-activation-profile.ts`'s own compiler source or to `DeliveryRecipe`.

## Semantics

- `resolveEffectiveConfigurationPolicy(request)` takes the requesting scope identity (`tenantId` required; `customerId`/`projectId`/`jobId`/`actionRef` optional, each only meaningful if the deeper fields it implies are also supplied — an `actionRef` without a `jobId` is itself malformed) plus a flat, caller-supplied `controls` array of untyped (`unknown`) entries. Every control is independently, fully revalidated at this one boundary — there is no separate factory whose invariants a hand-built plain object could bypass (A11): `kind`/`scope`/`key`/`sourceRef`/`version`/`identity`/`protectedFloor` are all re-checked from raw shape, regardless of whether the caller used the exported TypeScript interfaces or hand-built an object matching their shape.
- Scope correlation is fail-closed (A7–A10): a control's `identity` must carry **exactly** the identity fields its own `scope` requires (`PLATFORM` none; `ORGANIZATION` tenantId; `CUSTOMER` +customerId; `PROJECT` +projectId; `JOB` +jobId; `ACTION` +actionRef), each exactly equal to the requesting context's own value for that field. A control claiming a scope deeper than the request actually supplies (e.g. a `JOB` control when the request carries no `jobId` at all) fails closed rather than being silently treated as inapplicable — this was deliberately tested as a distinct case from an outright identity mismatch.
- Same `kind`+`key` supplied more than once at the same scope is ambiguous and fails closed (A6) — this is exactly "the same effective layer," since every accepted control in one resolution call already correlates to that call's single fixed identity.
- Precedence: among all validated controls for a given `kind`+`key`, the winner is the entry at the numerically highest scope precedence (`ACTION` > `JOB` > `PROJECT` > `CUSTOMER` > `ORGANIZATION` > `PLATFORM`) — **unless** a `PLATFORM` entry for that `kind`+`key` is `protectedFloor: true`, in which case that floor is the only ever-valid answer and the presence of any other-scope entry for the same `kind`+`key` is itself an invalid, rejected input (A4) — never a silent override, never a silent discard.
- Output ordering is deterministic and independent of caller array order (A5): winners are sorted by `kind` then `key` (lexicographic).
- `effectiveConfigRefs`/`effectivePolicyRefs` are derived, one opaque ref string per winning control, via **`JSON.stringify([key, version, sourceRef])`** (Rev143 F1 correction — see Provenance) — a deterministic, injective structural encoding of the exact tuple, requiring no separate lookup to interpret. `effectiveControls` retains full provenance (`kind`/`key`/`scope`/`sourceRef`/`version`/`protectedFloor`) for explainable readback (A12).
- `ACTION` scope here is configuration/policy resolution provenance only — deliberately **not** execution approval, permission, entitlement, or protected-effect authority. This module has zero dependency on `authority.ts`/`approval-reference.ts`/`worker-routing-policy.ts` (enforced by the A14 boundary scan), so it is structurally impossible for a config/policy resolution to grant or imply protected authority.
- Pure and deterministic only: no persistence, no database, no provider/model call, no clock read (`now` is never needed — there is nothing time-varying in this resolver), no randomness, no new runtime dependency (A14 boundary scan confirms `package.json`'s `dependencies`/`devDependencies` are unchanged).
- Integration witness (A13, in `tests/project-activation-profile.test.ts`): one test proves `compileProjectActivationProfile`'s `profile.effectiveConfigRefs`/`profile.effectivePolicyRefs` are exactly the resolver's own output, byte-for-byte; a second test proves that overriding one key's selected control at a higher-precedence scope (a different `sourceRef`/`version`) changes the resolver's output and, fed through the same otherwise-identical `readyInputs`, changes `ProjectActivationProfile.sourceFingerprint`. Neither witness modifies `project-activation-profile.ts` itself.

## Reuse/dependency contract

No new runtime dependency was introduced (`package.json`'s `dependencies` remains empty; `devDependencies` remains exactly `@types/node`/`typescript`, confirmed by the A14 boundary test). `effective-configuration-policy.ts` imports only the existing `TenantScope`/`Customer`/`Project` identity types (type-only) — it does not import `authority.ts`, `approval-reference.ts`, `worker-routing-policy.ts`, `delivery-recipe.ts`, or `project-activation-profile.ts`. `project-activation-profile.ts`'s own source is entirely unchanged; the integration witness lives in its existing test file, consuming the new resolver's output as plain data.
