## Controlling design decisions actually taken

- **A (reuse economics core):** `CostAmount`/`createCostAmount`'s REPORTED-vs-UNKNOWN presence discipline is imported directly from `execution-economics-attribution.ts`, not re-implemented. No parallel `UsageEvent` ledger was created.
- **B (minimum admission port):** `execution-quota-admission.ts` exposes exactly the packet's own named primitives — resolve current allowance for an exact scope (`projectQuotaScopeUsage`), reserve (`admitQuotaReservation`), reject safely (the same function's `REJECTED` outcome), commit actual usage (`commitQuotaUsage`), release unused reservation (`releaseQuotaReservation`), and surface unknown/reconciliation state (`projectQuotaReadModel`). The store owns atomicity/idempotency; the pure module owns no provider/model logic at all.
- **C (scope):** `QuotaAdmissionScope` is deliberately the same top-level tenant/customer/project/plan(+version) tuple `ExecutionEconomicsLineage` already binds to — the smallest scope that is both a real existing identity in this codebase and sufficient to prove every mandatory witness. Job/run/attempt identify one reservation *within* that scope, not the scope itself.
- **D (fallback/retry):** a retry re-admits under the current envelope for its **own** new attempt (a distinct `attemptRef`) — it never reuses or bypasses the prior attempt's reservation, and (because each attempt's `idempotencyKey` is unique) a caller-side retry of the *same* attempt is a safe, non-double-reserving replay.
- **E (usage/cost truth):** `CostAmount` already distinguishes estimated/reserved (the `RESERVED` event's `amount`) from actual/measured (the `COMMITTED`/`RECONCILIATION_REQUIRED` event's `amount`) from UNKNOWN. No exchange-rate/subscription-allocation/provider-pricing table was invented.
- **F (product billing separation):** confirmed by the boundary scan — no invoice/refund/payment/credit-pack/public-pricing token appears anywhere in the new source.
- **G (AI execution envelope):** deliberately minimal — `QuotaEnvelope` carries only `scope` + `envelopeRef` + `sourceFingerprint` + a single REPORTED `limit`. No second AI budget engine, no non-monetary (call-count/retry/concurrency/time) ceiling was added — no live consumer at this head requires one, and inventing one un-evidenced would violate POLICY VALUES below.

## POLICY VALUES (packet's own constraint, honored structurally)

"There are no canonical global numeric defaults... never invent limits." `createQuotaEnvelope` **requires** a REPORTED `limit` — an envelope with an `UNKNOWN` limit cannot be constructed at all (verified directly by `tests/execution-quota-admission.test.ts` Q2, and by the boundary scan's dedicated assertion that `createQuotaEnvelope` contains no `??`-fallback for any caller-controlled policy value). A caller with no real policy value simply cannot admit anything — that is an integration-layer concern (treat "no envelope available" as BLOCKED/UNAVAILABLE), never this module's problem to paper over.

## ATOMICITY (packet's own constraint)

- **File store** (`FileDurableQuotaReservationStore`): `admit`/`commit`/`release` are fully **synchronous** methods with no `await` in their read-decide-write critical section — the same discipline `FileDurableConnectorConnectionStore.save()`/`FileDurableOutcomeJobExecutionStore.appendEvent()` already establish. Two "concurrent" async callers issued via `Promise.all` cannot interleave inside a synchronous JS function, so this genuinely proves single-process atomicity (`P1`), not merely a passing test by construction.
- **Postgres store** (`PostgresQuotaReservationStore`): `admit()` is the one operation with real shared-resource contention (two *different* idempotency keys in the same scope competing for the same remaining allowance), so it issues **one** atomic SQL statement — a `pg_advisory_xact_lock`-guarded CTE that reads current scope usage and decides RESERVED/REJECTED before inserting — rather than a read-then-write sequence across multiple `SqlClient.query()` calls (the port exposes no explicit transaction control, but a single top-level statement is itself an implicit Postgres transaction for its own duration, which is exactly the window the advisory lock needs). `commit()`/`release()` have no such cross-request contention (each touches only the one reservation its own idempotencyKey names), so they reuse the pure `commitQuotaUsage`/`releaseQuotaReservation` reducers against a small `SELECT`, relying on the same `UNIQUE (tenant_id, event_id)` + `ON CONFLICT ... DO NOTHING` + retry-on-loss pattern already established by `PostgresOutcomeJobExecutionStore`/`appendAndGetState`.

## PERSISTENCE decision (packet's own explicit framing)

"File-only proof is insufficient if the activated execution edge is genuinely multi-process... No concrete DB driver/live DB activation" applies here exactly as it does to every other Postgres store in this repository (`PostgresOutcomeJobStore`, `PostgresOutcomeJobExecutionStore`): the only currently **activated** execution lane is the single-process `"INJECTED"` executor kind (`ACTIVATED_EXECUTOR_KINDS`, unchanged), for which the synchronous file store is a sufficient, genuinely-atomic authority. The Postgres store is built as dark/proof scaffolding for a future genuinely multi-process activation, tested only against a purpose-built `FakeSqlClient` (no live database anywhere in this repository), exactly mirroring OS-V0-05's own precedent.

## A genuine defect found and fixed during this task's own adversarial witness construction

Writing `QI2` (a retry must not bypass an exhausted ceiling) first exposed a real bug in `projectQuotaScopeUsage`: a `COMMITTED` event whose actual amount was `UNKNOWN` contributed **zero** to the scope's outstanding total — silently freeing the reservation's allowance the instant real cost became unknown, which is exactly the "UNKNOWN treated as free" defect Minimum Adversarial Evidence #8 forbids (there, for *estimates*; the same principle applies to *actuals* affecting *future* admission decisions). Fixed by having a `COMMITTED`/`RECONCILIATION_REQUIRED` event with an `UNKNOWN` actual amount conservatively fall back to counting its **original RESERVED amount** toward `committedTotal`, keeping that allowance occupied until a real reconciliation resolves it. Guard-disable-verified: reverting the fix reproduces `QI2`'s exact failure (see below).

### F3 (rejection ordering) - REJECTED is now checked before ATTEMPT_STARTED is ever constructed

**Finding.** `quota.decision.status === "REJECTED"` was checked only after `ATTEMPT_STARTED` had already been unconditionally appended (and won), briefly making the run durably `RUNNING` before immediately appending a `BLOCKED` closing event. Rev176: "A rejected quota admission may persist REJECTED quota truth, but it must not create a RUNNING attempt."

**Correction.** In both `dispatchOutcomeJobExecutionRun` and `retryOutcomeJobExecutionAttempt`, the REJECTED check now happens immediately after admission and strictly before `ATTEMPT_STARTED` is ever constructed. A REJECTED decision returns `{ invoked: false }` with the run left at its current durable status (`ACCEPTED` for a fresh dispatch; the unchanged prior terminal attempt for a retry) - no `ATTEMPT_STARTED`, no `BLOCKED` event, no fake `RUNNING` attempt ever created. The `BLOCKED` execution-event type is no longer used by this module (it remains a valid, unmodified type for other, unrelated reasons elsewhere in this codebase).

This surfaced a real, previously-latent design gap: a `REJECTED` decision was being treated by `admitQuotaReservation` exactly like `RESERVED` for replay purposes - a *permanent* cached outcome. Since `dispatch`/`retry` no longer progress the run past `ACCEPTED`/its prior terminal attempt on rejection, a caller's only path to recovery is calling `dispatch`/`retry` again later with the identical idempotencyKey - which would have replayed the exact same stale `REJECTED` forever, even after the blocking reservation was released. **Fixed** in `admitQuotaReservation`/`findAdmissionEvent`: a `RESERVED` decision remains permanent (it already durably consumed real allowance), but a `REJECTED` decision - which consumed nothing - is now re-evaluated fresh against current usage on every later call with identical content; if it now fits, a genuinely new `RESERVED` event is appended (a distinct `eventId`, since `eventId` depends on `type`); if it still does not fit, the original cached `REJECTED` event is replayed unchanged rather than appending a duplicate-`eventId` row. New pure-domain witness `Q21` and Postgres witness `PG5` cover this directly; `QI1`/`QI2` were updated to assert the corrected `ACCEPTED`/unchanged-terminal-status behavior instead of the retired `BLOCKED` path; new `QI-concurrent-rejection` proves two concurrent rejections create zero fake attempts.

**A second real defect found and fixed while implementing this correction:** `PostgresQuotaReservationStore.admit()`'s `current_usage` SQL summed `amount_minor_units` over **every** row matching `type IN ('RESERVED','COMMITTED','RECONCILIATION_REQUIRED')` for the scope - since this store is strictly append-only (a `COMMITTED`/`RELEASED` transition never deletes or updates its reservation's earlier `RESERVED` row), this double-counted a reservation's original amount alongside its own later lifecycle row. Fixed by adding a database-assigned `id BIGSERIAL` column (migration `0003`) and selecting only the latest row per `idempotency_key` (`DISTINCT ON (idempotency_key) ... ORDER BY id DESC`) before summing - mirroring the pure `projectQuotaScopeUsage` reducer's own "latest event per reservation" fold exactly. Guard-disable-verified: reverting the test fake's equivalent computation reproduces `PG5`'s exact failure.
