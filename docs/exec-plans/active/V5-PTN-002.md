## Reconciliation against PR #24 (why it is not simply merged)

- PR #24's `resolvePartnerRoute` modeled eligibility on **capability admission alone** (`resolvePartnerCapabilityClaimStatus` against a `PartnerOrganization` + `PartnerCapabilityClaim` pair). Diffing PR #24's base (`912e66927e432c955fcd3135d302e0a8c941cc0c`) against current `main` confirmed `resolvePartnerCapabilityClaimStatus`'s signature/behavior is unchanged (only `revokePartnerCapabilityClaim`'s `revokedAt` validation was hardened in Rev62, unrelated to this function) — so PR #24's capability-side logic itself was not stale.
- What PR #24 never modeled is §6's own "explicit agency employee → client/account assignment is the authority" requirement (`partner-organization.ts`'s `PartnerClientAssignment`/`resolvePartnerClientAccess`, tenant/customer/project/serviceRef-scoped, per-employee). An admitted organization-level capability claim proves a partner organization **can** perform a class of work in general — it never proves any specific partner **employee** is actually authorized against the **specific** tenant/customer/project a routing decision is for. Routing on capability alone would let a capability-admitted partner organization be routed work for a client it has never been granted access to.
- This checkpoint therefore composes **both** existing authority dimensions into one routing decision — capability admission (`resolvePartnerCapabilityClaimStatus`) and per-employee client/project access (`resolvePartnerClientAccess`) — rather than porting PR #24 as-is or inventing a third, parallel authority model.

## Scope (this checkpoint)

- `src/domain/partner-routing-decision.ts`:
  - `PartnerRoutingCandidate` bundles one specific partner employee's contribution to a routing attempt: `partnerOrganization`, `capabilityClaim`, `partnerEmployeeMembership`, and that employee's own `clientAssignments`. This module has no persistence/lookup capability of its own (consistent with every other pure domain module in this codebase) — a caller supplies already-validated domain objects.
  - `resolvePartnerRoute(request)` — pure function, mirrors `resolveWorkerRoute`'s structure exactly. A candidate is eligible only when: its `capabilityClaim` and `partnerEmployeeMembership` structurally belong to its own `partnerOrganization`; the claim's `capabilityRef` matches `requiredCapabilityRef` and resolves `ADMITTED` as of the caller-supplied `asOf`; `decidedByOwnerId` does not literally reuse either the candidate's `partnerOrganizationId` or its `partnerEmployeeMembershipId` (Rev101 F1 correction — see below, a bounded opaque-identity-reuse guard, not a proof of independent authority); and the specific candidate employee resolves `AUTHORIZED` via `resolvePartnerClientAccess` for the request's `targetOwnership` (tenant/customer/project/serviceRef-scoped, revocation-aware). Selects the first eligible candidate in order; every other eligible candidate's partner organization (deduplicated) becomes `fallbackPartnerOrganizationIds`. Never throws on "no eligible candidate" — returns an explicit `REJECTED` decision with a mandatory `reason`. `reason` and `decidedByOwnerId` are always non-empty on every returned decision.
  - Exactly four sibling-module imports (`partner-organization.ts` × 2, `partner-capability-admission.ts`, `project-ownership.ts`), no filesystem/network/child_process coupling, no system-clock read, no persistence of the resulting decision.
- `tests/partner-routing-decision.test.ts` (24 tests: P1-P24) and `tests/v5-ptn-002-boundary-scan.test.ts` (6 tests) — the boundary scan pins the exact import list, the exported surface, and the "no secret/provider literal, no `Date.now()`" invariants.

## Rev101 correction (F1 — self-routing identity semantics)

Brain's Rev101 independent exact-head review (fresh-read from the canonical Drive Handoff, `CHANGES_REQUIRED, BOUNDED` against this PR's exact pushed head `87b777cc8747ea367d2a4d98f964525957fa9b21`) found a genuine gap: the original `(candidate.partnerOrganization.partnerOrganizationId as string) === decidedByOwnerId` check was never proven to compare values from the same semantic identity domain (`decidedByOwnerId` is a bare, unbranded, caller-supplied `string` with no repository-enforced binding to `PartnerOrganizationId` or any other identity type), and it never accounted for the candidate's own distinct `partnerEmployeeMembershipId` — a deciding identity equal to the candidate's *employee* id, rather than its *organization* id, sailed through undetected.

A fresh repo-wide search for an existing delegation/cross-domain identity-mapping primitive that could instead bind `decidedByOwnerId` to a provably independent identity found none (`project.ts`'s own `ownerRef` is an equally bare, unbranded, unrelated-concept string — binding to it would not add real proof either). Per Rev101's own explicit disjunction ("bind to an existing semantically compatible identity and enforce independence correctly, **or** narrow/remove the unsupported self-certification claim and fail closed where independence cannot be proven... must not invent a new IAM"), this checkpoint takes the second path: the module's own doc comments were rewritten to state precisely and only the narrow, honestly-provable claim — `decidedByOwnerId` is rejected when it literally reuses either identifier the candidate itself carries (`partnerOrganizationId` **or** `partnerEmployeeMembershipId`), mirroring the exact same bounded opaque-identity-reuse discipline `admitPartnerCapabilityClaim`'s own self-admission guard (`partner-capability-admission.ts`, Rev55 F1) already uses and Brain already PASSed. The code itself is widened (the equality check now covers both identifiers instead of one); the documentation is narrowed (no more overclaiming this proves independent authority).

`isEligible`'s check is now: `decidedByOwnerId !== candidate.partnerOrganization.partnerOrganizationId AND decidedByOwnerId !== candidate.partnerEmployeeMembership.partnerEmployeeMembershipId`. New test P24 proves the specific gap Rev101 named: a `decidedByOwnerId` equal to a candidate's `partnerEmployeeMembershipId` (not its `partnerOrganizationId`) is rejected exactly as the organization-id case (P6) already was. P6's own title/framing was corrected from the overclaiming "§12 'cannot self-certify'" language to the same bounded "opaque-identity-reuse guard" framing.

Sanity-checked: the fix was temporarily reverted via `git stash` while the updated test file was kept — exactly P24 failed (P6, the pre-existing organization-id case, still passed) — confirming the new assertion genuinely detects the gap the org-id-only check missed; the fix was then restored and 738/738 reconfirmed.

No exported symbol was added or removed, so `tests/v5-ptn-002-boundary-scan.test.ts`'s "exact expected surface" assertion required no update.

## Architecture / semantic invariants (verified by test)

- An admitted capability claim alone is **not** sufficient to route work to a partner: a candidate with no client assignment at all for the target project (P17), only a **revoked** assignment (P18), or an assignment scoped to a **different** tenant/customer/project (P19) or a **different `serviceRef`** (P23, extending Rev62's own serviceRef-exactness invariant into routing) is rejected even though its capability claim is genuinely `ADMITTED`.
- Per-employee granularity is real, not cosmetic: two employees at the *same* partner organization, one authorized for the target project and one not, resolve differently (P22) — the authorized employee's membership id is recorded on the decision (P21), not merely the partner organization.
- All of PR #24's original semantics are preserved: capability-ref mismatch (P2), UNVERIFIED (P3)/EXPIRED (P4)/REVOKED (P5) claims rejected, opaque-identity-reuse self-routing guard excluded on the organization-id dimension (P6) and, per the Rev101 correction below, the employee-membership-id dimension (P24), no-eligible-candidate REJECTED with empty fallback (P7), first-eligible-selected/rest-as-fallback-in-order (P8), structurally mismatched claim ownership treated as ineligible not thrown (P9), fail-closed on malformed structural input (P10-P13), `reason` always non-empty (P14), fallback deduplication (P15), an ineligible-but-earlier candidate never beating an eligible later one (P16), and a structurally mismatched employee-to-partner-org relationship treated as ineligible not thrown (P20).
- Sanity-checked: the `resolvePartnerClientAccess` eligibility check was temporarily removed and the build/tests rerun — exactly the five tests proving the new tenant/client/project dimension (P17, P18, P19, P22, P23) failed, with every other test (including all of PR #24's original semantics) still passing; the fix was then restored and 737/737 reconfirmed.
