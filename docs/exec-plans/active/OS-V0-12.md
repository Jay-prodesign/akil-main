## Goal

Add a pure, stateless **observability composer** on top of EXISTING, UNMODIFIED V0 primitives, so an operator (via a caller-injected read source wired into the existing `/os/admin` view) can see, for one organization's current operational state: task state vs worker health (from `OutcomeJobExecutionRunState`), connection health including the real scoped kill-switch signal (`REVOKED`) (from `ConnectionBinding`), cost/quota (from `QuotaReadModel`, passed through verbatim), pending approvals (from caller-supplied wait/resume pairs — honestly bounded by the wait store's own exact-id-only lookup contract), and audit/evidence (from `EvidenceReference`/`VerificationResult` pairs). No new domain authority, no new persistence, no new runtime dependency, no second resolution/status model duplicating an existing one's own vocabulary.

## Semantics

- **Task state vs worker health** (Rev194's own named distinction). `TaskObservability.runStatus`/`currentAttemptStatus` are the TASK's own truth, read verbatim from `OutcomeJobExecutionRunState`. `workerHealth` is a narrower, separately-derived `"ACTIVE" | "AWAITING_CONTROL_ACK" | "IDLE" | "UNKNOWN"` signal: `ACTIVE` while the current attempt is `RUNNING` with no outstanding `pendingControlRequest`; `AWAITING_CONTROL_ACK` while `RUNNING` with one; `IDLE` once the current attempt reaches an ordinary terminal outcome (`SUCCEEDED`/`FAILED`/`CANCELLED`/`TIMED_OUT`) or no attempt has started yet; `UNKNOWN` whenever the attempt's own status is itself ambiguous (`STALLED`/`DEGRADED`/`BLOCKED`/`UNKNOWN`/`UNSUPPORTED`) — exactly the cases the existing reducer already refuses to resolve further without a fresh attempt or operator intervention.
- **Connection health and the scoped kill switch**. `ConnectionObservability` surfaces `connectionState` verbatim and derives `degraded`/`killSwitchEngaged` directly from it (`DEGRADED`/`REVOKED` respectively) — this repository has no generalized kill-switch abstraction today; `REVOKED` (reachable only through the existing `mutateConnectorConnectionStateAsAdmin` admin-authorized mutation) IS the real scoped-disable mechanism, surfaced honestly rather than wrapped in an invented new object.
- **Cost/quota**. `QuotaReadModel` is passed through the view verbatim (`quota?: QuotaReadModel`) — no re-derivation, no re-wrapping, no new monetary/unit model.
- **Pending approvals**. `DurableProtectedDecisionWaitStore` has no enumeration method by design (confirmed by inspection before this packet — only exact-`waitRequestId` lookup). This composer never invents one: it takes caller-supplied `{request, resume?}` pairs (a caller who already knows which `waitRequestId`s are outstanding for its own job/run) and reports `resolved: boolean` (resume authorization present) plus `resolvedAt` when true. This is an honestly-disclosed bound, not a silent gap: a caller with no independent way to enumerate outstanding waits simply supplies an empty list, and the view renders zero pending approvals rather than fabricating a count.
- **Audit/evidence**. `AuditEvidenceObservability` correlates caller-supplied `{evidence, verification?}` pairs, surfacing `verificationStatus` (`PASSED`/`FAILED`) only when a real `VerificationResult` was supplied — absent verification renders no `verificationStatus` field at all, never a fabricated default.
- **Admin wiring**. `resolveOperationalObservabilityView`/`OperationalObservabilitySource` mirror the Rev183 F3 `resolveResourceBindingView`/`OrganizationResourceBindingSource` pattern exactly: an absent source renders `NOT_ACTIVE` (honest Phase A default, never fabricated); a wired source always returns a real (possibly empty-dimensioned) `OperationalObservabilityView` — there is no separate "never bootstrapped" state here, since every dimension of the view is already independently optional/empty by construction. This optional source is threaded all the way into the LIVE `/os/admin` HTTP route (`internal-os-request-handler.ts` → `internal-os-http-server.ts`) and rendered (`internal-os-render.ts`'s `renderOperationalObservabilityCard`) as of the Rev195 F1 correction round below — the initial Phase A submission deferred this exact step (mirroring Rev183 F3 → Rev184 F3-residual's two-round precedent), and Rev195 F1 closed it within the same packet instead of waiting for a second round.
