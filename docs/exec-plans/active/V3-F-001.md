## Rev28 bounded correction (2026-09-02) — CHANGES_REQUIRED_SOURCE_SECURITY

Brain Handoff Rev28 finding on PR #8: "The resolver checks requested ownership before querying the source but does not fail closed if the returned projection itself carries a different tenant/customer/project scope. A faulty or compromised source could therefore yield READY with foreign-scope data."

Required bounded correction: "validate returned projection tenantId/customerId/projectId against requested ownership before READY; fail closed on any returned-scope mismatch; add adversarial tests for foreign tenant/customer/project projections; verify viewerRole cannot be emitted from a non-current membership under the existing membership semantics, proving via tests if the input contract already guarantees currentness."

Root cause: `resolveProtectedTeamAttentionView`'s `requireTenantOwnership` check proves the *caller's session* is allowed to see the requested tenant/customer/project scope. It proved nothing about what `source.getTeamAttentionProjection` actually returned — a `TeamAttentionSource` implementation that is faulty (wrong lookup key) or compromised (deliberately substitutes data) could hand back a `TeamAttentionProjection` for a completely different tenant/customer/project, and the resolver would wrap it in `READY` unexamined.

Fix (`src/web/team-attention-view-state.ts`): after obtaining a defined `projection` from the source, `resolveProtectedTeamAttentionView` now independently compares `projection.tenantId`/`projection.customerId`/`projection.projectId` against `input.requestedOwnership`'s own three fields; any mismatch resolves `UNAVAILABLE` (the same honest "no trustworthy data" outcome the type already used for a missing/throwing source) rather than `READY`. No new `TeamAttentionViewState` union member was added — `renderTeamAttentionSection` (`shell-render.ts`) already renders every non-`READY` kind identically as "Unavailable," so this fail-closed path needed no render-layer change.

Second required item — "verify viewerRole cannot be emitted from a non-current membership": `OrganizationMembership` (V3-ORG-001, merged) carries exactly four fields (`membershipId`/`tenantId`/`principalRef`/`role`) and no status/supersede/revoke/timestamp field of any kind in this bounded slice (unlike `OwnershipAssignment`, which does have provenance-preserving supersede semantics). There is therefore no representable "non-current" `OrganizationMembership` value for `buildTeamAttentionProjection`'s existing tenant-match check to fail to catch — this is proven structurally by a new test asserting the type's exact closed field set, plus a corroborating behavioral test, rather than by adding a check against a state dimension that does not exist. No source change was required for this half of the correction.

**This structural argument was rejected by Brain at Rev29 as insufficient — see the Rev29 section immediately below.**

## Rev29 bounded correction (2026-09-02) — CHANGES_REQUIRED_SOURCE_SECURITY (membership currentness)

Brain Handoff Rev29 accepted the Rev28 returned-scope validation and its regression evidence at head `322b107c1ef3f749ebf6c38744baa6435724276f` outright ("Returned projection tenantId/customerId/projectId is independently validated against requested ownership before READY... adversarial coverage is accepted... Full regression: 519/519 pass, 0 fail, exit 0... Strict typecheck: exit 0... Dependency/lockfile drift: none"), but reopened the membership-currentness half of Rev28's second required item as an **OPEN FINDING**:

> "viewerRole membership currentness remains unproven. The fact that OrganizationMembership's bounded type shape lacks a lifecycle/status field does not prove that a supplied membership object is current; a stale/historical membership can still be represented by the same shape unless currentness is established at an authoritative source boundary. The controlling V3 Workstream A acceptance contract explicitly requires that stale role/membership state cannot grant access."

Root cause: the Rev28 fix proved something true but insufficient — that `OrganizationMembership`'s field set cannot *encode* staleness. It did not prove that any given `viewerMembership` value handed to `buildTeamAttentionProjection` actually *is* the principal's current membership. A caller could construct or receive a stale/superseded `OrganizationMembership` value (identical in shape to a current one) and it would still pass the tenant-match check and surface `viewerRole` — exactly the "stale role/membership state can grant access" outcome the V3 Workstream A contract forbids.

Required bounded correction: "Before emitting READY + viewerRole, establish membership currentness from an authoritative membership source/boundary. Unknown or unproven membership currentness must fail closed to UNAVAILABLE, or suppress viewerRole only if that path is demonstrably contract-compatible... Do not treat a caller-provided bare isCurrent/currentness boolean as authority. Add focused tests covering: authoritative current membership; stale/superseded membership; unknown/unproven currentness. Preserve the already accepted returned-projection tenant/customer/project scope protections and existing fail-closed behavior."

Fix (`src/domain/team-attention-projection.ts`, the one file this checkpoint owns that constructs a `TeamAttentionProjection` — confirmed by repo-wide search that `buildTeamAttentionProjection` has exactly two call sites, this module's own fixture and nothing else, so gating construction itself is equivalent to gating "before emitting READY"):

- New exported type `MembershipCurrentnessRecord { membershipId; tenantId; supersededAt? }` — a minimal, append-only directory-entry contract mirroring `OwnershipAssignment`'s own `supersededAt`-based currentness proof (V3-OWN-001), deliberately **not** a bare boolean: a directory record carries its own membershipId/tenantId identity that must independently match the membership being vouched for, so it cannot be fabricated inline the way an unstructured `isCurrent: true` flag could.
- `buildTeamAttentionProjection` gains an optional `viewerMembershipCurrentness?: ReadonlyArray<MembershipCurrentnessRecord>` input. `viewerRole` is now surfaced only when the existing tenant-match check passes **and** exactly one non-superseded (`supersededAt === undefined`) record in the directory matches the viewer's own `membershipId` **and** `tenantId`.
- Every other outcome — no directory supplied at all, a directory with no matching record, a matching record that carries `supersededAt`, or a data-integrity ambiguity (more than one active match for the same membershipId/tenantId) — fails closed to `viewerRole` simply absent (`Object.hasOwn(projection, "viewerRole") === false`), the same "honestly absent, never guessed" contract this projection already applies to every other optional field. The rest of the projection (`owners`, `attention`) is unaffected — suppressing only `viewerRole` was judged the smaller, contract-compatible correction over failing the whole view to `UNAVAILABLE`, since `viewerRole` was already optional by this type's own existing contract and a precedent test already proved the shell tolerates its absence.
- Unlike `resolveCurrentOwner` (which throws on a data-integrity ambiguity for `OwnershipAssignment`), an ambiguous currentness match here is treated identically to "unproven" rather than thrown — a single optional display label warrants the smaller blast radius of silent omission over crashing the whole page render.
- Fixture (`src/fixtures/website-build-v1-team-attention.ts`): added `WEBSITE_BUILD_V1_VIEWER_MEMBERSHIP_CURRENTNESS`, one active record for the reference viewer membership, so the fixture's own `viewerRole: "STAFF"` remains genuinely proven current rather than merely tenant-matched.
- No change was needed in `src/web/team-attention-view-state.ts` — `resolveProtectedTeamAttentionView`'s Rev28 fail-closed behavior is preserved verbatim; it operates on the already-constructed projection, and currentness is now a construction-time guarantee upstream of it.

## Architecture / semantic invariants

- `buildTeamAttentionProjection` is pure and reuses `resolveCurrentOwner` (V3-OWN-001) independently for each of the four `OwnerRole`s — one role is never inferred from another (§9: "render separately").
- `viewerRole` is surfaced only when the supplied `viewerMembership.tenantId` exactly matches the requested `ownership.tenantId` — a cross-tenant membership is never surfaced (adversarial test coverage). (Rev29 supersedes Rev28's structural-only claim here) tenant match is necessary but not sufficient: `viewerRole` additionally requires `isViewerMembershipCurrent` to find exactly one non-superseded `MembershipCurrentnessRecord` matching the viewer's own `membershipId`+`tenantId` in the caller-supplied `viewerMembershipCurrentness` directory — an authoritative-source proof, not a structural argument about the type's field set.
- `attention` is surfaced only when the supplied `AttentionState.tenantId`/`projectId` exactly match the requested `ownership` — mirroring `buildAttentionState`'s own existing two-field fail-closed check verbatim (no new isolation rule invented).
- `resolveProtectedTeamAttentionView` performs the identical `requireTenantOwnership` check as `resolveProtectedSnapshotView` before ever querying `source` — a tenant/project mismatch never reaches the new port at all. (Rev28) It additionally verifies the *returned* `projection`'s own tenant/customer/project identity against the requested ownership before ever returning `READY` — a faulty or compromised source's foreign-scope projection resolves `UNAVAILABLE`, never `READY`.
- `TeamAttentionViewState`'s `FORBIDDEN_TENANT_SCOPE` and `UNAVAILABLE` render the identical "Unavailable" message in the shell — no boundary-detail difference is ever exposed to the page.
- `team-attention-projection.ts` imports nothing from `outcome-job.ts`, `authority.ts`, `capability-admission.ts`, `connection-authority.ts`, or `partner-organization.ts` — visibility cannot transition a job or grant permission.
- No file in this checkpoint imports `commercial-authority.ts`, `service-capability-routing.ts`, or `operations-attention.ts` — structurally impossible, since none of those files exist on this branch (cut from merged `main`, prior to any of PR #5/#6/#7 merging).
- `teamAttentionSource` is optional everywhere it is threaded (`createRequestHandler`, `createHttpServer`) — every existing caller/test that omits it continues to compile and behave exactly as before (verified: all 483 pre-existing tests still pass unchanged).
