## Design decisions and why

- **Mirrors `DelegatedAccessGrant` (OS-V1-02) as its closest precedent, but is deliberately NOT the same primitive.** A `DelegatedAccessGrant` delegates a SUBSET of a membership's EXECUTION authority inside the same tenant's own organization context. Break-glass support access is a DIFFERENT shape entirely: a support principal (who may hold no membership in the target organization at all) viewing READ-ONLY observability data ACROSS a tenant boundary. Reusing `DelegatedAccessGrant` itself would conflate "delegated execution authority" with "cross-tenant support visibility" — two genuinely different authority questions this corridor's own "re-resolve fresh, never conflate" discipline keeps separate.
- **`expiresAt` is mandatory, never optional** (unlike `DelegatedAccessGrant`'s own precedent, which also makes it mandatory, so this is consistent) — "time-bounded" is non-negotiable for a support-access grant specifically, since it exists to view potentially sensitive cross-tenant data.
- **`consentRequired` gates on a FRESH, per-call `consentRef`, never a value recorded once on the grant at mint time.** Consent for a real support session is a per-session fact (the affected org's own representative consents to THIS session, not to "any future session this grant might authorize") — recording it once on the grant would let a single consent event authorize unlimited future sessions, which is not "consented where required."
- **The identity check mirrors OS-V1-02's own authenticated-delegated-access discipline exactly**: `currentPrincipalRef` must exactly match `grant.grantedToRef` — a grant can never be exercised by anyone other than who it was issued to, regardless of who presents it, closing the same "stolen credential/grant" risk class OS-V1-02 already closed for delegation.
- **`BreakGlassSupportAccessAudit` is mandatory on every `GRANTED` result, never optional** — mirroring `ProtectedDecisionResumeAuthorization`'s own `decisionEvidenceRef`/`resolvedAt` discipline exactly. There is no code path that can produce a `GRANTED` outcome without it; "unaudited access" is structurally impossible, not merely checked.
- **The gate changes WHO may assemble an observability view, never WHAT that view honestly shows.** `UNKNOWN1` proves this directly: once break-glass access is granted, the SAME already-accepted `composeOperationalObservabilityView` composition is used, and it still honestly reports an ambiguous attempt as `UNKNOWN`/`STALLED` worker health — the new gate adds an authorization boundary, not a second, laxer observability path that could ever show "UNKNOWN as success."
