## Scope (this checkpoint)

- New `src/domain/durable-project-store.ts`: `DurableProjectStore` port (`create`/`update`/`get`/`listByCustomer`/`listByTenant`) + `FileDurableProjectStore` reference implementation.
  - **Collision-safe Project identity**: `Project` has a composite identity — `(tenantId, customerId, projectId)` — and a bare `projectId` is never asserted globally unique across customers within a tenant. The compound storage key is `base64url(JSON.stringify([customerId, projectId]))`: JSON's own string-escaping makes this encoding injective, so no two distinct `(customerId, projectId)` pairs can ever collide onto the same key regardless of what characters either field contains (proven by a dedicated adversarial test using a customerId/projectId split that WOULD collide under naive `"::"`-joining).
  - **create/put semantics**: `create` is the sole creation path, idempotent on an exact-content replay (safe no-op, no version bump), fails closed (`ProjectConflictError`) on any existing record under the same compound key whose content differs even in one field.
  - **update semantics**: optimistic-concurrency versioned (`expectedVersion`), fails closed (`ProjectVersionConflictError`) on a nonexistent record or a stale version, fails closed (`ProjectConflictError`) on any attempt to reassign a project's own tenant/customer/project identity.
  - **exact get**: `get(tenantId, customerId, projectId)` — direct compound-key lookup, matching `WorkProjectSource.getProject`'s own shape exactly.
  - **customer-scoped and tenant-scoped listing**: `listByCustomer`/`listByTenant`, both needed by the existing `WorkProjectSource`/`OrganizationResourceBindingSource` consumer shapes.
  - **restart/replay reconstruction**: every read reconstructs the full tenant record set from disk, no separate in-memory index that could diverge — proven by a dedicated restart test.
  - **full fail-closed persisted-state validation**: every structural invariant `project.ts`'s own `createProject` enforces at construction time is re-checked on read, plus a stored-key-vs-embedded-identity consistency check unique to this module's composite-key scheme (a corrupted or hand-forged file could not otherwise be caught).
  - **cross-tenant/cross-customer substitution rejection**: proven by dedicated adversarial tests (a different tenant's file never sees this tenant's projects; a forged record whose embedded tenantId disagrees with its own tenant file fails closed; the compound key itself makes cross-customer substitution structurally impossible rather than merely checked).
  - **real cross-process concurrency/race proof**: `tests/helpers/project-store-race-worker.ts` (new, cloned pattern) + `tests/durable-project-store-concurrency.test.ts` (new) — 5 real spawned OS processes race to `update` the same stored `Project` at the same `expectedVersion`; exactly one wins, every loser fails closed with `ProjectVersionConflictError`, and a fresh store instance over the same `baseDir` reconstructs exactly the winner's state.
  - **no new persistence framework or runtime dependency**: only `node:fs`/`node:path`/`node:crypto`, reusing the already-accepted `linkSync` lock primitive.
- New `src/web/work-project-admin-source.ts`: `createDurableWorkProjectSource(store: DurableProjectStore): WorkProjectSource` — the smallest existing blocked consumer this store genuinely unlocks. `DurableProjectStore.get`'s own signature already matches `WorkProjectSource.getProject`'s shape exactly, so this adapter is a thin, direct pass-through: no new query shape, no new product scope. Proven end to end through the real, unmodified `resolveWorkView`/`resolveWorkProjectDetailView` resolvers in `internal-os-view-state.ts` with real staff-assignment fixtures.
- Tests: `tests/durable-project-store.test.ts` (new, 19 tests — create/idempotent-replay/conflict, collision-safety across a customer/project split, get/listByCustomer/listByTenant, update/version-conflict/identity-reassignment × 2, cross-tenant isolation, restart reconstruction, 6 corrupted-file fail-closed cases); `tests/durable-project-store-concurrency.test.ts` (new, 1 test, 5-process race); `tests/web-work-project-admin-source.test.ts` (new, 5 tests — real surfacing, nonexistent-returns-undefined, cross-tenant isolation, cross-customer isolation, end-to-end `resolveWorkView`/`resolveWorkProjectDetailView`).
- Full regression: **2900/2900 passing** (2875 pre-existing on PR #157's tip + 25 new), clean strict typecheck, zero new runtime dependency.

## Guard-disable sanity

Two guards are genuinely novel to this module (not merely cloned-and-already-proven elsewhere):

1. **Collision-safe compound-key encoding.** Temporarily swapped `compoundKeyFor` from `base64url(JSON.stringify([customerId, projectId]))` to a naive `` `${customerId}::${projectId}` `` join, rebuilt, reran the suite: exactly the one dedicated adversarial collision test failed (two projects with a `customerId`/`projectId` split that collides under naive joining silently overwrote each other), no other test regressed. Restored; verified byte-identical via `diff` before the final regression run.
2. **Stored-key-vs-embedded-identity revalidation on read.** Temporarily short-circuited the `expectedKeyForIdentity !== expectedKey` check in `validatePersistedProject` (`false && ...`), rebuilt, reran the suite: exactly the "corrupted: a stored key not matching the embedded (customerId, projectId)" test failed, no other test regressed. Restored; verified byte-identical via `diff` before the final regression run.

The cross-process lock mechanism itself is cloned verbatim from `durable-customer-offboarding-request-store.ts` (already guard-disable-sanity proven there) and is independently re-proven here by the dedicated 5-process race test passing deterministically — not re-sanity-checked as a separate "disable the lock" step, since that would just be re-running the same already-accepted primitive's own proof. The `update`'s identity-reassignment check is the same shape as `CustomerOffboardingRequestConflictError`'s own already-proven identity check, cloned into this module; it is covered by two dedicated adversarial tests here (tenant reassignment, customer reassignment) but not separately guard-disable-sanity re-run, consistent with `OBS-ADMIN-SOURCE-001`'s own stated discipline for an already-proven pattern cloned verbatim.
