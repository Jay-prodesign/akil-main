## Scope (this checkpoint)

- New `src/domain/durable-customer-offboarding-request-store.ts`: `DurableCustomerOffboardingRequestStore` interface (`createRequested`, `transitionToTerminal`, `get`, `list`, `listPending`) + `FileDurableCustomerOffboardingRequestStore` implementation.
  - `createRequested`: sole creation path. No existing record → create at version 1. An existing record with EXACTLY identical content → safe no-op (idempotent replay), never a version bump or error. An existing record that differs in any field (including one already past `REQUESTED`) → `CustomerOffboardingRequestConflictError` (collision-safe keying: an accidental `requestId` collision between two different customers can never silently co-opt or clobber the other, mirroring `connectionBindingId`'s own established discipline).
  - `transitionToTerminal`: sole terminal-transition path (`REQUESTED → COMPLETED | DENIED`). Fails closed, **in this order**: (1) no existing record → version conflict; (2) `expectedVersion` mismatch → version conflict; (3) current status already terminal → `CustomerOffboardingRequestTerminalError` (no resurrection); (4) `next`'s own tenant/customer/requestId doesn't exactly match the existing record's → `CustomerOffboardingRequestConflictError` (no identity reassignment). `next.status` must be `COMPLETED` or `DENIED` (validated before the lock is even taken).
  - Every read revalidates every persisted field's shape, including status-to-decision-field consistency (`REQUESTED` carries no decision fields; `COMPLETED` requires `decidedByRef`/`decidedAt` and no `denialReason`; `DENIED` requires all three) and cross-tenant containment (an embedded `tenantId` not matching the file it's stored under fails closed).
- New `src/web/customer-offboarding-admin-source.ts`: `createDurableCustomerOffboardingAdminSource(store)`, a thin adapter satisfying `V2-ADMIN-SURFACE-001`'s `CustomerOffboardingAdminSource` port from the new durable store — the pending-offboarding queue on `/os/admin` is no longer only an abstract optional source with no real implementation anywhere.
- Tests: `tests/durable-customer-offboarding-request-store.test.ts` (22: create-once/idempotent-replay/collision-conflict, get/list/listPending, both terminal transitions, 4 adversarial transition-guard tests, cross-tenant isolation, restart/replay reconstruction, 8 persisted-state-corruption tests); `tests/durable-customer-offboarding-request-store-concurrency.test.ts` + `tests/helpers/customer-offboarding-request-race-worker.ts` (1 genuine 5-process OS-level race proof); `tests/web-customer-offboarding-admin-source.test.ts` (3: real pending surfaced, terminal never surfaced, foreign tenant never surfaced).

## Errors and fixes (this checkpoint)

- **Guard-order bug caught live by the multi-process race test, not a flake.** The first implementation checked "is the current record already terminal" BEFORE checking "does the version match" inside `transitionToTerminal`. Since a successful transition always increments the version, a racing loser whose `expectedVersion` was stale (because a winner had already terminalized the request) hit the terminal-status check first and threw `CustomerOffboardingRequestTerminalError` — a type the race-test worker script did not expect or catch, crashing the worker process and failing the test. Diagnosed by re-reading the actual thrown error (not re-run speculatively): the correct fix is checking version BEFORE terminal-status, since a caller whose version still matches can only ever be looking at a `REQUESTED` record by construction (nothing else could change the record without also bumping its version past what that caller observed). Reordered; re-ran the race test three additional times after the fix with no further failures; re-verified the "no resurrection... even at the correct version" adversarial test (which exercises the terminal-status check via a caller who legitimately supplies the terminal record's own CURRENT version) still passes correctly under the new order.
